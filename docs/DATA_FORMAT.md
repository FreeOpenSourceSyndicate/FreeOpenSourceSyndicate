# Gameplay data format (ADR-0003)

Content lives in `assets/data/` as **JSON**, parsed by the small, dependency-free
reader in `src/core/data/` (`Json.h`, `Json.cpp`, `MissionData.h`,
`MissionData.cpp`). This document is the schema reference.

The parser is **not** a general JSON implementation. It supports the subset our
content needs — objects, arrays, strings, numbers, booleans, `null` — and rejects
anything else with a readable error. To keep files valid JSON and diffable,
**comments and trailing commas are not allowed.**

## Why JSON, hand-rolled (ADR-0003)

- Ubiquitous and easy for LLM agents to generate and review; human-diffable.
- No third-party dependency, so the low-spec binary stays small (AGENTS.md §1b).
- The loader lives in `core`, so it is unit-tested headlessly and stays SDL-free
  (ADR-0002). The engine layer only decides *where* the file is.

## Mission schema

A mission file describes one mission. Example:
`assets/data/missions/demo.json`.

```jsonc
{
  "name": "Downtown Sweep",   // optional, defaults to "Mission"
  "width": 24,                 // required, > 0
  "height": 24,                // required, > 0

  "buildings": [               // optional
    { "x": 5, "y": 5, "width": 4, "height": 4 }
  ],

  "blocked": [                 // optional: individual blocked tiles
    { "x": 12, "y": 10 }
  ],

  "objective": {               // optional; defaults to eliminate-all
    "kind": "eliminate"        // "eliminate" | "reach" | "survive"
    // "kind": "reach", "tileX": 20, "tileY": 20
    // "kind": "survive", "seconds": 60
  },

  "agents": [                  // required, non-empty
    {
      "agentId": "trooper",    // optional: inherit a template from agents.json
      "name": "ALPHA",         // optional, defaults to "AGENT" (or the template's)
      "team": "player",        // "player" | "enemy" | "civilian"
      "x": 1.5, "y": 1.5,      // required, tile coordinates (fractional)
      "speed": 3.0,            // optional, tiles/second, > 0
      "health": 100,           // optional, > 0
      "weapon": {              // optional; defaults to the pistol
        "name": "Rifle",
        "damage": 8,
        "range": 9,
        "fireRate": 4,         // shots/second, > 0
        "accuracy": 0.65       // [0, 1]
      },
      "weaponId": "rifle"      // optional: reference weapons.json by id
    }
  ]
}
```

### Field notes

- **`buildings`** are rectangular footprints; **only the perimeter blocks
  movement**, so the interior stays walkable. `width`/`height` are in tiles and
  must be positive.
- **`blocked`** marks single tiles as impassable (in addition to buildings).
- **`objective`** is the mission's win condition; omit it for the default.
  - `"eliminate"` — win when every enemy agent is dead (the default, so existing
    missions are unchanged).
  - `"reach"` — win as soon as any living player agent stands on the tile
    `(tileX, tileY)`. Both are required and are integer tile coordinates.
  - `"survive"` — win after `seconds` (a number, `> 0`) of mission time have
    elapsed.
  - The lose condition is universal and unchanged: every player agent dead.
    Civilians never affect win/lose. `Mission::elapsedSeconds()` reports the
    mission clock (frozen once the mission ends).
- **`team`** must be `player`, `enemy`, or `civilian`. Civilians are never
  auto-targeted and never affect win/lose (see `AGENTS.md` §10).
- **Agent coordinates** are fractional tile positions, matching `Agent(x, y, …)`;
  `1.5, 1.5` is the centre of tile `(1, 1)`.
- **`weapon`** is optional per agent. Omitted fields fall back to the pistol's
  values. `fireRate` must be greater than zero.
- **`weaponId`** references a weapon in the shared catalogue by id (see below).
  An agent may set either `weapon` (inline) **or** `weaponId`, not both; an
  unknown id is a readable error.
- **`agentId`** references an agent template in the shared catalogue. The
  template supplies `name`, `team`, `speed`, `health`, and the weapon; any field
  the mission also sets inline overrides the template. `x`/`y` always come from
  the mission (a template has no position). An unknown id is a readable error.
- Unknown keys are ignored, so the format can grow without breaking older files.

## Shared catalogues (`weapons.json`, `agents.json`)

Weapons and agent templates that several missions share live in two catalogue
files at the **content root** (`assets/data/`), so they can be edited once and
referenced by id instead of copied into every mission (ADR-0003):

```jsonc
// assets/data/weapons.json
{
  "weapons": [
    { "id": "pistol", "name": "Pistol", "damage": 10, "range": 6, "fireRate": 2.5, "accuracy": 0.72 },
    { "id": "rifle",  "name": "Rifle",  "damage": 8,  "range": 9, "fireRate": 4,   "accuracy": 0.65 }
  ]
}
```

```jsonc
// assets/data/agents.json
{
  "agents": [
    { "id": "guard", "name": "GUARD", "team": "enemy", "speed": 3, "health": 70, "weaponId": "rifle" }
  ]
}
```

- Each entry needs a non-empty **`id`**, unique within its file; a duplicate or
  missing id is a readable error.
- A weapon entry takes the same fields as an inline `weapon` object (plus `id`).
- An agent entry takes the same fields as a mission agent (`id`, `name`, `team`,
  `speed`, `health`) plus `weapon` or `weaponId`; it has no `x`/`y`.
- **Both are optional.** A mission that inlines everything (such as `demo.json`)
  needs no catalogues and behaves exactly as before. A missing catalogue file is
  not an error; the game still starts (AGENTS.md §1b).
- A mission loaded from disk (`MissionData::loadFromFile`) automatically loads
  the catalogues **next to it**: a mission in `assets/data/missions/` finds
  `assets/data/weapons.json` and `assets/data/agents.json`.

## Loading

```cpp
#include "core/data/MissionData.h"

fossynd::core::MissionData data;
std::string error;
if (!fossynd::core::MissionData::loadFromFile(path, data, error))
{
    // error is human-readable, e.g. "line 12: unknown team 'droid'"
}

fossynd::core::TileGrid grid = fossynd::core::buildGrid(data);
fossynd::core::Mission mission(grid, seed);
fossynd::core::populateMission(data, mission);
```

The engine layer (`src/game/`) decides the file path and renders the result; it
contains no schema knowledge.

## Choosing which mission to load

The path is resolved at startup, highest priority first:

1. **`--mission <path>`** on the command line (an explicit file that must exist).
2. **`mission = <path>`** in the config file (an explicit file that must exist).
3. **`mission_dir = <dir>`** in the config file: `<dir>/demo.json` is used.
4. **Built-in fallbacks**, checked for existence in order — the first that
   exists wins: `assets/data/missions/demo.json` (a fresh build / run from the
   repo root), next to the executable, `../share/fossynd/missions/`,
   `/usr/local/share/fossynd/missions/`, then `/usr/share/fossynd/missions/`.
5. **The copy embedded in the binary** (built from `demo.json` at configure
   time), so the game always starts even with no data files present.

The config file itself is found from `--config <path>`, else the first existing
of `./fossynd.conf`, `<exe-dir>/fossynd.conf`, `/etc/fossynd.conf`,
`/usr/local/etc/fossynd.conf`. See `assets/data/fossynd.conf.example`.

An explicit path (steps 1–3) that does not exist is a startup error, because the
user asked for it specifically. Nothing found (step 5) is not an error.

The resolution logic lives in `core/data/Config.{h,cpp}` and
`core/data/ContentPaths.{h,cpp}` (SDL-free, unit-tested).

## Validating content

`core/data/ContentValidation.h` (header-only, engine-free, no new dependency)
resolves every mission's `weaponId`/`agentId` references against the shared
catalogues and reports readable problems, so bad content is caught in CI instead
of at play time:

```cpp
#include "core/data/ContentValidation.h"

const fossynd::core::content::ValidationReport report =
    fossynd::core::content::validateContentDir("assets/data");
if (!report.ok())
{
    std::fputs(fossynd::core::content::formatReport(report).c_str(), stderr);
}
```

- `validateContentDir(dataDir)` loads `weapons.json`/`agents.json` from `dataDir`
  (missing files are fine) and checks every `*.json` in `dataDir/missions/`.
- It collects **all** problems rather than stopping at the first, and each line
  names the file: `content: assets/data/missions/demo.json: unknown weaponId ...`.
- It reports a missing `weaponId`/`agentId`, a duplicate catalogue `id`, a
  malformed mission, and a missing catalogue directory.
- A `dataDir` with **no** catalogue files is reported, because then no mission
  reference could ever resolve — a likely misconfiguration.
- The shipped content is covered by `tests/test_content_validation.cpp`
  (`ContentValidation.ShippedContentPasses`), so a broken mission or catalogue
  fails CI.

## Adding content

To add a mission, drop a new `assets/data/missions/<name>.json` file. Two agents
can add missions in parallel without touching the same C++ file (AGENTS.md §4.7,
"data over code"). Point the game at it with `--mission` or a config file.

To add a weapon or a reusable agent template, append an entry to
`assets/data/weapons.json` or `assets/data/agents.json` and reference it by
`weaponId` / `agentId`. Two agents can add catalogue entries in parallel too:
each entry is one array element, so edits rarely collide.
