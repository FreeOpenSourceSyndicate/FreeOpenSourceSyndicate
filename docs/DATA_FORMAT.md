# Gameplay data format (ADR-0003)

Content lives in `assets/data/` as **JSON**, parsed by the small, dependency-free
reader in `src/core/data/` (`Json.h`, `Json.cpp`, `MissionData.h`,
`MissionData.cpp`). This document is the schema reference.

The parser is **not** a general JSON implementation. It supports the subset our
content needs — objects, arrays, strings, numbers, booleans, `null` — and rejects
anything else with a readable error. To keep files valid JSON and diffable,
**comments and trailing commas are not allowed.**

## Why JSON, hand-rolled (ADR-0003)

- Ubiquitous and easy for LLM agents to generate and review; human-diffable.
- No third-party dependency, so the low-spec binary stays small (AGENTS.md §1b).
- The loader lives in `core`, so it is unit-tested headlessly and stays SDL-free
  (ADR-0002). The engine layer only decides *where* the file is.

## Mission schema

A mission file describes one mission. Example:
`assets/data/missions/demo.json`.

```jsonc
{
  "name": "Downtown Sweep",   // optional, defaults to "Mission"
  "id": "demo",                // optional: stable key for localised mission text
  "width": 24,                 // required, > 0
  "height": 24,                // required, > 0

  "buildings": [               // optional
    { "x": 5, "y": 5, "width": 4, "height": 4 }
  ],

  "blocked": [                 // optional: individual blocked tiles
    { "x": 12, "y": 10 }
  ],

  "objective": {               // optional; defaults to eliminate-all
    "kind": "eliminate"        // "eliminate" | "reach" | "survive"
    // "kind": "reach", "tileX": 20, "tileY": 20
    // "kind": "survive", "seconds": 60
    // "kind": "escort", "agentIndex": 3, "tileX": 20, "tileY": 20
    // "kind": "destroy", "tileX": 12, "tileY": 13
    // "kind": "persuade", "targetCount": 3
  },

  "agents": [                  // required, non-empty
    {
      "agentId": "trooper",    // optional: inherit a template from agents.json
      "name": "ALPHA",         // optional, defaults to "AGENT" (or the template's)
      "team": "player",        // "player" | "enemy" | "civilian"
      "x": 1.5, "y": 1.5,      // required, tile coordinates (fractional)
      "speed": 3.0,            // optional, tiles/second, > 0
      "health": 100,           // optional, > 0
      "weapon": {              // optional; defaults to the pistol
        "name": "Rifle",
        "damage": 8,
        "range": 9,
        "fireRate": 4,         // shots/second, > 0
        "accuracy": 0.65,      // [0, 1]
        "areaRadius": 0        // optional, tiles; > 0 = explosive (AoE)
      },
      "weaponId": "rifle"      // optional: reference weapons.json by id
    }
  ],

  "vehicles": [                // optional: hijackable cars/trains placed on the map
    { "vehicleId": "car", "x": 3.5, "y": 4.5 },   // inherit a vehicles.json template
    { "kind": "train", "x": 5.5, "y": 2.5,        // or inline a vehicle
      "speed": 9.0, "health": 400, "weaponId": "rifle" }
  ]
}
```

### Field notes

- **`id`** is optional. It is a stable, language-independent identifier for the
  mission, used to key localised mission text: a mission with `"id": "demo"`
  looks up `mission.demo.name` / `mission.demo.desc` in the string table (see
  `core/i18n/MissionText.h`). Omit it and the mission falls back to an id derived
  from its file name, so `id` is only needed when you want the key to survive a
  rename. A present-but-non-string `id` is a readable error.
- **`buildings`** are rectangular footprints; **only the perimeter blocks
  movement**, so the interior stays walkable. `width`/`height` are in tiles and
  must be positive. The whole rectangle must lie inside the map.
- **`blocked`** marks single tiles as impassable (in addition to buildings). Each
  tile must be inside the map. A tile may also set `"destructible": true` (an
  optional boolean, default `false`) to make it a cracked wall: weapon fire that
  lands on it chips its hit points and, at zero, opens it (the tile becomes
  walkable and is remembered as rubble). An explosive weapon's blast — and a
  vehicle wreck's detonation — breach every destructible tile within the blast
  radius, not just the tile a shot lands on. A solid (non-destructible) wall is
  never breached.
- **Geometry must fit the map** (issue #212). A building, a `blocked` tile, an
  agent position, or a `reach` objective tile that falls outside
  `[0, width) × [0, height)` is a readable error rather than being silently
  dropped or left unreachable. Positions are checked with `< width`/`< height`,
  so a fractional position on the far edge (e.g. `8.0` on an 8-wide map) is
  rejected. This keeps an unwinnable mission (`--check-content` failing) out of
  CI instead of letting it fail at play time.
- **`objective`** is the mission's win condition; omit it for the default.
  - `"eliminate"` — win when every enemy agent is dead (the default, so existing
    missions are unchanged).
  - `"reach"` — win as soon as any living player agent stands on the tile
    `(tileX, tileY)`. Both are required and are integer tile coordinates.
  - `"survive"` — win after `seconds` (a number, `> 0`) of mission time have
    elapsed.
  - `"escort"` — win when the agent at `agentIndex` (an integer index into the
    `agents` array, `>= 0`) reaches the tile `(tileX, tileY)` **alive**. Unlike
    `"reach"` it names one unit: the mission is lost if that unit dies, even while
    the rest of the squad lives. The index must name an agent in the mission, and
    the tile must be on the map.
  - `"destroy"` — win when the tile `(tileX, tileY)` has been **breached**, i.e.
    it is a `destructible` blocked tile that weapon fire has broken (see
    `blocked`). The mission is not won by killing the defenders. The tile must be
    on the map (it is not checked for being destructible, since the breach can
    only ever happen on one).
  - `"persuade"` — win when at least `targetCount` (an integer, `>= 1`)
    civilians have been recruited as followers of the player's agents (the
    ComplianceBeacon). Counts living followers across the whole squad.
  - The lose condition is universal and unchanged: every player agent dead (and,
    for `"escort"`, the escorted unit dying). Civilians never affect win/lose.
    `Mission::elapsedSeconds()` reports the mission clock (frozen once the
    mission ends).
- **`team`** must be `player`, `enemy`, or `civilian`. Civilians are never
  auto-targeted and never affect win/lose (see `AGENTS.md` §10).
- **Agent coordinates** are fractional tile positions, matching `Agent(x, y, …)`;
  `1.5, 1.5` is the centre of tile `(1, 1)`.
- **`weapon`** is optional per agent. Omitted fields fall back to the pistol's
  values. Every numeric field is range-checked when the content loads (issue
  #190), so a bad number fails the load rather than misbehaving at play time:
  `damage` > 0, `range` > 0, `fireRate` > 0, `accuracy` in `[0, 1]`, and
  `areaRadius` ≥ 0.
- **`areaRadius`** is optional and defaults to `0` (a single-target weapon, the
  old behaviour). When greater than `0`, a successful hit also damages every
  other living agent within that many tiles of the impact — an explosive. The
  primary target is damaged once; in-radius civilians can be killed by the blast
  (counted in `civilianKills`).
- **`weaponId`** references a weapon in the shared catalogue by id (see below).
  An agent may set either `weapon` (inline) **or** `weaponId`, not both; an
  unknown id is a readable error.
- **`agentId`** references an agent template in the shared catalogue. The
  template supplies `name`, `team`, `speed`, `health`, and the weapon; any field
  the mission also sets inline overrides the template. `x`/`y` always come from
  the mission (a template has no position). An unknown id is a readable error.
- **`vehicles`** is optional and places hijackable cars/trains. Each entry needs
  a numeric `x`/`y` **inside the map** (like an agent, §"Geometry must fit the
  map"); an off-map or missing position is a readable error. A vehicle may:
  - **`vehicleId`** reference a template in the shared vehicle catalogue
    (`vehicles.json`), inheriting its `name`, `kind`, `speed`, `health`, and
    mounted weapon; any field the mission also sets inline overrides it, or
  - **inline** its own fields: `kind` is `"car"` or `"train"` (an unknown kind is
    a readable error), `speed`/`health` must be positive (defaults: car 6/150,
    train 9/400), and `weapon`/`weaponId` set the mounted weapon exactly as they
    do for an agent. `x`/`y` always come from the mission. Omitting `vehicles`
    entirely leaves a mission vehicle-free, exactly as before (golden rule 7).
- Unknown keys are ignored, so the format can grow without breaking older files.

## Shared catalogues (`weapons.json`, `agents.json`, `vehicles.json`)

Weapons, agent templates, and vehicle templates that several missions share live
in catalogue files at the **content root** (`assets/data/`), so they can be
edited once and referenced by id instead of copied into every mission
(ADR-0003):

```jsonc
// assets/data/weapons.json
{
  "weapons": [
    { "id": "pistol", "name": "Pistol", "damage": 10, "range": 6, "fireRate": 2.5, "accuracy": 0.72 },
    { "id": "rifle",  "name": "Rifle",  "damage": 8,  "range": 9, "fireRate": 4,   "accuracy": 0.65 },
    { "id": "launcher", "name": "Launcher", "damage": 45, "range": 10, "fireRate": 0.8,
      "accuracy": 0.85, "areaRadius": 2.0 },
    { "id": "minigun", "name": "Minigun", "damage": 4, "range": 6, "fireRate": 16, "accuracy": 0.5 },
    { "id": "flamethrower", "name": "Flamethrower", "damage": 7, "range": 4, "fireRate": 8, "accuracy": 0.6 },
    { "id": "laser", "name": "Laser", "damage": 22, "range": 12, "fireRate": 1, "accuracy": 0.9 },
    { "id": "shotgun", "name": "Shotgun", "damage": 18, "range": 3.5, "fireRate": 1, "accuracy": 0.65 },
    { "id": "sniper", "name": "Sniper", "damage": 35, "range": 15, "fireRate": 0.5, "accuracy": 0.95 },
    { "id": "gauss", "name": "Gauss", "damage": 7, "range": 11, "fireRate": 5, "accuracy": 0.8 },
    { "id": "time-bomb", "name": "Time Bomb", "damage": 75, "range": 5, "fireRate": 0.4,
      "accuracy": 0.9, "areaRadius": 3.0 }
  ]
}
```

```jsonc
// assets/data/agents.json
{
  "agents": [
    { "id": "guard",  "name": "GUARD",  "team": "enemy", "speed": 3, "health": 70, "weaponId": "rifle" },
    { "id": "gunner", "name": "GUNNER", "team": "enemy", "speed": 2.5, "health": 90, "weaponId": "launcher" },
    { "id": "police", "name": "POLICE", "team": "enemy", "speed": 3.1, "health": 75, "weaponId": "uzi" }
  ]
}
```

```jsonc
// assets/data/vehicles.json
{
  "vehicles": [
    { "id": "car",   "name": "Car",   "kind": "car",   "speed": 6, "health": 150, "weaponId": "uzi" },
    { "id": "train", "name": "Train", "kind": "train", "speed": 9, "health": 400, "weaponId": "rifle" }
  ]
}
```

- Each entry needs a non-empty **`id`**, unique within its file; a duplicate or
  missing id is a readable error.
- A weapon entry takes the same fields as an inline `weapon` object (plus `id`),
  including an optional **`fuseSeconds`** (`>= 0`, default `0` = immediate). A
  weapon with `fuseSeconds > 0` **arms** on impact and **detonates** after the
  fuse through the normal area-damage path (shields still cover it, walls breach,
  civilian collateral applies). `fuseSeconds` is parsed by `parseWeaponNode`
  (issue #461), so the `time-bomb` entry can carry a real fuse from data alone.
- **The `time-bomb` entry is a fused area weapon.** It ships as a high-damage
  blast (`areaRadius` > 0), and it may now carry a **`fuseSeconds`** delay from
  data (issue #461), so the Definition of Done's time-bomb family can be a planted
  charge that arms and then detonates — the fuse mechanic itself lives in
  **Tactical** (issue #449, `core::Mission`). Setting a fuse on the shipped entry
  (so the saboteur arms a charge rather than firing an immediate blast) is a
  **Tactical/Content** balance decision, not part of #461.
- An agent entry takes the same fields as a mission agent (`id`, `name`, `team`,
  `speed`, `health`) plus `weapon` or `weaponId`; it has no `x`/`y`.
- A vehicle entry takes the same fields as a mission vehicle (`id`, `name`,
  `kind`, `speed`, `health`) plus `weapon` or `weaponId`; it has no `x`/`y`.
  `kind` is `"car"` or `"train"`, and `speed`/`health` must be positive.
- **All catalogues are optional.** A mission that inlines everything (such as
  `demo.json`) needs no catalogues and behaves exactly as before. A missing
  catalogue file is not an error; the game still starts (AGENTS.md §1b).
- A mission loaded from disk (`MissionData::loadFromFile`) automatically loads
  the catalogues **next to it**: a mission in `assets/data/missions/` finds
  `assets/data/weapons.json`, `assets/data/agents.json`, and
  `assets/data/vehicles.json`.

## Loading

```cpp
#include "core/data/MissionData.h"

fossynd::core::MissionData data;
std::string error;
if (!fossynd::core::MissionData::loadFromFile(path, data, error))
{
    // error is human-readable, e.g. "line 12: unknown team 'droid'"
}

fossynd::core::TileGrid grid = fossynd::core::buildGrid(data);
fossynd::core::Mission mission(grid, seed);
fossynd::core::populateMission(data, mission);
```

The engine layer (`src/game/`) decides the file path and renders the result; it
contains no schema knowledge.

### Applying a squad loadout (deployment)

Milestone B's deployment (docs/METAGAME.md §7 R1, ADR-0027) can override the
mission's authored player weapons and gadgets at load time, without changing the
mission file. A `core::PlayerLoadout` names catalogue ids per slot; slot `i`
maps to the i-th **player** agent in authored order, and a slot past the last
player agent is ignored:

```cpp
#include "core/data/Catalogues.h"
#include "core/sim/PlayerLoadout.h"

fossynd::core::PlayerLoadout loadout;
loadout.slots.resize(2);
loadout.slots[0].weaponId = "rifle";        // resolved against weapons.json
loadout.slots[1].gadgetId = "medkit";       // "medkit" | "shield" | "scanner" | "drugs"
loadout.slots[0].cyberneticId = "legs";     // "legs" | "arms" | "chest" | "eyes" | "targeting-implant"

fossynd::core::WeaponCatalogue weapons;
bool found = false;
weapons.loadFromFile("assets/data/weapons.json", found, error);

// `mission` was already filled by populateMission(data, mission).
if (!fossynd::core::applyLoadout(loadout, mission, weapons, error))
{
    // error is human-readable, e.g. "loadout slot 0: unknown weaponId 'railgun'"
}
```

An empty `weaponId`/`gadgetId`/`cyberneticId` (or a missing slot) keeps the
mission's authored default, so a mission with no loadout is byte-for-byte
unchanged. An id that is not in its catalogue is a **content error**
(`applyLoadout` returns false), not a silent fallback. The gadget vocabulary is
`medkit` (one heal), `shield` (one absorbed hit), `scanner` (one timed reveal of
nearby enemies), and `drugs` (one timed speed/accuracy buff), matching the
`kind: "gadget"` items in
`assets/data/world/equipment.json`.

The cybernetic vocabulary (`CyberneticEffect`, `src/core/sim/Cybernetic.h`) maps
a `kind: "cybernetic"` catalogue id to permanent stat **multipliers** applied
once at load by `Mission::applyCybernetic`: `legs` (movement speed), `arms`
(weapon accuracy), `chest` (maximum health), `eyes` (sight range / perception),
and `targeting-implant` (accuracy). An upgrade is separate from the
weapon/gadget loadout because it is a passive, permanent change rather than a
deployable item (ADR-0031).

## Choosing which mission to load

The path is resolved at startup, highest priority first:

1. **`--mission <path>`** on the command line (an explicit file that must exist).
2. **`mission = <path>`** in the config file (an explicit file that must exist).
3. **`mission_dir = <dir>`** in the config file: `<dir>/demo.json` is used.
4. **Built-in fallbacks**, checked for existence in order — the first that
   exists wins: `assets/data/missions/demo.json` (a fresh build / run from the
   repo root), next to the executable, `../share/fossynd/missions/`,
   `/usr/local/share/fossynd/missions/`, then `/usr/share/fossynd/missions/`.
5. **The copy embedded in the binary** (built from `demo.json` at configure
   time), so the game always starts even with no data files present.

The config file itself is found from `--config <path>`, else the first existing
of `./fossynd.conf`, `<exe-dir>/fossynd.conf`, `/etc/fossynd.conf`,
`/usr/local/etc/fossynd.conf`. See `assets/data/fossynd.conf.example`.

An explicit path (steps 1–3) that does not exist is a startup error, because the
user asked for it specifically. Nothing found (step 5) is not an error.

## Choosing the UI language

The language is resolved at startup (issue #123):

1. **`--lang <code>`** on the command line (e.g. `--lang de`).
2. **`lang = <code>`** in the config file.
3. Neither set means English (`en`).

A non-English code loads `assets/lang/<code>.json` and overlays it on the English
table, so a key the locale omits keeps its English value (ADR-0016). An unknown
code is **not** an error: the game warns on stderr and keeps English. `--lang en`
and no `--lang` are equivalent.

The resolution logic lives in `core/data/Config.{h,cpp}` and the overlay in
`core/i18n/StringTable.{h,cpp}` (SDL-free, unit-tested); the engine layer
(`src/game/Game::loadLanguage`) applies it at init.

## Validating content

`core/data/ContentValidation.h` (header-only, engine-free, no new dependency)
resolves every mission's `weaponId`/`agentId`/`vehicleId` references against the
shared catalogues and reports readable problems, so bad content is caught in CI
instead of at play time:

```cpp
#include "core/data/ContentValidation.h"

const fossynd::core::content::ValidationReport report =
    fossynd::core::content::validateContentDir("assets/data");
if (!report.ok())
{
    std::fputs(fossynd::core::content::formatReport(report).c_str(), stderr);
}
```

- `validateContentDir(dataDir)` loads `weapons.json`/`agents.json`/`vehicles.json`
  from `dataDir` (missing files are fine) and checks every `*.json` in
  `dataDir/missions/`. It also cross-checks `dataDir/world/*.json` when present
  (see below).
- It collects **all** problems rather than stopping at the first, and each line
  names the file: `content: assets/data/missions/demo.json: unknown weaponId ...`.
- It reports a missing `weaponId`/`agentId`/`vehicleId`, a duplicate catalogue
  `id`, an out-of-range catalogue or inline weapon field (`damage`/`range`/
  `fireRate` ≤ 0, `accuracy` outside `[0, 1]`, negative `areaRadius`), a bad
  `team`, an unknown vehicle `kind`, off-map mission geometry (a building,
  `blocked` tile, agent, vehicle, or `reach` tile outside the grid), a malformed
  mission, and a missing catalogue directory. Each message names the file and the
  offending entry/field.
- **The metagame world data is cross-checked too** (issue #369): a
  `kind: "weapon"` item in `dataDir/world/equipment.json` must exist in
  `weapons.json`, and a `research.json` node's `unlocks` must be an
  `equipment.json` id. Without this a weapon the shop sells but the catalogue
  does not define (the pre-#369 `longshot`/`railgun`) would be bought and then
  make `applyLoadout` reject the **whole** squad loadout at deploy. The world
  files are optional, so a content dir that ships no campaign still validates.
- A `dataDir` with **no** catalogue files is reported, because then no mission
  reference could ever resolve — a likely misconfiguration.
- The shipped content is covered by `tests/test_content_validation.cpp`
  (`ContentValidation.ShippedContentPasses`), so a broken mission or catalogue
  fails CI.

## Adding content

To add a mission, drop a new `assets/data/missions/<name>.json` file. Two agents
can add missions in parallel without touching the same C++ file (AGENTS.md §4.7,
"data over code"). Point the game at it with `--mission` or a config file.

To add a weapon, a reusable agent template, or a vehicle, append an entry to
`assets/data/weapons.json`, `assets/data/agents.json`, or
`assets/data/vehicles.json` and reference it by `weaponId` / `agentId` /
`vehicleId`. Two agents can add catalogue entries in parallel too: each entry is
one array element, so edits rarely collide.
