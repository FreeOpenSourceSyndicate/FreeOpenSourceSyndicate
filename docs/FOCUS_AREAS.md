# Focus Areas & Parallel Ownership

`AGENTS.md` is the rulebook and `docs/COORDINATION.md` is the playbook. **This
file is the assignment sheet**: it splits the repository into nine **focus
areas** and defines exactly which files each area owns, how an agent picks an
area each cycle, and what happens when two areas meet.

Read this together with `AGENTS.md` §3 (protocol) and `docs/COORDINATION.md`
(claims, labels, review). Where this file and `AGENTS.md` disagree, `AGENTS.md`
wins — then fix this file in the same PR.

> **Restored to eight focus areas (now nine), self-coordinating.** An earlier revision
> merged these into four lanes when agents could not stay connected; that was
> reverted because multi-agent work was unstable at that granularity. A later
> revision routed coordination through a single **coordinator** role; that is
> **removed** (ADR-0019) because an agent may abort mid-cycle and a fleet that
> depends on one role stalls when that agent dies. Coordination is now **flat**:
> the area boundaries below *are* the coordination mechanism, and every rule is
> self-service.
>
> **A ninth area, `focus: metagame`, was added for the campaign layer** (ADR-0022,
> Milestone B). The metagame is the largest missing block on the critical path —
> world map, economy, research, purchase, campaign — and it had no area to claim,
> so an agent could not start it. It owns a new `src/core/economy/**` tree and the
> map/management screen. The name deliberately avoids `content`, `world`, and
> `render`, which already own other meanings of those words.

## 1. Coordination is flat (no coordinator)

There is **no coordinator role** and no `focus: coordinator` label. Every agent
is an equal peer; no agent has authority over another's focus. The rules that a
coordinator used to apply are now **mechanical and area-local**, so any agent can
apply them without permission (ADR-0019).

**Why.** Agents abort mid-cycle. If a single role owns the merge queue, overlap
arbitration, and the workload plan, its death stalls the fleet. Under the flat
scheme an aborted agent strands **at most its own claim**, which a timeout
reclaims; nobody was ever waiting on it.

**How coordination happens without a coordinator.**

| What used to need the coordinator | What happens now |
|-----------------------------------|------------------|
| Assigning work / reassigning foci | Agents **self-claim** a free area with the highest workload (`scripts/coord claim`, §7); the claim is a **lease** with a TTL (§5.3, ADR-0021). |
| Merging the queue | **Peer review/merge** (`AGENTS.md` §3a): any agent reviews and merges any PR it did not author; an orphaned PR is adopted by whoever is free. |
| Arbitrating overlaps | The fixed **priority order in §4** decides; ties go to **merged code** (whoever landed first wins), never to an authority. |
| Owning the process docs | **Shared maintainers**: any agent may PR a change to the rules, needing **two peer reviews** (§6) and never colliding with an active claim. |
| Keeping the workload plan current | The board is **generated** from the ledger (`scripts/coord board`, §8); there is no plan to keep current. |
| Answering process questions | The rules are written down here and in `AGENTS.md`; read them. Genuine **human** questions go straight to the maintainer (§5.2). |

**What is still not allowed.** An agent must not start work in another area's
files on its own — it **requests** it from that area's owner (§5). This is the
one place the flat scheme keeps a boundary, and it is exactly what keeps two
agents from colliding on one file.

### 1.1 Coordination state is the lease ledger

There is no hub issue and no bulletin board to check in on. The coordination
state is the **lease ledger** — the git refs under `refs/coord/leases/*` — and
its generated view, `docs/COORDINATION_BOARD.md`. Use it to **see**, not to ask:

- **Start:** `scripts/coord claim` (the claim *is* your check-in; it is visible to
  everyone the instant it is pushed).
- **Idle:** read `scripts/coord status`; if an area is free and has work, claim
  it. Reviewing/merging PRs needs no assignment (§5).
- **End:** `scripts/coord release`.
- **Blocked / overlap dispute:** `scripts/coord renew --state blocked --note "..."`,
  then post the files and areas on the issue thread.

No one has to read the ledger before acting, and no comment is required to start,
merge, or take over work.

## 3. How an area works

   branch, implement, PR.
2. **Stay in your lane.** Only edit files your area owns. Need a change in

3. **One task = one branch = one PR** (`AGENTS.md` §3). Branch prefixes by area:

## 4. Overlap rules

The whole point of focus areas is that most work never touches the same file.
Where areas unavoidably share a file, these rules apply. They are ordered:
**rule 1 wins over rule 2, and so on.**

### Rule 1 — One file, one owner

A file has exactly one owning area (§2). An agent from another area **never
edits an owned file directly**. It files a request instead (Rule 4).

### Rule 2 — Shared files: serialise, never co-edit

Two files are genuinely shared and are the main collision risk:

- **`src/game/Game.cpp`** — owned by **Render** (it is mostly drawing), but
  **Input/UI** legitimately needs to change `handleEvents`, selection, and the
  title-card start path in the same file.
- **`tests/test_mission.cpp`** — owned by **Tactical**, but World and Content add
  assertions to it.

For these, use **turn-taking**, not parallel edits:

1. The current holder opens a small PR touching only their concern.
2. It is merged before the other area opens its PR touching the same file.
3. Do **not** open two concurrent PRs that both modify `Game.cpp` (or
   `test_mission.cpp`). If that happens, the **later** PR waits and rebases onto
   the first once it merges. Which is "first" is decided by merge order, not by
   any agent's authority.
4. A PR that must touch the shared file says so in its description and names the
   other area, so the other agent can see the collision on the PR itself.

Where practical, **split the file instead of sharing it**: new engine features go
into new files (`src/game/Hud.cpp`, `src/game/Camera.cpp`, `src/game/Input.cpp`,
`src/game/TitleCard.cpp`) so Render and Input/UI stop sharing `Game.cpp`.
Splitting is the preferred long-term fix and a good task for whichever area gets
there first — but it is one PR, serialised by the rules above, not a race.

### Rule 2a — One task, one PR: no duplicate work

An issue has **one** claimant at a time (`AGENTS.md` §3.2). Before you start:

1. Run `scripts/coord status` and read the ledger. If the issue's area has a
   **live** lease (§5.3), do **not** claim it — pick a free area.
2. If the lease is **expired** (past its TTL), the area is free: claim it
   normally (`scripts/coord claim`). No announcement is needed — the clock
   already freed it. To take a **live but stale** lease, use
   `scripts/coord claim ... --takeover` (printed, never silent).
3. If two agents nevertheless open PRs for the same issue, the **first merged PR
   wins**. The later one does not get merged; its author **rebases onto the
   winner** and keeps only the parts the winner is still missing (usually the
   wiring, docs, or tests), then opens a small follow-up PR.

**A merged PR that adds a capability but never wires it in is not done.** If your
area lands a new core function, land its caller (or a clear follow-up issue) in
the same PR; otherwise another area may "fix" it in a way that fights yours. The
#99/#100 pair is the worked example: #99 added string-pulling to `findPath` but
left `Agent::moveTo` on the 4-way default, so the feature was inert until #101
passed `allowDiagonal=true`.

### Rule 3 — Core headers are a contract; the owning area freezes them

`core::Agent`, `core::Mission`, `core::Weapon`, `core::TileGrid`, the data
structs, and the config structs are interfaces many areas build against. Adding
a field or method is how areas communicate. To avoid churn:

1. An area that needs a new member **requests it from the owning area** (§2.1).
2. The owning area lands a **contract PR** that adds only the header/signature, a
   stub if needed, and a test — small and fast.
3. Everyone else then builds against the frozen signature.

Never land a behaviour change and an interface change in the same PR unless the
interface change is trivial and local to your own area.

### Rule 4 — Cross-area requests (the hand-off)

When area A needs work in area B's files, A posts a **request** — a GitHub issue
(or comment) that contains:

```
Requested by: <area A> (agent <model>)
Needed in: <area B> — <files>
What & why: <one paragraph>
Interface: <exact signature(s) wanted, or "no interface change">
Blocks: <issue/PR that is waiting>
Deadline/urgency: <e.g. "blocks my PR #123">
```

B's owner either implements it, delegates it to a helper (§5), or pushes back
with a reason and a counter-proposal. If B's owner is gone (aborted), the request
itself is the takeover signal: the first agent to notice may take the requested
work under the normal lease rules (§5.3) — if the area's lease has expired it is
already free; if it is live but stale, claim it with `--takeover`.

### Rule 5 — Cross-cutting changes are serialised globally

A few changes affect every area and must never be in flight twice. These are
serialised by **ownership + the two-review rule**, not by a coordinator:

- `AGENTS.md`, `docs/COORDINATION.md`, `docs/FOCUS_AREAS.md`, `docs/DECISIONS.md`,
  `docs/ROADMAP.md` (the rules and the plan) — **shared maintainers**: any agent
  may PR a change, but it needs **two peer reviews** (or, under the sole-account
  rule, an explicit self-review against the §6 checklist) and must not collide
  with an active claim.
- A new top-level dependency or build option — **Platform**, announced before it
  lands so other areas can rebase.
- A rename or format change to shared data (JSON schema, config keys) — requires
  an ADR (`AGENTS.md` §3.5) and a deprecation window; **Content** owns it.
- A change to `core::Vec2`/`TilePos` or the namespace — **World**, requires an
  ADR, announced.

### Rule 6 — Ownership ties are decided by the rules, then by merged code

If two areas both believe they own a file, the **§2 file map decides** — it is the
single source of truth, so check it before claiming. If the map is genuinely
ambiguous, or two areas both need the file now, resolve it in this order, with no
authority involved:

1. **The area named in §2 owns it.** The other area files a request (Rule 4).
2. **For a shared file (Rule 2), merge order decides.** Whoever's PR merges first
   is the holder; the other rebases. This is automatic — no one adjudicates.
3. **If the rules truly cannot decide** (a new file no area lists, or a real
   disagreement about the map), the agents involved **write a one-paragraph ADR
   in `docs/DECISIONS.md`** (options + recommendation) and the **first merged**
   proposal wins. A rules change is itself just a PR (§6), so it does not need a
   coordinator to bless it.

### Rule 6a — A new file follows the area that owns its directory

Most new files are obvious: they sit in one area's directory (§2) and belong to
that area. The one case that has caused friction is a **feature area adding a new
engine-free module inside another area's directory** — Render added
`core/data/AgentSprites.*` (the agent-sprite bake, #39) and `core/data/TileSprites.*`
(the ground-tile bake, #189). The rules decide it, so nobody has to negotiate:

1. **The directory's area owns the file**, and its PR is reviewed normally (§3a).
   The adding area states in the PR description what it added, why, and why it
   cannot live in its own directory.
2. **The forced exception is core purity.** Baking, parsing, and other logic that
   must be SDL-free belongs in `src/core/` even when the *feature* is visual
   (golden rule 1). Placement there is required by the architecture, not a claim
   on the owning area's lane — so it is **not** an overlap to arbitrate.
3. **Keep the addition self-contained** so it does not collide with the owning
   area's files: a new `.h`/`.cpp` pair, one line in the directory's
   `CMakeLists.txt`, and its **own** test file registered in
   `tests/CMakeLists.txt`. That is how #39 and #189 landed with no merge conflict
   and no shared-file turn-taking (Rule 2).
4. **New test files belong to the adding area** (e.g. `tests/test_tilesprites.cpp`),
   even though they live among the owning area's tests; the owning area still
   reviews the PR. Do not add assertions to the owning area's test file for this —
   that is a Rule 2 shared file.

## 5. Helpers, leases, and questions

### 5.1 Helpers

An agent whose own queue is empty **must not start work on its own initiative in
another area**. It helps only on request:

1. **Look at the ledger, not an announcement venue.** There is no "available to
   help" comment and no hub thread to post it in (ADR-0021: the lease is the
   check-in). Run `scripts/coord status`; the area states *are* the availability
   signal. If a free area has pending work, prefer taking it yourself (§7).
2. **Ask the owner.** If a **live** area needs a helper, the agent holding its
   claim posts the task it wants done, with files, interface, and acceptance
   criteria. A live owner may also request help in a PR or issue thread it owns.
3. **Get assigned — by the owner, or by the lease.** The area's owner assigns the
   task. If there is **no live owner** (the area is free, or its lease has
   expired, §5.3), the helper takes the task itself with `scripts/coord claim` —
   no one's permission is needed.
4. **Respect ownership.** A helper edits the owner's files only for the assigned
   task, and the owner reviews the PR (`AGENTS.md` §3a).
5. **Hand back.** Report in the hand-off format and return to your own queue.

There is deliberately **no announcement venue** — not on the generated board
(`docs/COORDINATION_BOARD.md`, a read-only view) and not on a hub issue. Posting
"available to help" somewhere no agent is obliged to read is friction, not
coordination; the ledger is the single source of truth.

### 5.2 Questions — answered by the rules or the human, never relayed

- A question about **scope, ordering, ownership, or process** is answered by
  **this file and `AGENTS.md`**. Read them first; the rules are written to be
  applied without a coordinator.
- If the rules are genuinely unclear, the asking agent **proposes the answer** in
  an ADR or a rules PR (§6) and proceeds on the reversible path — the proposal is
  self-service, not a request for permission.
- A **human** decision (product direction, licensing, a rule change, release
  policy) is posted **by the asking agent directly to the human maintainer**, on
  the issue thread, tagged `question` + `status: blocked`, with options and a
  recommendation. **Do not route it through anyone, and do not wait silently.**

### 5.3 Claims and leases — how abandonment is handled

A claim is a **git-ref lease**, not a comment (ADR-0021). The mechanics live in
`scripts/coord`; the full protocol is `docs/COORDINATION.md`. In one place:

- **To claim**, run:
  `scripts/coord claim --area <area> --issue <n> --agent "<model>" --branch <branch>`
  This writes `refs/coord/leases/<area>` on the remote via an atomic
  `git push --force-with-lease`. If the area has a **live** lease, the claim fails
  and names the holder; pick another free area.
- **While working**, extend the lease: `scripts/coord renew --area <a> --issue <n>
  --agent "<model>"` (optionally `--state blocked|needs-review --note "..."`).
- **The TTL is the lease.** Default **6 h**, capped at **24 h**. A lease past its
  expiry is **dead** and the area is claimable by anyone — no announcement needed,
  because the ledger says so. A lease live but quiet for **> 12 h** shows as
  **stale** on the board: `scripts/coord claim ... --takeover` is fair game and is
  printed, never silent.
- **To release**, run `scripts/coord release --area <a> --issue <n> --agent "<m>"`
  — do this as soon as the PR merges, or when you abandon the task. A lease you
  forget to release is reclaimed by the TTL, so the fleet never waits.

This is the whole replacement for "the coordinator reassigns work": the clock
does it, and the fleet never waits on a missing agent. `scripts/coord status` and
`docs/COORDINATION_BOARD.md` are the authoritative views; do **not** infer a live
claim from comment timestamps.

The legacy `CLAIM:` / `LEASE:` / `TAKEOVER:` comment lines are **read** by
`scripts/coord migrate` for the transition (`docs/COORDINATION_MIGRATION.md`) but
are no longer the mechanism of record.

### What an idle agent may do without being asked

- **Review** open PRs from other areas (never a file edit; `AGENTS.md` §3a
  explicitly asks for it).
- **Adopt an orphaned PR** (one whose author has gone quiet — on the board its
  area shows as **stale**): review it, ask for any missing tests, and merge it
  under §3a. This is the peer replacement for a coordinator draining the queue.
- **Triage** issues: add the missing `focus:` label, split a too-large issue, or
  write acceptance criteria. (`status:` labels are mirrored from the ledger by the
  sweep — do not hand-manage them.)
- **Write tests** for behaviour that already exists and is owned by no one
  *inside your own area's test file* — never in another area's test file.

### What an idle agent may never do

- Start a feature in another area's files.
- Edit another area's owned file "while passing through".
- Move or re-tag a published release (`AGENTS.md` §6b).

## 7. Picking a focus and planning the workload

**The fleet size varies** — there may be ten active agents, or only one. The
scheme must work either way, so focus choice is driven by the **ledger**, not by
a hand-kept plan.

### 7.1 How an agent picks a focus each cycle

1. **Read the ledger.** `scripts/coord status` lists every live lease and the
   **free areas** (`docs/COORDINATION_BOARD.md` is the same view, generated).
2. **Pick a free area with pending work.** "Free" means **no live lease** in it
   (§5.3). Prefer an area on the **v1.0.0 critical path** (§2, ADR-0024) — the
   tactical finish and the metagame — over lower-priority capacity; then prefer
   the area with the most open issues, to spread agents out.
3. **Prefer known areas to reduce scope.** Given a choice, prefer an area you have
   worked before — familiar files mean smaller, safer changes.
4. **Claim it.** `scripts/coord claim --area <area> --issue <n> --agent "<model>"
   --branch <branch>`. If it turns out to be taken, the claim fails and names the
   holder; go to step 2.
5. **Do not start a second agent in an area someone already holds.** If every
   busy area is taken, take the next free one, or review/merge a PR (§5).

With one active agent, it simply takes any free area. With ten, they fan out
across the nine areas. Nothing assigns these picks; each agent reads the ledger
and claims.

### 7.2 Keeping the plan useful

There is no hand-kept plan any more (ADR-0021). The **board is generated** from
the ledger, and **pending workload is the open-issue count**, which GitHub already
tracks. Concretely:

- **Do not** edit `docs/COORDINATION_BOARD.md` by hand; the scheduled sweep
  rewrites it.
- **Do not** open a "refresh the queue" PR. That class of PR is gone: the git
  history had 22 of them, each changing one table. Seeding a task now means
  **opening an issue** with the right `focus:` label.
- Keep at least one claimable issue per area so a free area is never empty of
  work; if you notice an area with none, open one from the roadmap.

---

## 8. The live queue

The live queue is the **lease ledger** plus the open issues — not a Markdown
table. To read it:

```bash
scripts/coord status                 # live leases + free areas
scripts/coord board --stdout         # the generated board
gh issue list --label "focus: world" # the open tasks in one area
```

`docs/COORDINATION_BOARD.md` is the checked-in, generated view; it is refreshed
automatically and is never edited by hand.
