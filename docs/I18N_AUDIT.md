# I18n audit — user-facing strings that bypass the table (issue #191)

The question: does any user-facing text in the engine layer skip `tr()` and the
string table (`assets/lang/*.json`), so it would stay English in a localised
run? This records the audit and the guard that keeps the answer "no".

## Method

Scanned the whole of `src/` (`.cpp`, `.h`, `.in`) for **key-shaped string
literals** (`segment(.segment)+`) and for every literal passed to a draw call:

```bash
# literals drawn without tr()
grep -rn 'draw(renderer_[^;]*"' src/game/*.cpp
# all-caps literals (candidate UI chrome)
grep -rnoE '"[A-Z][A-Z0-9 :.,/()+-]{2,}"' src/game/*.cpp src/game/*.h
```

## Known gap: data-driven names are not key-shaped literals

The scan above only sees **literals in `src/`**. Two HUD values come from
**authored data** instead, so no literal exists for rule 1 to find: the squad row
substitutes `agent.name()` (callsign, e.g. `ALPHA`) and `agent.weapon().name`
(e.g. `Rifle`) straight from `assets/data/missions/*.json` /
`assets/data/{agents,weapons}.json` (`src/game/Hud.cpp:166-169`). Mission
**names** are localised by a derived key (`mission.<id>.name`), but these have no
key scheme, so a localised run shows them verbatim in English.

This is **not** a bypass of the table in the sense this audit looks for — it is a
deliberate "proper nouns" treatment that has never been written down. Whether to
localise them (mirror `mission.<id>.name` as `weapon.<id>.name`) or to keep them
as proper nouns is a product decision tracked in **#270**; `docs/FOCUS_AREAS.md`
§2 puts localisation beyond English out of v1.0.0 scope, which favours documenting
them as proper nouns. Recorded here so the "none found" result above is not read
as "every user-visible string is localised".

## The guards

A literal is easy to re-introduce. `tests/test_i18n_keys.py` (ctest
`i18n_key_coverage`) fails if:

1. any key-shaped literal in `src/` does not resolve in `assets/lang/en.json`
   (so a localised run cannot silently show an English fallback);
2. any shipped locale does not carry **exactly** the English key set — a missing
   key (which would show English) or an invented key (a typo rendered raw), and
   a duplicate key (a copy-paste that shadows an earlier entry);
3. any `tr(key, "literal")` fallback differs from `en.json[key]` — the fallback
   is the no-localisation copy, so a table edit (e.g. #210 adding `SPACE  PAUSE`)
   must not leave a stale one behind (#240). Adjacent C++ string literals are
   concatenated before the comparison. `ALLOWED_FALLBACK_DRIFT` exists for a
   known drift pending a fix in another area's file, and is currently **empty**
   (the #238 drift it held was fixed by #245);
4. `en.json` itself has a duplicate key — the locale rule above uses `en.json` as
   the reference, so its own duplicates were the one place the check did not
   reach (#246);
5. any shipped mission (a file in `assets/data/missions/`) lacks
   `mission.<id>.name` or `mission.<id>.desc` in `en.json` or any locale. Mission
   keys are derived **at runtime** from the file stem (`core::i18n::MissionText`),
   so they are not key-shaped literals in `src/` and rule 1 cannot see them; the
   C++ gate now derives the mission set from the same directory rather than a
   hardcoded list (#246);
6. any value in `en.json` or a locale is **empty**. This is not "untranslated":
   `StringTable::get` returns a present key's value verbatim, so `""` wins over
   the `tr()` fallback and blanks the UI element. The mission path already treats
   empty as untranslated (`localizeMissionText`), the UI path does not (#254).
7. any value in `en.json` uses a character the embedded font cannot draw. The 5x7
   bitmap font covers ASCII 32–126 only (`src/game/Font.cpp`), and
   `BitmapFont::draw` maps any other byte to a blank glyph. The English reference
   is drawn by that same font, and some of its values have no `tr()` fallback to
   hide behind — the OS window title and `mission.<id>.name` / `.desc` — so a
   non-ASCII English string (a typographic quote, an em-dash, an accent) ships an
   invisible glyph. The C++ renderability gate walked only the **locale** files,
   so the reference table was the one place this went unchecked (#288); it now
   asserts the English entries too.

It ignores file-name literals (`.json`, `.bmp`, …) and allow-lists `no.such.key`
(looked up on purpose by `Game::languageSelfTest`). The rules are mutation-checked:
renaming a key, dropping one, duplicating one, corrupting a `tr()` fallback,
adding a mission without its keys, emptying a value, or adding a non-ASCII
character to an English value each makes the guard fail.
The C++ parity gate
in `tests/test_i18n.cpp`
(`ShippedLocalesMatchTheEnglishKeySet`) covers the same key-set rule for the
in-engine loader, so the two guards agree.

## Adding a string

Add the key to `assets/lang/en.json` **and** every shipped locale (both guards
require an exact key match), keep it ASCII 32–126 (`docs/LORE.md` §4), and
reference it with `tr("key", "FALLBACK")`.
