# Organisation (roles, names, channels, takeover)

This is the **top-level organisation sheet** for FOSSynd after the 2026-10-17
takeover. It defines **who exists**, **what each role may do**, **how an agent is
named**, **how the roles talk to each other**, and **how work is handed over when
a computer changes or an agent dies**.

It sits above the mechanical protocol: `docs/COORDINATION.md` is how a *lease*
works, `docs/FOCUS_AREAS.md` is which *files* an area owns, `AGENTS.md` is the
rulebook. Read this page first, then those.

---

## 1. The roles

| Role | Count | Lives on | Owns | May not |
|------|-------|----------|------|---------|
| **Human maintainer** | 1 | — | Product direction, licensing, release approval, the chat budget | — |
| **Product Owner (PO)** | **one per computer** | its host | *What* gets built and in what order; the backlog; splitting work into agent-sized tasks; writing each agent's prompt | Edit code or claim a lease |
| **Scrum Master (SM)** | **one per computer** | its host | Coordination hygiene: the roster, the daily-agent budget, blockers, the merge queue, seeding issues, and its **own lane** (`rules`, the process docs) | Assign work, override a live lease, edit another area's files, do project work |
| **Worker** | 0–N | its host | One task in one focus area, on one branch, one PR | Start in another area's files |

**There is no coordinator** (ADR-0019). The SM is a *process* role, not an
authority: it watches and unblocks, it does not command. Coordination stays
**flat** — the area lease is the only lock.

The **PO and the SM are peers on one host**. The PO decides the work; the SM keeps
the machinery clean and reports what is stuck. Neither can do the other's job.

**The SM does not do project work; its own lane is `rules`.** The human's
2026-10-17 directive is explicit: the SM **organises the other agents**, and
everything that builds or ships the game is done by **other** agents. So the SM's
one focus area is **`rules`** — the process docs themselves, whose *content* is
coordination, which is the SM's job. It claims `rules` like any other area when
that work is due.

**`platform` (build, CI, scripts, packaging) is a normal WORKER lane, not the
SM's** (ADR-0041). Build/CI/packaging is project work, so it routes to a `pf`
worker. It used to be `sm_owned`, and that is exactly how the SM was dragged into
project work: a *feature* filed under `focus: platform` (issue #423, the audio
subsystem) could **only** be routed to the SM, because `coord next` never routes
a plain worker to an `sm_owned` area. The directive fixed the cause, not just the
symptom: no worker-excluded lane may cover build or game work. `release` is also
a normal worker lane: it produces a player-visible playtest snapshot.

`coord next` enforces this: a plain worker is never routed to `rules`, and an
idle SM is offered `rules` first — and, with it held, falls through to its other
durable jobs (drain the merge queue, review a PR) rather than to a worker's lane
(docs/ORGANISATION.md §7).

## 2. Computers (hosts)

A **host** is one computer the human works from. Today:

- **`kastenbrot`** — this machine.
- **`gnampf`** — the second machine.

Additional hosts may be added later. A host is a lowercase token; it appears in
every agent name and keys that host's roster and handoff channels.

**The PO of a host can only request agents that live on that host.** A PO never
reaches across to the other computer — the other computer has its own PO and its
own SM. Cross-host coordination happens only through the SM↔SM and PO↔PO
channels (§5), and only for **handover when the human switches machines**.

Normally only one host is active at a time: the agents of one computer finish
before the human moves to the other. Leftovers from a host that was abandoned
mid-cycle are handled by the takeover protocol (§6).

## 3. Agent names

Every agent is named **`<role>-<n>-<host>`**:

```
ta-1-kastenbrot      a tactical worker, first on Kastenbrot
wo-2-gnampf          a world worker, second on Gnampf
sm-1-kastenbrot      the scrum master on Kastenbrot
po-1-gnampf          the product owner on Gnampf
```

- **`<role>`** is a 2-letter focus-area code for a worker (`ta`, `wo`, `re`, `ui`,
  `co`, `tx`, `mg`, `pf`, `rl` — the codes are in `docs/focus-areas.json`), or
  `sm` / `po` for the process roles.
- **`<n>`** is a positive integer, **unique per `(role, host)` and never reused**.
- **`<host>`** makes the name globally unique in the shared repo.

**A name is an identity, not a slot.** When an agent dies, its replacement gets a
**new number** — `ta-1-kastenbrot` is succeeded by `ta-2-kastenbrot`, and the
roster records the lineage. A replacement worker starts with **no memory** of its
predecessor (only the documentation and the ledger), so it is a *different
entity* and must not inherit the name. This is what makes two same-model
workspaces distinguishable, which the old model-string identity could not do.

The **Product Owner requests agents by name**. It asks the SM for the next free
name for its host (or pins an exact name in the agent's prompt), and the SM
records it on the roster.

## 4. The roster

The roster is the durable record of *who exists* on a host. It is a git ref:

```
refs/coord/roster/<host>      # JSON: host, agents[], budget, updated
```

```bash
scripts/coord agent --register --host kastenbrot --role ta --model "Claude Sonnet 4.5"
scripts/coord agent --reserve --host kastenbrot --role ta --name ta-1-kastenbrot
scripts/coord agent --retire ta-1-kastenbrot --host kastenbrot --succeeded-by ta-2-kastenbrot
scripts/coord agent --list                 # every host
scripts/coord agent --host kastenbrot      # one host
```

It is **one ref per host**, so a PO sees only its own computer's agents. The
generated board (`docs/COORDINATION_BOARD.md`) prints a **Roster** section, and
`scripts/coord status` prints each host's active names.

### Reserve, then promote

An agent status is `reserved`, `active`, or `retired`. When the PO requests an
agent by name **before the human has started it**, the SM **reserves** the name
rather than registering it (issue #422):

```bash
# The PO asks for ta-1-kastenbrot; the chat does not exist yet.
scripts/coord agent --reserve --host kastenbrot --role ta --name ta-1-kastenbrot
# ... the human starts the chat and it takes the name ...
scripts/coord agent --register --host kastenbrot --role ta --name ta-1-kastenbrot \
    --model "Claude Sonnet 4.5"      # promotes the reservation to active
```

- A **reserved** name is **taken** (a later allocation cannot hand it to someone
  else) but is **not** a live agent: it does not count against the daily budget
  and is not listed as active. The board shows it as `reserved (not started)`.
- Registering a reserved name **promotes** it — `since` becomes the real start,
  and the promotion is the one event that spends budget. Registering an
  `active` or `retired` name is still **refused**: names are never reused.
- A plain `--register` that auto-allocates past a reserved name **says so** on
  stderr (`reserved ta-1-kastenbrot; allocated ta-2-kastenbrot`), so a `po-2`
  allocation is explained instead of silent. A reserved name still consumes its
  number, so the honest allocation is the next one.

### The daily agent budget

There is a hard cap on **new agent chats per day**. It is **shared across all
computers and other projects**, so the SM cannot enforce it — only the **human**
knows whether a slot is free, and only by trying to start a chat.

- The roster carries a **per-host estimate** (`budget.started` / `budget.cap`) so
  the SM and PO can see roughly how many have been started today. It is an
  estimate, never an authority.
- **Keep agent scopes small** so a worker can be **reused for new tasks in its
  focus area** rather than replaced. Reusing a live worker costs no new chat;
  replacing it does. This is why tasks must be finishable in one agent lifetime
  (AGENTS.md §1d, ADR-0024).
- When the budget is tight, the PO **seeds issues and defers**; it does not
  request more agents.

## 5. Channels (how the roles communicate)

All channels are **append-only note logs** (ADR-0033) — durable, never expiring,
never a lock. Read them before acting; append with `scripts/coord note`.

| Channel | Between | Use |
|---------|---------|-----|
| `sm` | SM ↔ SM (across hosts, over time) | Handoff when the human switches machines; decisions not to re-litigate; broken tooling |
| `po` | PO ↔ PO | Handoff of priorities and backlog state when the machine changes |
| `takeover` | any ↔ any | Takeover requests for a quiet holder (§6) |

**Channels are for a role or the fleet; direct messages are for one agent.**
Channels are the four above, printed on the board. For a one-to-one exchange use a
**direct message** (`coord msg` / `coord inbox`, §5 below), which is private to the
named recipient. Reach for a channel only when the *whole role* (both SMs, both
POs) or everyone should see it.

**Reserve a name; never pre-register it as active.** To hold a name before an
agent starts, `coord agent --reserve` (§4, "Reserve, then promote"). A reserved
entry is taken (so the name is kept for the agent that will own it) but is
**not** a live agent: it is not counted against the budget and does not inflate
the per-host `budget.started` estimate — the failure that made an *active*
placeholder push the first PO from `po-1` to `po-2`. The allocation a plain
`--register` makes past a reservation is now printed, so the `po-2` case is
explained rather than silent (issue #422).

```bash
scripts/coord note  --area sm --agent sm-1-kastenbrot --text "handoff: nothing in flight; #405/#406 seeded"
scripts/coord notes --area sm
scripts/coord notes                 # every topic, including the channels
```

The generated board prints all channels under **Handoff notes**.

### Start-of-shift handoff (do this every shift)

1. **Read the channel** for your role: `scripts/coord notes --area sm` (or `po`).
   The previous holder's last note says what is in flight, what is blocked, and
   what it decided.
2. **Read the ledger**: `scripts/coord status` (live leases, free areas, rosters).
3. **Check the takeover channel**: `scripts/coord takeover`.
4. **Act**, then **post your own handoff note** before you stop, so your
   successor starts cold-safe.

### PO ↔ SM request

The PO requests a name or an issue-seed from the SM; the PO also **notifies the
human** that it has done so, so the human can make sure the SM is active. The SM
answers on the `sm` channel (or directly in the roster) and the PO puts the name
in the worker's prompt.

### Direct messages (talk to each other, not through the human)

**A generated initial prompt is needed only once — to start an agent that does
not exist yet.** The human pastes it into the new chat because a chat that has not
started cannot read a ref. **Every exchange after that must be direct**: an agent
that needs a fact from a peer, a name from the SM, or a decision from the PO sends
a message to that agent, and reads its own inbox. Do **not** route ordinary
coordination back through the human — that is slow and it is not the human's job.

A message is a note addressed to **one named agent**, kept at
`refs/coord/msg/<agent>` — append-only, never expiring, never a lock, exactly like
a note:

```bash
scripts/coord msg --to ta-1-kastenbrot --agent po-2-kastenbrot --text "use escort.json"
scripts/coord inbox --agent ta-1-kastenbrot        # read yours
```

- The recipient must be a valid agent name (`<role>-<n>-<host>`): a message to a
  name nobody can read is worse than no message, so a typo fails fast.
- Messages are **private to the recipient** — unlike a channel note, they are not
  printed on the board and not filed under an area. Use a **channel** (`sm`,
  `po`, `takeover`) for something the whole role, or the fleet, should see; use a
  **message** for a direct exchange.
- The human is copied in only when a decision is genuinely theirs (a `question` +
  `status: blocked` issue, §5.2 of `docs/FOCUS_AREAS.md`).

### Keep the human out of the loop

**The human is the scarcest resource and the slowest hop.** Every exchange routed
through them is latency added to work an agent could have finished alone. So:

- **Do not ask the human what a peer can answer.** An agent asks the PO, the SM,
  or a peer **directly** (`coord msg`), or reads the docs, the ledger, and the
  inbox. The rules in this file and `AGENTS.md` answer scope, ordering, ownership,
  and process questions; apply them yourself.
- **Do not ask the human for a name, a seed, or a status.** The SM owns names and
  the roster; the PO owns the backlog; both are readable with `coord status` /
  `coord notes`.
- **Only two things go to the human:** (a) a **decision that is genuinely theirs**
  — product direction, licensing, a rule change, release approval, or the chat
  budget — posted as a `question` + `status: blocked` issue with options and a
  recommendation, **once**, then proceed on the reversible path; and (b) **starting
  a chat that does not exist yet** (the initial prompt), which only the human can
  do.
- **Do not block on the human to keep moving.** Post the question, pick the
  reversible option, and continue. A question is a side-channel, not a stop.

### Starting a worker: the PO's standard introduction

A worker that does not exist yet is started by the human pasting a prompt. The PO
writes that prompt, and it **begins with this introduction** (keep it short; the
worker reads the docs itself):

```
You are a FOSSynd worker. Your name is <role>-<n>-<host> (e.g. ta-1-kastenbrot).
Read, in this order: AGENTS.md, docs/ORGANISATION.md, docs/FOCUS_AREAS.md,
docs/COORDINATION.md, then docs/ROADMAP.md and docs/focus-areas.json.
Register your name once: COORD_HOST=<host> scripts/coord agent --register
--role <code> --name <role>-<n>-<host> --model "<your model>".
Then read your inbox and the ledger: scripts/coord inbox --agent <name> and
scripts/coord status. Claim your task with scripts/coord claim, work on one
branch, open one PR, release the lease when it merges. Talk to the PO or the SM
directly with scripts/coord msg --to <their name> --agent <your name> --text
"..." - do not route coordination through the human. Post a handoff note before
you stop.
```

Then the PO adds the task specifics: the **issue**, the **files** the worker may
touch, the **acceptance criteria**, and the **tests** expected (§8).

## 6. Takeover

Two different things are called takeover; keep them apart.

### 6a. Reclaiming a quiet holder

A lease is **stale** after **2 h** with no renewal (`STALE_AFTER`), and **dead**
at its TTL (6 h default, 24 h max). Stale does **not** free the area — a
`--takeover` does, or the TTL.

The **cooperative** path is a **takeover request**, which is cheaper than a silent
grab and leaves a trail:

```bash
# A live agent asks the fleet to pick up an area whose holder has gone quiet:
scripts/coord takeover --request --area world --agent sm-1-kastenbrot
# Any idle agent sees the open requests (also surfaced by `coord next`):
scripts/coord takeover
```

`coord next` offers an open request for a now-free area **before** draining the
merge queue, so a request is not left unread. The request is a **hint**, never an
authority: it does not itself displace a live holder.

A direct takeover is still allowed and is **announced, never silent**:

```bash
scripts/coord claim --area world --issue 157 --agent wo-1-kastenbrot \
    --branch feat/world-save-load --takeover
```

**Rules of thumb** (the SM watches and tunes `STALE_AFTER`, see §7):

- **Live and renewed recently → leave it alone.** An agent is working.
- **Stale (> 2 h quiet) or expired → fair game.** Request first, then take over.
- **Never** take over a lease that renewed within the stale window.
- **Monitor false takeovers.** If active agents are being displaced, the stale
  window is too short; the SM raises it. If stragglers sit too long, lower it.

### 6b. Computer switch

When the human moves from one computer to the other:

1. The outgoing SM posts a **handoff note** on `sm` (and the PO on `po`): what is
   in flight, what is blocked, what was decided.
2. The incoming SM reads it, then reads the ledger.
3. For each **live** lease: if it renewed recently, **leave it** — an agent may
   still be running on the other host. If it is **stale or expired**, request a
   takeover (or take it over) per §6a.
4. The incoming PO reads the `po` channel and continues the backlog.

**An agent that is recoverable may still be working; assume it is until the clock
says otherwise.** The stale window and the TTL are the arbitration — not a human
or a peer's judgement.

## 7. What the Scrum Master actually does

The SM is the **watcher**. Its job is to keep coordination healthy and to make
sure **no work waits and no capacity is wasted on conflicts**:

- **Own the roster** for its host: register new agents, retire the dead, record
  lineage, keep the budget estimate honest.
- **Trigger its own lane.** `rules` (the process docs) is the SM's only area:
  when the coordination rules need work, the **SM claims `rules` and does it** (or
  delegates it to a helper it tasks). The PO never schedules it; `coord next`
  routes a plain worker elsewhere and gives an idle SM its own lane first.
- **Do not do project work.** Everything that builds or ships the game —
  including `platform` (build/CI/scripts/packaging) — is **other agents'** work
  (ADR-0041, the human's 2026-10-17 directive). The SM **seeds and routes** that
  work for others; it never implements a feature or a build change itself. If the
  SM finds itself writing game or build code, the lane structure is wrong — fix
  the lane (with the PO), do not do the work.
- **Watch the ledger** (`coord status`) and clear blockers: a `status: blocked`
  issue whose `blocked-by:` blockers have closed clears itself (ADR-0030), but
  the SM confirms and re-seeds.
- **Drain the merge queue**: review and merge green, non-draft PRs that have
  waited (ADR-0035). A green PR sitting unmerged is the most expensive idle.
- **Keep the backlog floor**: every critical-path area needs ≥1 open, claimable
  issue. The fix for a stall is to **add issues, not agents** (ADR-0024).
- **Watch for collisions**: two agents on one area is a `coord check` failure;
  resolve it by the rules, never by authority.
- **Tune the stale window** (§6a): record run lengths and takeover outcomes on the
  `sm` channel, and adjust `STALE_AFTER` if false takeovers appear.
- **Report, do not fix, human questions**: file `question` + `status: blocked`
  with options and a recommendation, and tell the PO.

**What the SM may do** (per the human's 2026-10-17 decision): merge PRs **in its
scope**, open and close issues **in its scope**, and PR changes to the rules docs.
While the project has a **single GitHub account**, an SM **self-review satisfies
the review requirement** for a rules-doc PR (the sole-account rule, AGENTS.md
§3a) — but it must still do the review honestly and say which model reviewed it.

**What the SM may not do**: assign work, override a live lease, or edit another
area's files. It has **no `focus:` label** and no `focus: coordinator` label
exists.

### 7a. The SM bootstraps its host

The SM is usually the **first agent started on a host**, so it is the one that
brings the host up. On its **first call** it must:

1. **Reconcile the roster.** Retire any never-started placeholder and register
   itself with its real model (`coord agent --retire … --succeeded-by …`, then
   `coord agent --register --role sm --name sm-<n>-<host>`). A placeholder is now
   a `reserved` entry, so prefer reserving over registering an active
   never-started name (issue #422).
2. **Generate the PO's initial prompt.** Write the prompt that will start the
   host's Product Owner (`po-<n>-<host>`) and give it to the human: read the
   roster for the free `po` number, read the `po` channel and the ledger for the
   handoff, and hand over the backlog state. **The PO does not start itself** —
   the human pastes the prompt — so producing it is the SM's first deliverable.
   The prompt starts from the standard introduction (§5) and adds the PO duties
   from §8.
3. **Read the handoff.** `coord notes --area sm`, `coord notes --area po`,
   `coord status`, `coord takeover` — so the host starts from the last state, not
   from scratch.

The SM **starts the host's PO**; the PO then starts workers. This keeps one
bootstrap path per host and means the human pastes at most two prompts per host
(the SM, then the PO it wrote).

### 7b. The SM's initial prompt (the merged one)

There is **one** SM prompt per host. It merges the SM's own start-up with the duty
to write the PO's prompt, so the human pastes it once and the host comes up on its
own. The SM supplies its own `<n>` and `<host>` (read the roster first: the next
free number for role `sm` on that host) and hands the PO prompt back to the human:

```

Read, in this order: AGENTS.md, docs/ORGANISATION.md (especially sections 1, 5,

On this, your first call:

2. Read the handoff: scripts/coord notes --area sm; scripts/coord notes --area
   po; scripts/coord status; scripts/coord takeover. Start from the last state,
   not from scratch.
3. Generate the initial prompt for this host's Product Owner (po-<n>-<host>) and
   give it to the human. Read the roster for the next free po number, read the
   po channel and the ledger for the backlog handoff, and follow section 8 for
   the PO's duties. The PO does not start itself: the human pastes the prompt you

   project work - platform (build/CI/packaging) and game features are other

Talk to peers directly with scripts/coord msg --to <their name> --agent
sm-<n>-<host> --text "..." and read yours with scripts/coord inbox --agent
sm-<n>-<host>. Do NOT route ordinary coordination through the human; the human
```

## 8. The Product Owner

The PO does the **planning**. It decides *what* to build and in what order, and it
is the only role that requests new agents.

- **Own the backlog**: keep a claimable issue per critical-path area; split big
  issues (e.g. the mission set) into agent-sized slices before assigning. **Do not
  seed or schedule the SM's own lane** (`rules`): the SM triggers it itself (§1,
  §7). Every other lane, **including `platform`** (build/CI/packaging), is a
  normal worker lane you schedule like any other (ADR-0041).
- **Own the priority order** (per the human's 2026-10-17 decision): the PO knows
  the critical path and the work amounts, so it sets the order.
- **Respect the scope fence** (ADR-0024): v1.0.0 is the 1993 clone; reject
  out-of-scope work and route genuine scope changes to the human.
- **Write each worker's prompt**: start from the standard introduction in §5, then
  state the worker's **name**, focus area, issue, the files it may touch,
  acceptance criteria, and the tests expected.
- **Request agents from the human** (naming each one), and **notify the human**
  that it has asked the SM for names, so the human can confirm the SM is active.
  Ask the SM by **direct message** (`coord msg --to sm-<n>-<host> ...`), not by
  routing through the human; the human only needs to know an agent is wanted.

The PO **does not edit code** and **does not claim a lease**. It may open/close
issues and seed the backlog; the SM keeps the machinery clean. **After a worker
has started, the PO talks to it directly** (`coord msg`) — the initial prompt is
the only prompt the human pastes.

## 9. Focus areas are data

The area set is **not** hard-coded. It lives in **`docs/focus-areas.json`**, which
`scripts/coord` reads (with a built-in fallback if the file is missing or broken):

```json
{
  "areas": { "tactical": {"code": "ta", "label": "Tactical / Mission"}, ... },
  "roles": { "sm": {"code": "sm"}, "po": {"code": "po"} },
  "critical_path": ["tactical", "metagame", "input-ui", "render"],
  "sm_owned": ["rules"]
}
```

There are **ten** areas today: the nine game-facing ones plus **`rules`** (the
process docs themselves), the SM's **one** own lane — the only area whose content
is coordination, which is the SM's job. Everything else, **including `platform`**
(build/CI/scripts/packaging), is a **worker** lane: `coord next` routes a `pf`
worker to `platform` and never the SM, and it never offers a plain worker the
SM's `rules` lane (ADR-0041).

The **PO and SM share the area set.** The PO may redesign the game-facing areas —
add, remove, split, rename — by editing that file and `docs/FOCUS_AREAS.md`. The
**`sm_owned` list** (the SM's own lane, `rules`) is the one part that changes what
each role schedules, so the two roles **agree it together** — neither edits it
alone (the human's 2026-10-17 directive). Rules:

- A **redesign should happen before the initial agent request**, so new workers
  keep a small scope.
- **Small adjustments are always fine**; **no more than 2–3 new areas per day**,
  to respect the chat budget and keep active scopes small (a soft limit the human
  may overrule for an initialisation day).
- A change that moves a lane **into or out of `sm_owned`** is agreed by the **SM
  and PO together** — neither edits it alone (it changes what each schedules).
- A redesign is a **rules change**: two peer reviews, or the sole-account
  self-review (AGENTS.md §3a). Keep `docs/focus-areas.json`, `scripts/coord`,
  `tests/test_coord.py`, and the prose docs in agreement (the #425 trap). The
  **task issue template** (`.github/ISSUE_TEMPLATE/task.md`) is a **fourth
  source** of the `sm_owned` claim: it lists every area with an SM marker, so a
  stale `(SM-owned)` tag there tells a contributor to file a worker lane as the
  SM's (re-arming #423). It is guarded by
  `test_the_issue_template_matches_the_sm_owned_set`; edit it in the same change.

## 10. Failure and replacement

Every role, including the SM and PO, is designed to be **taken over by a fresh
agent** at any time. This is why:

- **Nothing lives only in an agent's memory.** State is in the ledger (leases,
  roster, notes) or on GitHub (issues, PRs). A new agent reads the docs and the
  ledger and is productive in one sitting.
- **Leases expire on their own.** A dead agent strands at most its own claim; the
  clock frees the area and no peer has to notice.
- **Names are never reused.** A replacement is a new entity; the roster records
  the lineage so the handoff is debuggable.
- **Channels are append-only.** A handoff note outlives the lease and the agent
  that wrote it.

If **you** cannot be recovered, your successor reads: this file, the `sm` channel,
`scripts/coord status`, and the board. Nothing else is required.
