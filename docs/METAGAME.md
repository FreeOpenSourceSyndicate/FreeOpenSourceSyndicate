# Milestone B — the metagame: interface contract (issue #249)

This is the **contract PR** for Milestone B (`focus: metagame`). It fixes the
public interfaces and the data schema for the metagame **before** any of it is
built, so the systems can land one small PR at a time without churning the
headers every area compiles against (`docs/FOCUS_AREAS.md` §4, Rule 3). It is the
"Interface contract" step the tracking issue (#249) asks for.

It contains **no behaviour**: the implementation PRs follow, each under the same
`focus: metagame` lease, smallest useful first. The contract exists so a reviewer
can approve the *shape* once, then each implementation PR is a small, mechanical
"make the stub real + tests" change.

## 1. Goal and scope

The metagame is the **management half** of the original: a world map of
territories, income and taxation, research & development, equipment purchase,
mission selection, and campaign progression. It is the largest missing block and
the long pole to a finished v1.0.0 (`docs/ROADMAP.md` → *The critical path*,
ADR-0024). It is now **built and playable** — the core systems are in and the map
screen drives the whole loop; see §8.

**In scope (this milestone):** the five systems below and the one map /
management screen that drives them.

**Out of scope:** anything ADR-0024 fences off (localisation beyond English, a
modding/scripting layer, modern quality-of-life, extra platforms, multiplayer).
Diplomacy, a persistent overworld AI, and a save-game format beyond a simple
in-memory campaign are **not** in v1.0.0 unless a later ADR says so (see §8).

## 2. Design principles

These follow the golden rules (`AGENTS.md` §4) and the project's existing shape:

1. **Engine-free.** All metagame logic lives in `src/core/economy/**` and must
   **not** include `SDL.h` (ADR-0002, golden rule 1). The map screen in
   `src/game/**` only reads core state and draws it.
2. **Pure and deterministic.** No global mutable state; systems are small value
   types and free functions where possible. Randomness (revolts) draws **only**
   from an injected `core::Rng` (`core/util/Rng.h`), never `<random>`/`rand()`,
   so a seed reproduces a campaign exactly (golden rules 2 and 4).
3. **Data over code.** Territories, research nodes, equipment, and campaign
   tuning live in `assets/data/world/**` as JSON, parsed by the existing
   dependency-free reader in `src/core/data/` (ADR-0003, golden rule 7, §7). No
   new JSON dependency.
4. **Testable headlessly.** Every system ships with unit tests in `tests/`
   (golden rule 6, `docs/FOCUS_AREAS.md` §2 area 7).
5. **Original names only.** Every territory, weapon, gadget, cybernetic, and
   faction name is **ours**; no name that is memorable from the 1993 original
   (`docs/LEGAL.md`, hard rule 4, and ADR-0018 as the worked example).

    std::string missionId;                // mission deployed from here; may be empty

### 4.2 `Economy` — income and revolt

```cpp
struct EconomyConfig
{
    int maxTaxLevel = 5;              // taxLevel upper bound (data-driven)
    float baseIncome = 0.0f;          // funds per owned territory per tick, at tax 0
    float incomePerTaxLevel = 100.0f; // funds per tax level per tick
    int revoltThresholdLevel = 3;     // tax at/above this can trigger a revolt
    float revoltChancePerTick = 0.02f;// probability per tick, per over-taxed territory
    float tickSeconds = 30.0f;        // in-game seconds between income ticks
};

class Economy
{
public:
    void configure(const EconomyConfig& config);
    const EconomyConfig& config() const;

    // Advances one or more income ticks. For each tick, adds income to every
    // syndicate, then rolls a revolt for each territory taxed at or above
    // `revoltThresholdLevel`. Deterministic: the only randomness is `rng`.
    void tick(float dt, WorldMap& map, Rng& rng);

    float funds(int syndicate) const;
    void addFunds(int syndicate, float amount);
    bool canAfford(int syndicate, float amount) const;
    bool spend(int syndicate, float amount);   // false (no change) if insufficient

    int tickCount() const;                     // ticks processed; for tests
};
```

**Revolt rule (deterministic):** a revolt flips an over-taxed territory back to
neutral (`owner = -1`) and resets its `taxLevel` to 0. The exact probability
curve is a balance value and lives in `EconomyConfig` (data), not in code.

### 4.5 `Campaign` — the top-level object

`Campaign` owns the four systems and is what the game layer drives. It is the
only type the map screen needs to know about.

```cpp
enum class CampaignState { Running, Won, Lost };

class Campaign
{
public:
    // Loads a campaign from `campaign.json`, which names the world/research/
    // equipment files and the mission list. Returns false and sets `error`.
    static bool fromJson(const Json& root, Campaign& out, std::string& error);
    static bool loadFromFile(const std::string& path, Campaign& out, std::string& error);

    WorldMap& map();
    Economy& economy();
    Research& research();
    Equipment& equipment();

    // --- player syndicate identity ---
    // The player's chosen name and logo id. A fresh campaign uses the data
    // defaults from `campaign.json`; a choice overrides them. An empty name, or
    // an empty/unknown logo id, clears the choice and falls back to the default,
    // so the map always has an identity and an unknown value is never fatal.
    const std::string& syndicateName() const;
    const std::string& syndicateLogo() const;
    void setSyndicateName(const std::string& name);
    void setSyndicateLogo(const std::string& id);
    const std::string& defaultSyndicateName() const;
    const std::string& defaultSyndicateLogo() const;
    const std::vector<std::string>& syndicateLogos() const; // pickable ids

    // --- end state ---
    // The terminal mission's id (the original's final confrontation), or empty.
    // Winning it under a `"final-mission"` win condition ends the campaign.
    const std::string& finalMission() const;
    // True only when the campaign was won *by* the final confrontation (never
    // under `own-all-territories`), so the victory panel can differ.
    bool wonFinalConfrontation() const;

    // --- selection & deployment ---
    // True if a mission can be deployed to `territory`: it has a mission, and it
    // is player-owned or on the frontier (adjacent to a player-held territory).
    // A win at a frontier territory claims it, so ownership grows inward from the
    // border (ADR-0029). A neutral behind other neutrals is not yet reachable.
    bool canDeployTo(TerritoryId territory) const;

    // Selects the mission deployed from `territory` and the agent slots to send
    // (at most `Equipment::kSquadSlots`). Returns false if the territory is not
    // deployable, or the slot list is too large or out of range.
    bool selectMission(TerritoryId territory, const std::vector<int>& agentSlots);
    TerritoryId selectedTerritory() const;      // -1 if none
    const std::string& selectedMissionId() const;  // empty if none

    // --- progression ---
    // Records the result of the selected mission. A win keeps/claims the
    // territory for `syndicate`; a loss leaves ownership unchanged. Updates the
    // campaign end state. A no-op once finished().
    void recordResult(bool won, int syndicate);

    CampaignState state() const;
    // True once won or lost. The end state is terminal: canDeployTo, recordResult,
    // and tick all become no-ops, so the final board is frozen for the end screen.
    bool finished() const;

    // Ticks the economy and research (the campaign clock). A no-op once finished().
    void tick(float dt, Rng& rng);
};
```

**Starting funds (settled).** `loadFromFile` grants the campaign's
`startingFunds` to the player syndicate in the funds ledger, so a loaded
campaign begins the "tax → research → buy" loop with money. `fromJson` (parsing
only) never moves money, so parsing a config cannot mutate a ledger. `tick` owns
no clock of its own: the caller supplies `dt` and an `Rng`, and the game layer
drives it on the campaign clock (§4.6).

**Deploy targets (settled — ADR-0029).** The original attacks *outward*: a region
is a legitimate target when the player already owns it or holds an **adjacent**
region. `canDeployTo` encodes that, and `selectMission` gates on it, so ownership
spreads inward from the frontier and the map is winnable. A neutral region behind
other neutrals is not yet reachable — the player must take a neighbour first.
Every non-owned region that can ever be attacked needs a `missionId` (a mission
is the only way to take it), and a `missionId` may be **shared** by several
regions, so a small mission set covers a larger map.

### 4.6 Game-layer wiring — the management screen (slice 5, landed)

The core systems are only useful once the game layer drives them. That driver is
`game::CampaignScreen` (`src/game/CampaignScreen.{h,cpp}`), a single
translation unit kept out of the shared `Game.cpp` (`docs/FOCUS_AREAS.md` §4,
Rule 2). It **owns** a `core::Campaign`, loads it from `--campaign <path>` or the
default search, and is presentation and input only: every rule stays in
`core/economy/**` (ADR-0002), and the screen never reimplements one.

```cpp
class CampaignScreen
{
public:
    bool init(const std::string& path, const std::string& exeDir);
    bool valid() const;                 // false => the caller skips the screen
    void toggle();  bool visible() const;  void setVisible(bool);

    void update(float dt);              // advances the campaign clock
    bool handleClick(int x, int y, int w, int h);  // selects a territory
    void adjustTax(int delta);          // clamped to [0, maxTaxLevel]
    bool deploySelected();              // selects the mission + full squad

    void render(SDL_Renderer*, const BitmapFont&, int w, int h) const;
    bool selfTest();                    // headless loop check (on a copy)
};
```

- **Layout is view-only and deterministic.** Territory nodes are placed by a
  breadth-first ring from territory 0 and never saved, so the map has a stable
  layout with no RNG. A missing campaign file leaves the screen invalid and it is
  simply skipped — the tactical game always starts (`AGENTS.md` §1b).
- **The clock is the campaign clock, not the tactical step.** While the screen is
  visible, `Game::update` freezes the tactical simulation (the player is on the
  map, not the board) and calls `CampaignScreen::update(realDt)`, which ticks
  economy + research. `M` toggles the screen; `-`/`+` change the selected
  territory's tax; `D` deploys; `B` opens the R&D shop.
- **The R&D shop is in play (the middle of the loop).** `B` toggles
  `CampaignScreen::shopOpen()`: one list of the research nodes followed by the
  equipment items, navigated with Up/Down, a squad slot chosen with Left/Right,
  and Enter funding research or buying + assigning gear. It is the *player* path
  for the tax → research → buy → deploy loop, which before this was reachable
  only from `selfTest` (the screen could tax and deploy, but never research or
  buy). While open the shop is modal — `CampaignScreen::handleKey` swallows every
  key (Esc/`B` closes) so a management binding cannot fire behind it — and it
  refuses to open once `finished()`. Every rule (cost, prerequisites, the
  research gate, funds) stays in `core/economy/**`; the shop only reads the
  campaign and forwards the action (golden rule 4).
- **The end state is terminal and has its own panel.** Once `Campaign::finished()`
  is true (won or lost), `canDeployTo`, `recordResult`, and `tick` all become
  no-ops, so the board the player sees is frozen; the screen also refuses to
  deploy or change tax (`CampaignScreen::deploySelected`/`adjustTax`). `render`
  then draws a centred victory/defeat panel (headline, a one-line detail, the
  held-territory count, and a quit hint) over a dimmed map. The self-test wins the
  campaign, then checks the won state refuses deployment and taxation.
- **The final confrontation is a distinct end state (issue #456).**
  `campaign.json` may name a `finalMission` (the id of the terminal mission, which
  must be one of its `missions`) and set `winCondition` to `"final-mission"`.
  Under that rule the campaign is won by winning *that* mission, independent of
  territory count — even with neutrals left on the map — so the original's
  climactic ending is representable. `Campaign::wonFinalConfrontation()` is true
  only when the campaign was won *by* the final mission (it stays false under
  `own-all-territories`, even if the terminal mission happened to be among those
  won), and the screen draws a distinct, warmer "FINAL CONFRONTATION WON" panel
  for it. The end state stays terminal either way (`finished()` freezes the
  board). Both conditions are supported: the shipped data keeps
  `own-all-territories` (its last neutral is the named `finalMission`, so the two
  agree today) until the final mission is authored as its own file.
- **Headless guard.** `--check-campaign` (ctest `game_campaign`) runs
  `CampaignScreen::selfTest`, which on a *copy* of the shipped campaign exercises
  starting funds → tax → income → research → buy → assign → attack the frontier
  → win through the real core systems, then drives the R&D shop through the
  player keys (`B`/Enter/Down) and draws it. It wins by *deploying and claiming*
  each remaining region, so a data file that leaves the campaign unwinnable fails
  the guard instead of a playtest. `--map` (ctest `game_map_flag`) starts on the
  screen so the render path is exercised headlessly.

Deployment records the selection (`Campaign::selectMission` with the four fixed
slots) for any region `Campaign::canDeployTo` accepts — owned or on the frontier
(§4.5, ADR-0029); the screen shows the selected region's `STATUS` as
`ATTACK READY` or `NOT REACHABLE`. Mapping the bought loadout onto the mission's
player agents is still **R1** (§7) — the screen calls the contract, and the
mission-side override is Tactical/Content's follow-up.

## 5. Data schema (`assets/data/world/**`)

Parsed by the existing hand-rolled reader (`core/data/Json.*`, ADR-0003). Real
files are strict JSON: **no comments and no trailing commas** (the examples below
use `jsonc` for annotation only, exactly as `docs/DATA_FORMAT.md` does).

### 5.1 `world.json`

```jsonc
{
  "territories": [
    { "id": 0, "name": "Westmarch", "neighbours": [1, 2], "owner": 0,  "missionId": "demo" },
    { "id": 1, "name": "Nordhelm",  "neighbours": [0, 2], "owner": 0,  "missionId": "demo" },
    { "id": 2, "name": "Vostara",   "neighbours": [0, 1], "owner": -1, "missionId": "blackout" }
  ]
}
```

- `id` — required, `>= 0`, unique, dense (`0..size-1`).
- `neighbours` — adjacency; **undirected**, so both sides must list each other.
- `owner` — syndicate index, or `-1`/omitted for neutral.
- `missionId` — optional; must match a mission's `id` (or file stem) when present.
  A neutral region needs one to be attackable, and the same `missionId` may be
  shared by several regions (ADR-0029), so a small mission set covers a larger map.
  In the **shipped** `world.json` every region carries a mission drawn from the
  tactical mission set (`demo`, `escort`, `blackout`, `assembly`, `overpass`) and
  each is listed in `campaign.json`'s `missions`, so the whole map is playable
  rather than five regions replaying two boards (#418). The mapping is pinned by
  `tests/test_campaign.cpp`.

**The shipped map is a world map (issue #448).** v1.0.0 replaces the original
six city-district regions with **twelve culturally-flavoured regions** — evocative
of real-world regions and cultures, never real country or brand names
(`docs/LEGAL.md`): `Westmarch` (the home region, player-owned), `Nordhelm`,
`Vostara`, `Sahari`, `Khoras`, `Sahelia`, `Zambara`, `Andura`, `Indara`, `Sinara`,
`Sundara`, `Pelagia`. Region `0` and `1` start player-owned; the rest are neutral
and are claimed inward from the frontier (ADR-0029). The graph is a fully
connected, symmetric, no-self-loop map whose BFS rings from region `0` lay out
legibly on the map screen (the layout guard in `CampaignScreen::selfTest`
enforces a minimum node separation, so a future edit cannot collapse the map).
Structural validity is pinned by `WorldMap.ShippedWorldIsAConnectedPlayableWorldMap`
in `tests/test_worldmap.cpp`. The region names are also recorded in
`docs/LORE.md` (text lane).

`winCondition` is `"own-all-territories"` (the default) or `"final-mission"`.
`finalMission` (optional) names the terminal mission; it must be one of
`missions`, and a `"final-mission"` win condition **requires** it — both are
schema errors otherwise, so a typo cannot leave the campaign unwinnable
(issue #456).

Sibling file names (`world`, `research`, `equipment`) resolve **relative to the
campaign file**, the same way the mission loader resolves catalogue paths
(`core/data/Catalogues.h` → `cataloguePathForMission`). A missing optional file
is not an error; the system starts empty (matching the mission/catalogue
tolerance, so the game still starts with no data files, `AGENTS.md` §1b).

**Player syndicate identity (issue #445).** `syndicate` is the display name and
`logo` the default logo id; `logos` is the pickable set. All three are plain data
(ADR-0003): a logo id is a stable string key the render lane maps to art — the art
itself is **not** metagame's, so a new logo is a data entry here plus a render
slice. A player choice (name + logo) overrides the default and is carried by the
save (§8); an empty name, or an empty/unknown logo id, falls back to the default
rather than leaving the map without an identity, and is never fatal. `logos` must
be an array of non-empty strings if present; a malformed list is a schema error.

## 6. How the systems compose

```
Campaign ──owns──▶ WorldMap      (topology + ownership + tax level)
         ├───────▶ Economy       (funds; income + revolt tick over the map)
         ├───────▶ Research      (tree + per-syndicate progress)
         └───────▶ Equipment     (catalogue + buy/assign)
```

- `Economy`, `Research`, and `Equipment` operate **on** the world state and a
  shared funds ledger; they do not own each other.
- `Campaign::tick` advances the economy and research; the game layer calls it on
  the campaign clock, not the tactical timestep.
- Deployment maps the selected slots' loadouts onto the player agents of the
  chosen mission. That is the one **cross-area** touch: it needs Tactical's
  `Mission`/`MissionData` to accept a squad loadout (see §7, request R1).

## 7. Cross-area requests (filed with this contract)

- **R1 → Tactical/Content. *(landed, #311)*** Deployment must place the chosen
  squad (up to four agents, with their bought weapons/gadgets) into the mission
  instead of the mission's default player agents. Needed in `core::MissionData` /
  `Mission`. Interface wanted: a way to override the player `AgentSpec`s (weapons
  and gadgets) at load time. Blocks the *mission selection & deployment* sub-task.
  **Delivered:** `core::PlayerLoadout` (`core/sim/PlayerLoadout.h`, data-only
  `weaponId`/`gadgetId` per slot) plus `core::applyLoadout(loadout, mission,
  weapons, error)` in `core/data/MissionData`; an empty id keeps the authored
  default and an unknown id is a content error (ADR-0027). The engine-side wiring
  (`Game`/`CampaignScreen` handing a loadout over on deploy) **landed in #312**:
  `D` on the map resolves the territory's mission file and the bought squad
  (`Campaign::selectedLoadout` → `PlayerLoadout`), starts it with
  `Game::startDeployedMission` (which calls `applyLoadout` at load), and feeds the
  mission's win/lose back to `Campaign::recordResult` (`Game::finishDeployment`),
  returning the player to the map.
- **R2 → Content.** The equipment catalogue's weapon ids must resolve to the
  shared weapon catalogue (`assets/data/weapons.json`). Needed so a bought weapon
  is the same `core::Weapon` the sim fires. Interface wanted: a documented id
  join, no schema change if the ids already match.

Both are filed as comments on #249; they do not block this contract or the first
implementation slice (the world map needs neither).

## 10. Open questions (to settle as the work lands)

1. **Save/load.** The original had save games. This contract keeps campaign state
   in memory for the first slices; a `Campaign` JSON round-trip is a candidate
   follow-up. If we add it, it is a schema change owned by Content (§4 Rule 5)
   and needs an ADR.
2. **Multiple syndicates.** The interfaces take a `syndicate` index and allow
   `-1` = neutral, so rival syndicates are representable, but no AI taxes or
   expands them in v1.0.0. Confirm this is the intended v1.0.0 scope (the
   original's rivals are mostly a campaign map colouring, not a live AI).
3. **Squad ↔ mission mapping.** R1's exact shape (override specs vs. a separate
   deploy step) is Tactical/Content's call; this contract only requires that a
   bought loadout reaches the deployed agents.
4. **Money scaling.** *(settled — #419, the balance pass.)* The shipped
   `campaign.json` is tuned so a fresh campaign (2 owned regions) reaches the win
   in a reasonable number of ticks, and over-taxation is a real gamble: at
   `revoltChancePerTick` 0.06 the risky max tax stops out-earning the safe tax
   after ~38 ticks, so the decision is live but not a trap. The pins live in
   `tests/test_economy.cpp` and `tests/test_research.cpp`, which read the shipped
   files. Further tuning is still a data question — edit `campaign.json`, not
   code.
5. **Player syndicate identity.** *(settled — #445.)* The original lets the
   player name the syndicate and pick a logo at the start. The core now carries
   the choice (`Campaign::syndicateName`/`syndicateLogo`, with data-authored
   defaults and a pickable `logos` set), and the save persists it. The **name
   input field and the logo picker** are a separate **input-ui** slice (the
   new-game screen), and the **logo art** is a **render** slice — a logo id is
   only a stable string key here, so the core stays free of art (golden rule 1).
   Both follow-ups are filed as Rule 4 requests, not built here.
