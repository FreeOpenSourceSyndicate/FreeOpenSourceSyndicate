# Architecture Decision Records (ADRs)

Every architectural decision is recorded here **before** it is implemented, so
parallel agents can rely on it. Format: short, dated, with options and a
decision. Supersede rather than delete.

Status values: `Proposed` · `Accepted` · `Rejected` · `Superseded by ADR-NNNN`.

## ADR-0001 — Game engine / rendering stack

- **Status:** Superseded by ADR-0006
- **Date:** 2026-10-12
- **Context:** The repo was bootstrapped with Cocos2d-x v4 (C++). Cocos2d-x is
  large (fetches a multi-hundred-MB tree), its CMake integration is awkward, and
  it is primarily a 2D/mobile engine. Syndicate needs isometric rendering,
  sprite animation, sound, and cross-platform desktop builds, on hardware as old
  as ~15 years.
- **Options:** keep Cocos2d-x; SDL2 + `SDL_Renderer`; another framework.
- **Decision:** Dropped Cocos2d-x. See **ADR-0006** for the replacement and the
  rationale.

## ADR-0002 — Engine-agnostic core (`src/core`)

- **Status:** Accepted
- **Date:** 2026-10-12
- **Context:** Multiple agents and models work in parallel, and CI must be able
  to verify logic without a GPU or the engine dependency.
- **Decision:** All game logic lives in `src/core/` and must not include
  `cocos2d.h` or any engine header. It builds and is tested with a plain C++
  compiler. The engine layer is a thin adapter that reads core state and draws it.
- **Consequences:** Core is unit-testable and parallelizable. Any logic that
  needs an engine type is by definition not core.

## ADR-0003 — Gameplay data format

- **Status:** Accepted (2026-10-13)
- **Date:** 2026-10-12, accepted 2026-10-13
- **Context:** Content (weapons, agents, missions, balance) must be editable
  without C++ changes and without merge conflicts between agents. The project
  targets very old, low-end hardware and prizes a tiny dependency footprint
  (AGENTS.md §1b, §1c), so a large parser dependency is undesirable. Content
  files are also read and written by many LLM agents, so a format that is easy
  to generate and diff matters more than one that is compact.
- **Options:**
  1. **JSON (subset), hand-rolled parser in `src/core/data/`.** Ubiquitous,
     LLM-friendly, and human-diffable. No third-party dependency if we implement
     a small, allocation-light parser that supports only what our content needs:
     objects, arrays, strings, numbers, booleans, `null`. Comments and trailing
     commas are rejected, so the files stay valid JSON.
  2. JSON via `nlohmann/json` (MIT). Battle-tested, but a large header to compile
     and pull in, against §1b.
  3. YAML. Friendlier to hand-edit but needs a parser and is easier to get wrong.
  4. A custom text/INI format. No dependency, but non-standard and more code to
     maintain, with worse tooling.
  5. Binary. Not editable; rejected.
- **Decision:** **Option 1.** Content lives in `assets/data/` as JSON, parsed by a
  small, dependency-free reader in `src/core/data/` (`Json.h`, `Json.cpp`,
  `MissionData.h`, `MissionData.cpp`). The schema is documented in
  `docs/DATA_FORMAT.md`. Weapons and agents are defined inline per mission for
  now; shared weapon/agent libraries can be added later without breaking the
  format.
- **Consequences:**
  - Content authors edit `assets/data/missions/*.json`; two agents can add
    missions without touching the same C++ file (§4.7, "data over code").
  - The parser is deliberately small: it is not a general JSON implementation,
    and the game rejects malformed or unsupported input with an error string.
  - No new third-party dependency; the low-spec binary stays small (§1b).
  - The loader lives in `core`, so it is unit-tested headlessly and stays
    SDL-free (ADR-0002). The engine layer only decides *where* the file is.
  - Missions may later reference a shared weapon catalogue; that is a
    non-breaking extension.

## ADR-0005 — CI scope

- **Status:** Accepted
- **Date:** 2026-10-12
- **Context:** The full game build needs the engine, which is too heavy to fetch
  reliably on a CI runner.
- **Decision:** CI builds and tests the **core-only** target
  (`-DFOSSYND_BUILD_GAME=OFF`) and runs `ctest`. It also runs a second job that
  installs `libsdl2-dev`, builds the **core + game** target
  (`-DFOSSYND_BUILD_GAME=ON`), and runs `ctest` including the headless `game_smoke`
  test. Engine-layer changes are therefore verified automatically.
- **Consequences:** Core logic and the SDL2 shell are both continuously
  verified. This supersedes the earlier temporary gap (ADR-0001 is resolved by
  ADR-0006).

## ADR-0006 — Adopt SDL2 + SDL_Renderer; drop Cocos2d-x

- **Status:** Accepted
- **Date:** 2026-10-12
- **Context:** Requirement: the game must run on very old, low-end hardware (a
  low-end machine from ~15 years ago). Cocos2d-x v4 is a multi-hundred-MB
  framework with awkward CMake integration and a hard OpenGL dependency; it is
  too heavy and too hard to build and verify in CI. We need a small, fast,
  software-friendly renderer for an isometric tile game.
- **Options:**
  1. **SDL2 + `SDL_Renderer`** — ~1 MB library, permissive zlib license, stable
     C API, mature, available in every distro. `SDL_Renderer` can use the
     `software` backend, so it runs without a GPU. We write our own tiny
     sprite/tile blitter on top.
  2. SDL2 + raw OpenGL — more control, but requires a GPU/driver and more code.
  3. raylib / SFML — similar trade-offs; less ubiquitous than SDL2 on old
     Debian systems.
- **Decision:** Use **SDL2 + `SDL_Renderer`** (software-capable). Keep the
  engine behind the `src/game/` boundary; `src/core/` stays SDL-free (ADR-0002).
- **Consequences:**
  - Small dependency, easy CI, runs on old hardware.
  - We own rendering/input/audio glue — more code, but simple for tiles/sprites.
  - SDL2 is zlib-licensed (MIT-compatible), satisfying the open-source-first rule.
  - The Cocos2d-x bootstrap scripts are obsolete and will be removed.
  - Supersedes ADR-0001.

## ADR-0007 — Simulation owns gameplay; the SDL2 layer is a thin view

- **Status:** Accepted
- **Date:** 2026-10-12
- **Context:** To reach something playable and demonstrable quickly, we needed
  combat, enemy AI, and a win/lose condition. The risk is putting those rules in
  the renderer, which would break the core/sim boundary (ADR-0002), make them
  hard to test, and block parallel work by other agents.
- **Options:**
  1. **All gameplay in `src/core/sim/` (`Mission` orchestrates agents, AI, fire,
     win/lose); `src/game/` only reads state and draws it.** Engine-agnostic,
     fully unit-testable, deterministic.
  2. Gameplay rules in `Game` (the SDL layer). Faster to write once, but
     untestable headless and breaks the boundary.
- **Decision:** Option 1. `core::Mission` steps movement, AI, weapon fire, and
  outcome evaluation on a fixed timestep using a deterministic RNG
  (`core::Rng`, xorshift64*). `Game` translates input into `Mission` orders and
  renders `Mission` state. The scene is described by data passed to
  `Mission::addAgent`, not baked into the renderer.
- **Consequences:**
  - Missions are reproducible: same seed + same orders ⇒ same result, enabling
    deterministic tests (`tests/test_mission.cpp`).
  - The renderer stays replaceable and lightweight (old-hardware goal, ADR-0006).
  - Content is still hard-coded in `Game::buildMission` for now; moving it to a
    data file remains ADR-0003.
  - A tiny embedded bitmap font (`src/game/Font.{h,cpp}`) avoids an SDL_ttf
    dependency; glyphs are original and baked once into an atlas texture.

## ADR-0008 — Low-spec profile for very old hardware

- **Status:** Accepted
- **Date:** 2026-10-12
- **Context:** Development happens on whatever machine is available at the time,
  which is frequently very old, low-end hardware (AGENTS.md 1b). The game must
  *always* run there, not merely "be portable in principle". ADR-0006 already
  chose a software-capable renderer; this ADR makes the low-end target explicit
  and gives it a build profile and a runtime mode that CI exercises.
- **Options:**
  1. **A build option (`-DFOSSYND_LOW_SPEC=ON`) plus a runtime `--low-spec` flag.**
     The build favours a small binary (`-Os`, stripped, no unwind tables); the
     runtime defaults to a small window and forces the SDL software renderer.
  2. A separate "minimal" renderer/backend. More work, more code to maintain,
     and unnecessary while `SDL_Renderer`'s software path exists.
  3. Nothing — rely on the compiler defaults and the existing software fallback.
     Rejected: no explicit target means old-hardware support silently rots.
- **Decision:** Option 1.
  - CMake: `FOSSYND_LOW_SPEC` adds `-Os -fno-unwind-tables
    -fno-asynchronous-unwind-tables`, `-s` at link, and defines
    `FOSSYND_LOW_SPEC_BUILD`.
  - Runtime: `--low-spec` (and the build default) selects a **320x200** window
    and a **software** renderer. Any machine that can open a window can run it.
  - The game runs without a GPU and without large dependencies either way; the
    profile only makes that guarantee explicit and testable.
- **Consequences:**
  - A dedicated CI job always builds `-DFOSSYND_LOW_SPEC=ON` so the profile cannot
    bit-rot (ADR-0005).
  - The low-spec binary is also the smallest artifact for packaging (Phase 5).
  - Low-spec does not change gameplay or determinism: the engine-agnostic core
    (ADR-0002, ADR-0007) is compiled identically in all profiles.

- **Status:** Accepted (2026-10-13)
- **Date:** 2026-10-13
- **Context:** The project must decide what "done" means for v1.0.0 and how to
  treat visual and handling improvements. An earlier convention (AGENTS.md §6a)
  told contributors to prefer **SVG** for graphics; the maintainer has since
  decided that the original's chunky **pixel-art** look is what v1.0.0 should
  reproduce, and that the SVG preference is retracted.
- **Options:**
  1. **Faithful reproduction for v1.0.0; improvements deferred.** Match the
     original's systems, feel, and pixel look; put better graphics and smoother
     handling in v2.x.x or a fork.
  2. Modernise as we go (vector art, smooth scaling, QoL changes). Rejected: it
     would drift away from the original, which is the whole point of v1.0.0.
  3. Ship two visual modes now (pixel and "enhanced"). Rejected as premature;
     that is a v2.x.x concern.
- **Decision:** **Option 1.** v1.0.0 targets the original's look and feel,
  including its **pixel graphics**. Prefer low-resolution, palette-based raster
  art scaled nearest-neighbour. The earlier "prefer SVG" guidance is
  **retracted**. Vector art, higher-fidelity rendering, and modern
  handling/quality-of-life changes are **out of scope for v1.0.0** and belong to
  a v2.x.x release or a fork.
- **Consequences:**
  - `AGENTS.md` §1 (goal), §6a (releases) and golden rule 8 updated; the SVG
    section in `docs/ASSETS.md` replaced with a pixel-art section.
  - The low-spec profile (ADR-0008) is aligned with, not opposed to, the v1.0.0
    goal: a small, low-resolution, software-rendered build is faithful.
  - Legal position unchanged: we recreate the *feel* and the *look* with
    original art and copy no original sprite, palette, or code (`docs/LEGAL.md`).
  - A v2.x.x/fork line is explicitly permitted to pursue the improvements.

## ADR-0010 — Project name: FOSSynd

- **Status:** Accepted
- **Date:** 2026-10-13
- **Context:** The project was named **Free Open Source Syndicate**, shortened to
  **FOSS**. "FOSS" is already the standard abbreviation for *Free and Open Source
  Software*, so the short name was ambiguous and unsearchable, and the build
  option prefix `FOSS_*` read like a generic open-source switch. A new short name
  was needed: English/German only, not an acronym that collides with another
  common term, and (as a bonus, not a requirement) able to nod to the *Syndicate*
  heritage in the `FreeCiv`/`FreeCol` style.
- **Options:**
  1. **`FOSSynd`** — reads as "FOSS" + "syndicate", keeps the open-source
     reference, and follows the `Free<Game>` naming pattern of FreeCiv/FreeCol
     (there, "Free"; here, "FOSS"). Collision-free (0 GitHub results) and
     distinct from the existing `FreeSynd` project and AMD's `FreeSync` mark.
  2. `FreeSyn` — rejected: one letter from the existing open-source `FreeSynd`
     *Syndicate* engine reimplementation and from AMD's trademarked `FreeSync`.
  3. `Sovereign Cartel`, `Konzernstaat`, `Chartered Company` — all clear, but
     none carries the open-source reference that was preferred.
  4. Keep `FOSS` — rejected: ambiguous with the generic term (the original
     problem).
- **Decision:** Option 1. The project is **FOSSynd** ("Free, Open-Source
  Syndicate"). "Syndicate" stays descriptive, never a brand mark (LEGAL.md §3).
  The CMake option prefix becomes `FOSSYND_*`, the core library `fossynd_core`,
  the C++ namespace `fossynd::`, the test macros `FOSSYND_TEST`/`FOSSYND_CHECK*`,
  and the game binary `FOSSynd`.
- **Consequences:**
  - All build options, namespaces, macros, docs, and CI strings use `FOSSynd` /
    `FOSSYND` / `fossynd`; the bare acronym `FOSS` no longer appears.
  - The GitHub org/repo name (`FreeOpenSourceSyndicate/FreeOpenSourceSyndicate`)
    is kept for now: `FOSSynd` is a valid abbreviation of it, so the clone URLs
    and the working-directory name remain correct and need no change.
