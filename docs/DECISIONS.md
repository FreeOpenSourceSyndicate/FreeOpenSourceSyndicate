## ADR-0002 — Engine-agnostic core (`src/core`)

- **Status:** Accepted
- **Date:** 2026-10-12
- **Context:** Multiple agents and models work in parallel, and CI must be able
  to verify logic without a GPU or the engine dependency.
- **Decision:** All game logic lives in `src/core/` and must not include
  `cocos2d.h` or any engine header. It builds and is tested with a plain C++

- **Consequences:** Core is unit-testable and parallelizable. Any logic that
  needs an engine type is by definition not core.

## ADR-0003 — Gameplay data format

- **Status:** Accepted (2026-10-13)
- **Date:** 2026-10-12, accepted 2026-10-13
- **Context:** Content (weapons, agents, missions, balance) must be editable
  without C++ changes and without merge conflicts between agents. The project
  targets very old, low-end hardware and prizes a tiny dependency footprint
  (AGENTS.md §1b, §1c), so a large parser dependency is undesirable. Content
  files are also read and written by many LLM agents, so a format that is easy
  to generate and diff matters more than one that is compact.
- **Options:**
  1. **JSON (subset), hand-rolled parser in `src/core/data/`.** Ubiquitous,
     LLM-friendly, and human-diffable. No third-party dependency if we implement
     a small, allocation-light parser that supports only what our content needs:
     objects, arrays, strings, numbers, booleans, `null`. Comments and trailing
     commas are rejected, so the files stay valid JSON.
  2. JSON via `nlohmann/json` (MIT). Battle-tested, but a large header to compile
     and pull in, against §1b.
  3. YAML. Friendlier to hand-edit but needs a parser and is easier to get wrong.
  4. A custom text/INI format. No dependency, but non-standard and more code to
     maintain, with worse tooling.
  5. Binary. Not editable; rejected.
- **Decision:** **Option 1.** Content lives in `assets/data/` as JSON, parsed by a
  small, dependency-free reader in `src/core/data/` (`Json.h`, `Json.cpp`,
  `MissionData.h`, `MissionData.cpp`). The schema is documented in
  `docs/DATA_FORMAT.md`. Weapons and agents are defined inline per mission for
  now; shared weapon/agent libraries can be added later without breaking the
  format.
- **Consequences:**
  - Content authors edit `assets/data/missions/*.json`; two agents can add
    missions without touching the same C++ file (§4.7, "data over code").
  - The parser is deliberately small: it is not a general JSON implementation,
    and the game rejects malformed or unsupported input with an error string.
  - No new third-party dependency; the low-spec binary stays small (§1b).
  - The loader lives in `core`, so it is unit-tested headlessly and stays
    SDL-free (ADR-0002). The engine layer only decides *where* the file is.
  - Missions may later reference a shared weapon catalogue; that is a
    non-breaking extension.

## ADR-0006 — Adopt SDL2 + SDL_Renderer; drop Cocos2d-x

- **Status:** Accepted
- **Date:** 2026-10-12
- **Context:** Requirement: the game must run on very old, low-end hardware (a
  low-end machine from ~15 years ago). Cocos2d-x v4 is a multi-hundred-MB
  framework with awkward CMake integration and a hard OpenGL dependency; it is
  too heavy and too hard to build and verify in CI. We need a small, fast,
  software-friendly renderer for an isometric tile game.
- **Options:**
  1. **SDL2 + `SDL_Renderer`** — ~1 MB library, permissive zlib license, stable
     C API, mature, available in every distro. `SDL_Renderer` can use the
     `software` backend, so it runs without a GPU. We write our own tiny
     sprite/tile blitter on top.
  2. SDL2 + raw OpenGL — more control, but requires a GPU/driver and more code.
  3. raylib / SFML — similar trade-offs; less ubiquitous than SDL2 on old
     Debian systems.
- **Decision:** Use **SDL2 + `SDL_Renderer`** (software-capable). Keep the
  engine behind the `src/game/` boundary; `src/core/` stays SDL-free (ADR-0002).
- **Consequences:**
  - Small dependency, easy CI, runs on old hardware.
  - We own rendering/input/audio glue — more code, but simple for tiles/sprites.
  - SDL2 is zlib-licensed (MIT-compatible), satisfying the open-source-first rule.
  - The Cocos2d-x bootstrap scripts are obsolete and will be removed.
  - Supersedes ADR-0001.

## ADR-0007 — Simulation owns gameplay; the SDL2 layer is a thin view

- **Status:** Accepted
- **Date:** 2026-10-12
- **Context:** To reach something playable and demonstrable quickly, we needed
  combat, enemy AI, and a win/lose condition. The risk is putting those rules in
  the renderer, which would break the core/sim boundary (ADR-0002), make them
  hard to test, and block parallel work by other agents.
- **Options:**
  1. **All gameplay in `src/core/sim/` (`Mission` orchestrates agents, AI, fire,
     win/lose); `src/game/` only reads state and draws it.** Engine-agnostic,
     fully unit-testable, deterministic.
  2. Gameplay rules in `Game` (the SDL layer). Faster to write once, but
     untestable headless and breaks the boundary.
- **Decision:** Option 1. `core::Mission` steps movement, AI, weapon fire, and
  outcome evaluation on a fixed timestep using a deterministic RNG
  (`core::Rng`, xorshift64*). `Game` translates input into `Mission` orders and
  renders `Mission` state. The scene is described by data passed to
  `Mission::addAgent`, not baked into the renderer.
- **Consequences:**
  - Missions are reproducible: same seed + same orders ⇒ same result, enabling
    deterministic tests (`tests/test_mission.cpp`).
  - The renderer stays replaceable and lightweight (old-hardware goal, ADR-0006).
  - Content is still hard-coded in `Game::buildMission` for now; moving it to a
    data file remains ADR-0003.
  - A tiny embedded bitmap font (`src/game/Font.{h,cpp}`) avoids an SDL_ttf
    dependency; glyphs are original and baked once into an atlas texture.

## ADR-0008 — Low-spec profile for very old hardware

- **Status:** Accepted
- **Date:** 2026-10-12
- **Context:** Development happens on whatever machine is available at the time,
  which is frequently very old, low-end hardware (AGENTS.md 1b). The game must
  *always* run there, not merely "be portable in principle". ADR-0006 already
  chose a software-capable renderer; this ADR makes the low-end target explicit
  and gives it a build profile and a runtime mode that CI exercises.
- **Options:**
  1. **A build option (`-DFOSSYND_LOW_SPEC=ON`) plus a runtime `--low-spec` flag.**
     The build favours a small binary (`-Os`, stripped, no unwind tables); the
     runtime defaults to a small window and forces the SDL software renderer.
  2. A separate "minimal" renderer/backend. More work, more code to maintain,
     and unnecessary while `SDL_Renderer`'s software path exists.
  3. Nothing — rely on the compiler defaults and the existing software fallback.
     Rejected: no explicit target means old-hardware support silently rots.
- **Decision:** Option 1.
  - CMake: `FOSSYND_LOW_SPEC` adds `-Os -fno-unwind-tables
    -fno-asynchronous-unwind-tables`, `-s` at link, and defines
    `FOSSYND_LOW_SPEC_BUILD`.
  - Runtime: `--low-spec` (and the build default) selects a **320x200** window
    and a **software** renderer. Any machine that can open a window can run it.
  - The game runs without a GPU and without large dependencies either way; the
    profile only makes that guarantee explicit and testable.
- **Consequences:**
  - A dedicated CI job always builds `-DFOSSYND_LOW_SPEC=ON` so the profile cannot
    bit-rot (ADR-0005).
  - The low-spec binary is also the smallest artifact for packaging (Phase 5).
  - Low-spec does not change gameplay or determinism: the engine-agnostic core
    (ADR-0002, ADR-0007) is compiled identically in all profiles.

## ADR-0011 — Published release branches are immutable; the sole account may self-merge

- **Status:** Accepted (2026-10-13)
- **Date:** 2026-10-13
- **Context:** Two coordination questions came up. (1) A published release
  (`release/vX.Y.Z-*` + tag + GitHub Release page) is an artifact a human may
  already have cloned and built; should later agents be allowed to commit to it?
  A concrete case: the `v0.3.0` release carries a `assets/ui/banner.svg` that the
  later pixel-art decision (ADR-0009) no longer favours. (2) With only one
  GitHub account active on the project, requiring independent review of every PR
  stalls the queue — the creator is also the only available reviewer.
- **Options:**
  1. **Freeze releases; allow creator self-merge for now.** Never touch a
     published release branch/tag except to keep it *working* (and then only on
     a new branch off it); let the creator review and merge their own PRs while
     they are the only account.
  2. Keep editing release branches for doc/cleanup fixes. Rejected: it rewrites
     a snapshot humans may depend on and breaks reproducibility.
  3. Require independent review even with one account. Rejected: impossible
     without a second account; it just leaves green PRs unmerged.
- **Decision:** **Option 1.**
  - **Release branches are immutable** once published. No commits, rewrites, or
    re-tags — not for docs or cleanup. The only exception is a fix needed because
    the release would otherwise **break** (e.g. a required library disappeared) or
    because the law requires it; such a fix goes on a **new branch cut from the
    finished release branch** (e.g. `fix/v0.3.0-<desc>`), never on the original.
  - **The creator may review and merge their own PR** as long as the repository's
    GitHub account is the only account working on the project. Once a second
    account joins, independent review resumes.
- **Consequences:**
  - `AGENTS.md` §6b (new) states the immutability rule; §3a states the
    sole-account self-merge rule.
  - The `v0.3.0` `banner.svg` is deliberately **left in place**: it is not loaded
    at runtime, so it neither breaks nor legally endangers the release, and
    ADR-0009 already governs all future art. No repair branch is needed.
  - Existing shipped releases (`v0.1.0`–`v0.3.0`) are frozen as of this ADR.

## ADR-0012 — `main` is the complete project record

- **Status:** Accepted (2026-10-14)
- **Date:** 2026-10-14
- **Context:** The release process (`AGENTS.md` §6a) had agents write the
  numbered `CHANGELOG.md` section and the `docs/releases/vX.Y.Z-<slug>.md`
  playtest doc **only on the release branch**, then cut the tag. As a result,
  `main` never showed `0.3.0` or `0.4.0` in its changelog, and `docs/releases/`
  did not exist on `main` at all: the project's own history was only visible if
  you checked out a tag. That makes `main` a poor source of truth for a human or
  agent trying to understand what has shipped. (The same mistake stranded the
  v0.3.0 on-screen version stamp's *code* on its release branch.)
- **Options:**
  1. **Keep release metadata only on the release branch.** Rejected: `main`
     loses the history, and the tagged snapshot is the only place the record
     lives — exactly the problem this ADR fixes.
  2. **Keep release metadata only on `main`, not on the release branch.**
     Rejected: the release doc is deliberately version-specific and belongs with
     the frozen snapshot too, so a person who checks out the tag sees it.
  3. **Keep it on both.** Chosen: the release branch carries the version-specific
     doc and the numbered changelog section *for that snapshot*; `main` carries
     the same numbered section and doc as the durable record. The two copies are
     identical at the moment of the tag and may drift only if `main` later
     corrects a typo (the release branch stays frozen — ADR-0011).
- **Decision:** **Option 3.** Everything the project has shipped is visible on
  `main`:
  - `CHANGELOG.md` on `main` keeps the **full, numbered history**; the
    `[Unreleased]` section only ever holds work that has not been released yet.
  - `docs/releases/vX.Y.Z-<slug>.md` is committed to `main` as well as to the
    release branch, and is listed in `docs/releases/README.md`.
  - When a release ships, these land on `main` in the same change that updates
    `AGENTS.md` §10.
- **Consequences:**
  - `AGENTS.md` §6a gains rule 6 ("`main` is the complete record");
    `docs/CONTRIBUTING.md` mirrors it.
  - Backfilled for the existing releases: `main` now carries the `0.3.0` and
    `0.4.0` changelog sections and their `docs/releases/*.md` docs. The v0.1.0
    and v0.2.0 changelog sections were already on `main`; they predate the
    `docs/releases/` convention, so no per-version doc is backfilled for them.
  - Release branches remain frozen and untouched (ADR-0011); this ADR only adds
    copies to `main`, it does not edit any published branch or tag.

## ADR-0013 — Sprites are authored text baked in `core`, uploaded by the view

- **Status:** Accepted (2026-10-13)
- **Date:** 2026-10-13
- **Context:** Phase 2 replaces the flat agent diamonds with pixel-art sprites
  (depth-sorted, with a short walk cycle). Several hard constraints collide:
  assets must be original and license-clean (`docs/ASSETS.md`) and authored by
  LLM agents, so no binary art can be committed from a drawing tool; the game
  must stay a single self-contained executable on very old hardware (AGENTS.md
  §1b); and `src/core/` must not include `SDL.h` (ADR-0002, golden rule 1), so
  the testable sprite logic cannot live in the view.
- **Options:**
  1. **Commit PNG/BMP art and load it with `SDL_image`.** Rejected: adds a
     dependency, a second binary-asset pipeline, and (for hand-picked art)
     licensing/attribution risk. Nothing here can be produced by a text-only
     agent and diffed in review.
  2. **Bake pixels directly in C++ as arrays.** Rejected: unreadable, hurts the
     "data over code" rule (golden rule 7), and makes edits merge-conflict-prone.
  3. **Author the sprites as plain text (`B`/`T`/`S`/`D` pixels + an `A`
     anchor), parse and palette them in `core`, and upload the result to an SDL
     texture in `game`.** Chosen: mirrors the existing `BitmapFont`
     (dependency-free, authored) and the embedded-mission pattern
     (`EmbeddedMission.cpp.in`), keeps the pixel logic engine-free and
     unit-testable, and lets a text-only agent author or adjust art in review.
- **Decision:** **Option 3.**
  - `assets/sprites/agents.txt` is the authored sheet: one `frame <name>` block
    per frame, pixels drawn with `B` (body), `T` (trim), `S` (skin), `D` (dark),
    `.` (transparent), and exactly one `A` (anchor) for agent frames. Props
    (crate, barrel) have no anchor; theirs defaults to bottom-centre so scenery
    rests on its tile.
  - `src/core/data/AgentSprites.{h,cpp}` parses and bakes this text into
    RGBA8888 frames. It is engine-free and I/O-free (the caller reads the file or
    the embedded string), so it is unit-tested with a plain compiler.
  - `src/game/Sprite.{h,cpp}` uploads a baked sheet to one texture laid out
    frames-left-to-right and blits a frame with its anchor. Per-role palettes give
    players, enemies, civilians, and followers distinct colours from one sheet.
  - The sheet is embedded at configure time via
    `game/EmbeddedSprites.cpp.in` (as the demo mission is), so the binary stays
    self-contained. A bad sheet is non-fatal: the view falls back to the old flat
    diamonds, and the `game_sprites` ctest fails instead of the player.
  - View-only animation state (facing, walk phase) lives in `Game` and is derived
    from position deltas; it never feeds back into the simulation (golden rule 4).
- **Consequences:**
  - New content is authored as text and diffed like code; no binary assets and no
    new dependency. Follow the `BitmapFont`/embedded-mission precedents.
  - `core` gains a generic `bakeSheet` (usable for future content) plus the agent
    wrapper. Both are covered by `tests/test_sprites.cpp`.
  - `TileGrid` gains a presentational `Decor` layer (crates/barrels) placed only
    on blocked tiles, so decor never competes with agents for a tile.
  - Rendering is now a single painter's-algorithm pass (agents + props sorted by
    screen Y), the depth-sorted sprite pass the roadmap called for.

## ADR-0014 — Mission win conditions are data-driven (`ObjectiveSpec`), evaluated in `core`

- **Status:** Accepted (2026-10-13)
- **Date:** 2026-10-13
- **Context:** Issue #30 asks for objectives beyond "eliminate all enemies":
  reach a tile, and survive for a time. The original win/lose check was a single
  `aliveCount(Enemy) == 0` in `Mission::evaluateOutcome`. Objectives are content,
  and golden rule 7 says content is data, not hard-coded C++. But the evaluation
  is simulation logic, which golden rule 1 keeps in `src/core/` with no SDL. The
  existing mission schema (ADR-0003, `docs/DATA_FORMAT.md`) is a natural place to
  declare the objective, but it is owned by the `focus: content` lane.
- **Options:**
  1. **A boolean/enum hard-coded in C++ per mission.** Rejected: violates "data
     over code"; every new mission branch would be a merge hotspot.
  2. **A scripting layer for objectives.** Rejected for now: ADR-0004 already
     defers scripting; a full interpreter is far more than #30 needs.
  3. **An `ObjectiveSpec` value type in `core` plus an optional `objective`
     block in mission JSON.** Chosen: the smallest extension that is data-driven,
     stays engine-free, and keeps the default behaviour identical.
- **Decision:** **Option 3.**
  - `core/sim/Objective.h` defines `ObjectiveSpec { kind, tileX, tileY, seconds,
    agentIndex, targetCount }` with `Kind` ∈ `{ EliminateAll, ReachTile, Survive,
    Escort, Destroy, Persuade }`, plus `objectiveKindName`. It is a plain value
    type with no JSON or SDL dependency. (`agentIndex`/`targetCount` and the last
    three kinds were added in #281; see the amendment below.)
  - `MissionData` (content lane) gains an `objective` field and
    `parseObjectiveJson`, wired into `fromJson`; `populateMission` calls
    `Mission::setObjective`. `docs/DATA_FORMAT.md` documents the block.
  - `Mission` owns the objective and a frozen-on-end `elapsedSeconds()` clock.
    `evaluateOutcome` checks the objective's win condition first, then the
    universal lose condition (squad dead). The original **win-first** precedence
    is preserved so the default `eliminate` outcome is unchanged.
  - `EliminateAll` is the default (an empty/absent `objective`), so every
    existing mission and the embedded demo behave exactly as before.
- **Consequences:**
  - New objectives are a new enum value + a data branch, not a code fork; the
    common "add a mission" path stays a JSON-only change.
  - The `reach` target tile is not bounds-checked against the grid at load time:
    parsing stays independent of `TileGrid`; an out-of-bounds target simply can
    never be won. Revisit if it proves confusing. (Superseded in practice by
    #212: `reach` — and now `escort`/`destroy` — tiles are bounds-checked against
    the declared `width`/`height` at load, which is still grid-independent.)
  - Covered by `tests/test_mission.cpp` (evaluation) and
    `tests/test_missiondata.cpp` (parsing, invalid schemas, disk loading).
  - Cross-lane touch (content: `MissionData`/`DATA_FORMAT.md`; render: one HUD
    string) is disclosed per `docs/FOCUS_AREAS.md` §4 Rule 3.

    the win is `targetCount` living followers across the squad.
  - Evaluation stays in `Mission::evaluateOutcome` via small const helpers, so
    the switch is a data branch, not a fork. The per-kind conditions are
    unit-testable in isolation.
  - The loader bounds-checks an escort's `agentIndex` against the parsed agents
    (a content error otherwise), and shares one on-map tile check across
    `reach`/`escort`/`destroy` (the #212 pattern).
- **Consequences:**
  - `assets/data/missions/escort.json` becomes the first escort mission, and the
    HUD banner reads a per-kind string (`hud.objective.escort/destroy/persuade`).
  - `assassinate` and `retrieve` are deliberately **not** new kinds: they are a
    thin variant of `eliminate` (one named target) and `escort` (a prop instead
    of an agent). If a mission needs them they can be added the same way, but the
    Roadmap treats "escort/retrieve" as one item and it is satisfied.
  - Covered by `tests/test_mission.cpp` (win/lose per kind, determinism) and
    `tests/test_missiondata.cpp` (parsing, invalid schemas, disk load, populate).

## ADR-0015 — A sanitizer build profile (`FOSSYND_SANITIZE`) and a CI lane

- **Status:** Accepted (2026-10-14)
- **Date:** 2026-10-14
- **Context:** `src/core/` is the engine-agnostic game logic (ADR-0002) and is
  where the subtle bugs live: the hand-rolled JSON parser, pathfinding, combat
  math, and fixed-timestep arithmetic. The existing CI lanes (ADR-0005) prove the
  core *builds* and its unit tests *pass*, but neither catches memory errors
  (buffer overruns in the JSON reader, use-after-free, leaks) nor undefined
  behaviour (signed overflow, bad shifts, misaligned access) that happen to
  produce passing tests on one compiler.
- **Options:**
  1. **A CMake option `FOSSYND_SANITIZE` plus a core-only CI job.** The option
     adds `-fsanitize=address,undefined -fno-sanitize-recover=all
     -fno-omit-frame-pointer -g` to compile and link, and sets strict
     `ASAN_OPTIONS`/`UBSAN_OPTIONS` on the test; CI runs it on every change.
  2. A separate build script that always sanitizes. Rejected: duplicates the
     CMake logic and drifts from the real build.
  3. Sanitize every build. Rejected: opposed to the low-spec goal (AGENTS.md
     §1b) — ASan inflates the binary and slows execution, and old hardware is the
     target, not a sanitizer host.
  4. Nothing. Rejected: memory/logic bugs would only surface as crashes on a
     player's machine.
- **Decision:** **Option 1.**
  - `FOSSYND_SANITIZE` is a top-level CMake option, **OFF** by default, so normal
    and low-spec builds are unchanged and pay no runtime cost (the low-spec
    profile, ADR-0008, is untouched).
  - `ON` applies ASan + UBSan to every target in the build; the CI lane uses
    `-DFOSSYND_BUILD_GAME=OFF`, so the sanitizer build stays core-only, needs no
    graphics dependencies, and stays fast.
  - `-fno-sanitize-recover=all` makes the first UBSan finding fatal, and the
    `core_unit_tests` test sets `ASAN_OPTIONS=detect_leaks=1:abort_on_error=1`
    and `UBSAN_OPTIONS=print_stacktrace=1:halt_on_error=1`, so a red lane is
    unambiguous.
  - CI also installs and caches `ccache` in every job, so sanitizer and plain
    builds are incremental.
- **Consequences:**
  - A new CI job `Sanitizers (ASan + UBSan, core)` runs on every push/PR; a red
    lane means a real bug in `src/core/`, not a flaky test.
  - The option is **additive**: no existing `FOSSYND_*` option, target name, or
    job name changes, so other areas rebase freely (`docs/FOCUS_AREAS.md` §4
    Rule 5).
  - Sanitizers are a developer/CI tool and are never shipped: the released and
    low-spec binaries do not link `libasan`/`libubsan`.
  - Engine-layer (`src/game/`) code is not sanitized by this lane — that would
    need SDL2 in CI and is deliberately out of scope for #36.

## ADR-0016 — UI strings live in a data-driven table (`core::i18n::StringTable`)

- **Status:** Accepted
- **Date:** 2026-10-14
- **Context:** Issue #35 (roadmap Phase 5, "Localization scaffolding") asks to
  move HUD/UI strings out of C++ into a data file so wording can be edited and
  translated without recompiling. Four constraints collide: the game must stay a
  single self-contained binary on very old hardware (AGENTS.md §1b) and add no
  dependency (§1c); `core` must stay SDL-free and unit-testable (ADR-0002);
  content is data, not code (golden rule 7); and text is a natural merge hotspot,
  so keeping it out of `src/game/Game.cpp` avoids collisions between agents.
- **Options:**
  1. **A heavyweight i18n library (gettext/ICU).** Rejected: a new dependency
     and binary weight for a handful of strings — conflicts with §1b/§1c.
  2. **Hard-coded `const char*` arrays in C++.** Rejected: violates "data over
     code"; every wording change is a code change and a merge hotspot in a
     shared file.
  3. **A dependency-free string table in `core`, loaded from JSON by the
     existing `core/data/Json` reader, plus a text-embedded fallback.** Chosen:
     reuses the ADR-0003 loader (no new dependency), keeps lookup engine-free and
     testable, and mirrors the embedded-mission / embedded-sprites pattern so the
     binary stays self-contained.
- **Decision:** **Option 3.**
  - `core/i18n/StringTable.{h,cpp}` is a value type: `loadFromJson` /
    `loadFromFile`, `get(key, fallback)`, `has(key)`, `size()`. `get` returns the
    value, else the caller's `fallback` literal, else the key itself — so a
    missing key is visible in the UI, never blank, and never throws. It holds no
    global state, so two tables (two languages) can coexist.
  - Keys are stable dotted identifiers (`hud.objective.eliminate`); values are
    display strings. `assets/lang/<lang>.json` is a flat `"key": "value"` object
    (`en.json` is the reference table); a leading `_comment` key is ignored by
    lookups. This is the string-table schema other areas compile against.
  - Placeholders (`{count}`, `{x}`, `{y}`, `{seconds}`, `{version}`, `{marker}`,
    `{name}`, `{weapon}`, `{hp}`) are substituted by the caller in `game`; the
    table does no formatting, so it stays presentation-free.
  - `defaultLangPaths(exeDir, lang)` mirrors `core/data/ContentPaths`
    (repo-relative, next to the exe, `/usr[/local]/share`). The table is also
    embedded at configure time via `game/EmbeddedLang.cpp.in`, as the demo
    mission and sprite sheet are, so the game runs with no data files.
  - `Json` gains one **additive** accessor, `asObject()`, so a table whose keys
    are themselves data can be enumerated; it changes no existing behaviour.
- **Consequences:**
  - New UI text becomes a JSON-only change; translators add
    `assets/lang/<lang>.json` without touching C++. Wording changes stop
    colliding in `Game.cpp`.
  - The engine layer still owns layout and placeholder substitution; only the
    literal strings move to data. Swapping the HUD literals in `Game.cpp` is a
    Render task, filed as a cross-area request (FOCUS_AREAS.md §4 Rule 4).
  - `docs/LORE.md` records original naming/lore guidance so new strings stay
    LEGAL-compliant (`docs/LEGAL.md`: no text from any commercial game).
  - Covered by `tests/test_i18n.cpp` (lookup, fallback, schema errors, disk load
    of the shipped `en.json`, path search). `Json::asObject` is exercised from
    that i18n-owned test file, so no cross-area edit to `tests/test_json.cpp` is
    needed.

## ADR-0017 — Packages are built with CPack (Linux first)

- **Status:** Accepted (2026-10-14)
- **Date:** 2026-10-14
- **Context:** Roadmap Phase 5 lists "Packaging for Linux/macOS/Windows" as
  tooling. Today a playtester copies a bare binary or runs `cmake --install` by
  hand (the v0.5.0 release doc documents the latter). Nothing produces a
  versioned, installable artifact, and nothing in CI guards the install layout,
  so a broken `install()` rule or a wrong version stamp would only be found by a
  human. Constraints: keep the footprint tiny and dependency-free (AGENTS.md
  §1b, §1c), keep the package layout single-sourced with the existing `install()`
  rules, and stay additive so other areas' builds are unchanged.
- **Options:**
  1. **CPack in the top-level `CMakeLists.txt`, `TGZ` + `DEB`, plus a CI job.**
     CPack ships with CMake (no new dependency), consumes the existing
     `install()` rules, and stamps the project version automatically.
  2. Hand-written `scripts/package.sh` calling `dpkg-deb`/`tar` directly.
     Rejected: duplicates the install layout and drifts from `install()`.
  3. Add `dh_make`/`debhelper` packaging. Rejected: heavyweight, more
     dependencies, aimed at distro maintainers, not our playtest artifacts.
  4. Nothing. Rejected: no reproducible artifact, install layout unguarded.
- **Decision:** **Option 1.**
  - The top-level `CMakeLists.txt` configures CPack: name `FOSSynd`, version
    from `project()`, MIT license, and `CPACK_PACKAGE_FILE_NAME`
    `FOSSynd-<version>-<system>`. `include(CPack)` is additive: it adds the
    `package` target and changes nothing unless that target runs.
  - Generators: `TGZ` always; `DEB` is appended only when `dpkg-deb` is found on
    a non-Apple Unix, so the config is harmless on macOS/Windows. DEB metadata is
    fixed: section `games`, priority `optional`, dependency `libsdl2-2.0-0`.
  - The package is built from the existing `install()` rules, which now also ship
    `LICENSE` and `README.md` under `share/doc/fossynd` (docs/LEGAL.md).
  - A CI job `Packaging (Linux TGZ + DEB)` builds both artifacts, asserts the
    tarball contains `bin/FOSSynd`, prints the `.deb` metadata, and runs the
    packaged binary headless — so packaging cannot bit-rot.
  - macOS/Windows packaging is **out of scope** here (no regular testers) and is
    a follow-up.
- **Update (2026-10-15) — platform follow-ups, same decision.** The other two
  platforms landed on this same CPack foundation, so they are recorded here
  rather than as new ADRs:
  - **macOS:** `DragNDrop` (`.dmg`) + `TGZ`, added by #118. The `Packaging
    (macOS …)` job is **gated to `workflow_dispatch` and non-blocking**, because
    macOS runners on this repo can queue and then be cancelled before starting,
    which would redden `main` and deadlock merges (#136, #138).
  - **Windows:** `ZIP` (no NSIS/WiX tooling needed), added by #133. The target
    links `SDL2::SDL2main` (SDL supplies `WinMain` and calls `main` from it) and
    the install rules ship `SDL2.dll` next to `FOSSynd.exe` so the archive is
    self-contained. Its CI job uses the same **dispatch-gated, non-blocking**
    pattern as macOS. Linux remains the only hard packaging gate.
  - No existing generator, `FOSSYND_*` option, target name, or job name changed,
    so other areas still rebase freely (`docs/FOCUS_AREAS.md` §4 Rule 5).
- **Consequences:**
  - `cmake --build build --target package` yields
    `FOSSynd-<version>-Linux.tar.gz` and `fossynd_<version>_amd64.deb`.
  - The layout stays single-sourced: changing an `install()` rule changes the
    package; there is no second copy of the file list.
  - New CI job only; no existing `FOSSYND_*` option, target name, or job name
    changes, so other areas rebase freely (`docs/FOCUS_AREAS.md` §4 Rule 5).
  - The packaged binary still finds its data via the install layout
    (`core/data/ContentPaths`), verified by running the extracted binary.
  - `FOSSYND_LOW_SPEC`/`FOSSYND_SANITIZE` builds are unaffected; packaging is not
    part of the shipped runtime and adds no dependency to the binary.

## ADR-0019 — Flat, self-coordinating focus areas (no central coordinator)

- **Status:** Accepted (2026-10-14)
- **Date:** 2026-10-14
- **Context:** The project is worked by several LLM agents in parallel, and they
  may **abort mid-cycle** (a chat ends, a run times out, a model is swapped). The
  previous scheme routed coordination through a single **coordinator** role: one
  agent per cycle reviewed and merged the queue, arbitrated overlaps, kept the
  workload plan, and was the first stop for questions. A single role that the
  whole fleet depends on is a **single point of failure**: when that agent
  aborts, the merge queue stalls, overlaps go unarbitrated, and no one is
  authorised to act. Coordination authority that lives in *one* agent is the
  wrong shape for an unreliable fleet.
- **Options:**
  1. **Keep the coordinator role, add a timeout/handoff.** Rejected: it still
     concentrates authority in one agent and depends on a successor noticing the
     silence; the failure mode (a stalled queue) remains.
  2. **Drop coordination entirely; let agents grab whatever is free.** Rejected:
     this is how two agents edit the same file and `main` goes red — the exact
     problem the focus areas exist to prevent.
  3. **Keep the eight focus areas as the only structure; derive all coordination
     from area boundaries, peer to peer.** Chosen: authority is already
     distributed — each area owns its files — so the rules that used to be the
     coordinator's job become *mechanical, area-local* rules any agent can apply
     without permission.
- **Decision:** **Option 3.** Coordination is **flat and self-service**:
  - **There is no coordinator role and no `focus: coordinator`.** Every agent is
    an equal peer. No agent holds authority over another's focus.
  - **A file has exactly one owning area** (`docs/FOCUS_AREAS.md` §2). That
    single rule does the work the coordinator used to do: only the owning area
    (or a helper it explicitly tasks) edits a file, so two agents cannot collide
    on one file by construction.
  - **Claiming is self-service and lease-based.** An agent claims an issue and
    records the lease in a **single machine-readable line** (§"claim protocol"
    below). No assignment step is needed.
  - **Abandoned work is reclaimed by timeout, not by a person.** A claim with no
    push and no comment for **24 h** is expired and any agent may take it over —
    this replaces "the coordinator reassigns". An orphaned **PR** is adopted by
    the first willing agent via the §3a merge path.
  - **Overlaps are resolved by the fixed priority order in
    `docs/FOCUS_AREAS.md` §4**, applied by the agents involved; ties are broken
    by *whoever's PR is already merged* (merged code wins), never by an
    authority.
  - **Process docs are shared-maintainer, not coordinator-owned.** Any agent may
    propose a change to `AGENTS.md`, `docs/COORDINATION.md`,
    `docs/FOCUS_AREAS.md`, `docs/DECISIONS.md`, `docs/ROADMAP.md` through the
    normal PR, but such a PR needs **two peer reviews** (or, under the sole-account
    rule, an explicit self-review against the checklist) and never edits a file
    that is under an active claim by another agent.
  - **The rules no longer need a live owner.** They are written down here and in
    `FOCUS_AREAS.md`; any agent can read and apply them, so an aborted agent
    leaves no role unfilled.
- **Consequences:**
  - The **merge queue is peer-run**: any agent may review and merge any PR it did
    not author (`AGENTS.md` §3a). A PR with no author present is adopted and
    merged by whoever is free. With a single GitHub account, the sole-account
    self-merge rule still applies.
  - The **workload plan** (`docs/FOCUS_AREAS.md` §8) is a *hint*, refreshed by
    whoever notices it is stale — not a coordinator deliverable.
  - The **coordination hub** (#38) becomes a **bulletin board**, not a control
    channel: check-ins, availability, and disputes are posted there for
    visibility, and no one needs to grant permission.
  - A single aborted agent now strands at most **its own claim**, which the 24 h
    lease expires; the fleet keeps moving because no other agent was ever waiting
    on it.
  - Helper work stays **request-based** (an agent does not start in another area
    on its own), but the request is now made **to the area's owner directly**;
    if that owner is gone, the 24 h lease (or the free-zone fallback in
    `FOCUS_AREAS.md` §5) lets the helper take it.

### Claim protocol (machine-readable, one line)

To make abandonment detectable without a coordinator, every claim writes exactly
one line, on the issue:

```
CLAIM: <model> | <focus: label> | <branch> | <YYYY-MM-DDThh:mmZ>
```

and every subsequent work signal (a push, a PR comment, a status update) appends:

```
LEASE: <model> | <branch> | <YYYY-MM-DDThh:mmZ>
```

The **latest `CLAIM`/`LEASE` timestamp for a branch is its lease**. If the lease
is older than **24 h** and the branch has had no new push in that window, the
claim is **expired**: any agent may comment `TAKEOVER: <model> | <focus: label>`
and proceed. Takeover is announced, never silent. This is the whole replacement
for reassignment by a coordinator.

## ADR-0020 — Mission-authored text is localised by mission id, not by file

- **Status:** Accepted
- **Date:** 2026-10-15
- **Context:** Issue #142. `core::i18n::StringTable` (ADR-0016) localises UI
  chrome, and `--lang` (issue #123) resolves a locale at runtime, but the text a
  mission authors — its `name` and `description` in
  `assets/data/missions/*.json` — stays English for a German player. Three things
  collide: mission files are **content** (`focus: tactical` owns
  `assets/data/missions/`, `focus: content` owns the loader), the text lane must
  not edit either; the localisation key must be **stable across a translated
  display name** (so keying on the English name is wrong); and the game must
  still run when a mission has no translation (self-contained binary, §1b).
- **Options:**
  1. **Key on the mission's English `name` string.** Rejected: editing the
     English copy silently orphans every translation, and two missions could
     share a name.
  2. **Add a `name`/`description` key map inside each mission JSON.** Rejected:
     it puts localisation into the content schema, which `focus: content` owns,
     and duplicates the string-table schema.
  3. **Derive a stable id from the mission content path (the file stem) and key
     the string table on it** (`mission.<id>.name` / `mission.<id>.desc`), with
     the text lane owning the lookup and the keys. Chosen: no content-schema
     change is *required* (an id is derived from the path), the key is stable
     across copy edits and languages, and a mission without keys simply shows its
     authored text.
- **Decision:** **Option 3.**
  - New `core/i18n/MissionText.{h,cpp}` (engine-free, no I/O):
    `missionIdFromPath(path)` returns the file stem (`.../demo.json` → `demo`)
    only when it is a safe key segment (`[a-z0-9_-]+`); `missionNameKey(id)` /
    `missionDescKey(id)` build `mission.<id>.name` / `mission.<id>.desc`, and
    return `""` for an unsafe id so localisation is skipped rather than building
    an ambiguous dotted key; `localizeMissionText(table, key, raw)` returns the
    table value when the key is present and non-empty, else `raw` unchanged.
  - The resolver is **idempotent**: it resolves from the mission's own authored
    text, so applying it twice is safe (the second pass yields the same value).
  - Shipped missions carry `mission.<id>.name` / `mission.<id>.desc` keys in
    every locale; the existing #125 parity gate in `tests/test_i18n.cpp` keeps
    `en`/`de` in lockstep, so a new key cannot ship untranslated.
  - An **optional** mission `"id"` field (parsed into `MissionData::id`) is
    proposed as an additive content-schema change (Rule 4 request, `focus:
    content`); until it lands, the id is derived from the content path, so this
    decision needs no content edit to be useful.
- **Consequences:**
  - A mission gains a translation by adding two JSON keys — no C++, no content
    edit, no rebuild of the mission schema.
  - Localisation is opt-in and fail-safe: no id, no keys, or an empty value all
    leave the authored copy intact (never blank, never a raw key).
  - Wiring `MissionData`'s localised text into the game (`Game::buildMission`)
    and any on-screen display is an **engine-layer** change owned by
    `focus: input-ui` / `focus: render`; filed as a Rule 4 request rather than
    edited here (`Game.cpp` had a live PR).
  - Covered by `tests/test_i18n.cpp` (key derivation, id-from-path, fallback,
    idempotency, empty-value safety, and shipped-locale parity for every
    mission).


## ADR-0021 — Git-ref leases: machine-checked, self-expiring coordination

- **Status:** Accepted (2026-10-15)
- **Date:** 2026-10-15
- **Supersedes:** the *claim mechanics* of ADR-0019. ADR-0019's central decision
  — **flat, no coordinator** — stands and is reinforced here; what changes is
  *how* a claim is recorded and expired.

- **Context:** ADR-0019 removed the coordinator and made the eight focus areas
  the coordination mechanism. That was the right call, but the *claim protocol*
  it introduced is prose that a human must police:

  1. **A claim is a comment.** `CLAIM:` / `LEASE:` / `TAKEOVER:` lines live in
     issue comments and PR descriptions. Whether a claim is live is decided by
     reading timestamps by eye — the fleet has no authoritative, machine-readable
     ledger. Two agents can both believe they hold an area.
  2. **The 24 h timeout is per *branch*, not per *area*.** It is computed from
     "the latest `CLAIM`/`LEASE` timestamp for a branch", so a lease is tied to a
     git branch name that may never be pushed. An agent that aborts before its
     first push strands a claim that is invisible to any mechanical check.
  3. **The workload plan (§8) is hand-maintained.** It is a large Markdown table
     that an agent must edit after every merge; the project has already paid for
     this — the git history contains **22 `docs(coord): refresh the queue`
     commits**, each a full PR that changes one table. The plan is a *derived*
     view, but it is stored as an *authored* document, so it drifts.
  4. **It is unverifiable.** No CI job can answer "are two agents on one area?"
     A comment-based claim cannot be a hard gate.
  5. **It adds ceremony that buys nothing.** Mandatory start/end check-ins on a
     hub issue, helper announcements, "adopt an orphaned PR" hand-wringing — all
     prose an agent must remember, none of it enforced.

  Meanwhile the *shape of the fleet* is: **1–10 agents**, each a stateless LLM
  session that may **stop mid-work or pause for an unbounded time** (a crash, a
  dropped connection, a run that never resumes), and human interaction must stay
  minimal. The system has to assume its agents are unreliable and must never
  block on one of them.

- **Options:**

  1. **Keep the comment protocol, tighten the prose.** Rejected: prose is exactly
     what fails when the reader is an unreliable agent, and it still cannot be a
     CI gate. It also keeps the hand-maintained §8 table and its churn.
  2. **A lock server / database / coordination service.** Rejected: it is a new
     single point of failure and a new dependency, and a dead agent could still
     hold a lock unless the service itself reaps it — reintroducing a "who owns
     the queue" role in operational form. The project's low-spec, no-heavy-deps
     stance (`AGENTS.md` §1c) also argues against it.
  3. **One coordinator agent that hands out work.** Rejected — this is precisely
     what ADR-0019 removed, and it fails the moment that agent pauses.
  4. **Trust git itself as the ledger: one ref per claim, updated by an atomic
     compare-and-swap, expiring on a TTL.** Chosen. Git already gives us the one
     primitive a lock needs — an atomic ref update that fails if the ref moved —
     and the remote is already the shared, always-on state the fleet agrees on.
     No new service, no new dependency, and expiry is a pure function of the
     clock, so a dead agent cannot hold anything.

- **Decision:** **Option 4.** Coordination state moves out of prose and into
  **git refs** on the shared remote, with a tiny CLI (`scripts/coord`) as the
  only interface.

  **1. The lease.** A claim is a lease stored as a git ref:

  ```
  refs/coord/leases/<area>
  ```

  The ref target is an empty commit whose message is one JSON line:

  ```json
  {"agent": "...", "area": "world", "issue": 157, "branch": "feat/world-x",
   "state": "claimed", "epoch": 1792050687, "ttl": 21600, "note": ""}
  ```

  - **One ref per leased area**, keyed by area alone — *not* by issue. The
    ref *is* the lock, so it must be keyed by what the lock protects. If it were
    `leases/<area>/<issue>`, two agents claiming different issues in one area
    would CAS two different refs and both win, silently breaking the area lock.
    Keying by area makes the single `push --force-with-lease` decide the area.
  - The **area is the lock**: a file has exactly one owning focus area
    (`docs/FOCUS_AREAS.md` §2), so two agents can collide on a file only by
    holding the same area. Locking the area is therefore sufficient and minimal.
  - **Claiming is `git push --force-with-lease`.** If two agents race, exactly one
    push wins; the loser is rejected and re-reads the ledger. This is a real
    compare-and-swap — the fleet needs no lock server to be correct.

  **2. The TTL.** Every lease carries `epoch + ttl`. Default TTL is **6 h**,
  capped at **24 h**. A lease past its expiry is **dead** and any agent may claim
  the area. Renewal (`coord renew`) is one ref update, so a healthy agent extends
  its lease cheaply; a **paused or dead agent cannot renew**, so its lease ages
  out and the area frees itself. **The fleet never waits on a missing agent** —
  this is the whole answer to "agents may stop mid-work or pause unreasonably
  long". A lease live but quiet for **> 12 h** is shown as **stale** on the board
  (the holder may still be working, but a `--takeover` is fair game).

  **3. The board is generated, not authored.** `docs/COORDINATION_BOARD.md` is
  rendered from the ledger by `scripts/coord board` and rewritten on every sweep.
  It is a **view**; it cannot drift, and it deletes the hand-maintained §8 table
  and its 22-refresh churn. Workload is the open-issue count, which GitHub already
  tracks — not a number a human has to keep current.

  **4. The sweep is the reaper.** A scheduled workflow
  (`.github/workflows/coordination.yml`, every 30 min) runs `coord sweep`: it
  deletes expired refs, syncs the `status:` labels and a convenience claim comment
  on GitHub, and regenerates the board. This is the mechanical replacement for
  "the coordinator reassigns work" and for every hand-written queue-refresh PR.

  **5. It is a hard gate.** `coord check` fails if two live leases collide on an
  area or an issue, and runs on every relevant PR/push plus in `ctest`. The
  protocol is now *verifiable*, which the comment protocol never was.

  **6. The ceremony is deleted.** No mandatory start/end check-ins, no hub
  bulletin board, no availability announcements. The lease *is* the check-in: a
  claim is visible to everyone the instant it is pushed, and its expiry is visible
  as a countdown. Human interaction is needed only for the genuinely human
  questions (product, licensing, a rule change), exactly as before.

- **Consequences:**
  - **A paused agent strands nothing.** Its lease expires on the clock; no human,
    and no peer, has to notice. This is the property the old protocol lacked.
  - **The protocol is machine-checkable**, so coordination regressions fail CI
    instead of relying on an agent reading timestamps correctly.
  - **Coordination overhead drops to three commands** (`claim`, `renew`,
    `release`) plus one read-only `status`/board view. The prose rulebook shrinks
    from a multi-document apparatus to one page plus the CLI.
  - **No new runtime dependency**: Python 3 (stdlib only) and `git`. CI already
    has both. Nothing heavy is added to the low-spec project (`AGENTS.md` §1c).
  - **A lease ref is global state on the remote.** It is cheap (one tiny commit
    per claim/renew) and invisible to a normal `git fetch`; clients that do not
    care never see it. Anyone can audit it with plain git:
    `git ls-remote origin 'refs/coord/*'`.
  - **Clock skew is the residual risk.** TTLs are hours and the tolerance is
    hours, so ordinary skew is harmless; a badly wrong clock is caught by
    `coord status` showing a nonsensical remaining time. Agents are told to
    trust the ledger's timestamps, not their own.
  - **The eight focus areas are unchanged.** The area is the lock, so the file
    map, overlap rules, and review policy in `docs/FOCUS_AREAS.md` §2/§4 all still
    apply verbatim; only §5.3 (claims and leases) is rewritten.
  - **Migration is lossless.** In-flight agents are imported from their existing
    `CLAIM:` comments by `scripts/coord migrate` (see
    `docs/COORDINATION_MIGRATION.md`); the legacy regexes stay in the tool so a
    claim posted by a not-yet-updated agent is still honoured.

## ADR-0022 — Enemies take cover when under fire

- **Status:** Accepted (2026-10-15)
- **Date:** 2026-10-15
- **Context:** Issue #120: enemies stand in the open and trade shots, so combat
  is a pure damage race. With line of sight now blocking fire (issue #62/#63),
  the pieces exist for a defensive move — a combatant under fire steps behind
  cover the shooter cannot see through, so the player must flank rather than
  out-DPS. Two questions had to be settled: **what counts as "under fire"**, and
  **where the cover state lives**. `core::Agent` is owned by the `focus: world`
  lane (`docs/FOCUS_AREAS.md` §2), so a new `AiState::TakeCover` there would be a
  cross-lane contract change for a tactical behaviour; the issue scopes the work
  to `Mission.{h,cpp}`.
- **Options:**
  1. **A new `AiState::TakeCover` on `core::Agent`.** Rejected for this change:
     it edits a world-owned header for a decision that is purely tactical, and it
     needs a cross-area contract PR (§4 Rule 3). The existing `AiState` values
     describe *what the agent is doing*, which "Engage while moving to cover"
     already covers.
  2. **Stateful cover in `Mission` (a member recording "this enemy is in
     cover").** Rejected: parallel per-agent state is easy to desync from the
     agent list, and the behaviour is a pure function of the current board.
  3. **Stateless cover, derived each think-tick from existing signals.** Chosen:
     the enemy is "under fire" if it was just hit (`Agent::hitFlash`) **or** the
     shooter is still firing (`shooter.gunfireTimer`, a 0.75 s window refreshed
     each shot). Cover is re-evaluated from `hasClearShot` every tick, so no new
     state is introduced and the decision is deterministic.
- **Decision:** **Option 3.**
  - `Mission::findCoverTile(index, attacker)` scans the eight neighbouring tiles
    and returns the walkable tile the attacker **cannot** see
    (`hasLineOfSight` false) that is furthest from the shooter; ties break by a
    fixed direction order. No RNG.
  - In `Mission::updateCombatantAI`, while engaged and under fire with usable
    cover, the enemy paths to that tile and returns (no fire that tick). It
    re-evaluates next think-tick: it stays if the tile still breaks the line, and
    slides to another covered neighbour or re-engages when the shooter regains
    the line.
  - Because cover relies on the shooter's gunfire timer as well as the hit
    flash, the behaviour survives the staggered think interval (0.4 s) during
    sustained fire, and it persists while the shooter keeps firing — the enemy is
    not dislodged by mere suppression, only by the shooter losing the line.
  - No `core::Agent` change: cover uses `moveTo`, `stop`, and the existing
    timers. `AiState` stays `Engage` while the agent is repositioning.
- **Consequences:**
  - Combat is now positional: an enemy with adjacent cover must be flanked to be
    finished, while an enemy in the open behaves exactly as before.
  - The behaviour is fully deterministic and RNG-free (AGENTS.md §10), so mission
    replays are unchanged.
  - Covered by `tests/test_mission.cpp`: `EnemyStepsIntoCoverWhenHit`,
    `EnemyHoldsCoverWhileStillUnderFire`, `EnemyWithoutCoverEngagesAsBefore`.
  - Only one step of cover is considered (the enemy does not path across the map
    to better cover); revisit if the AI needs richer positioning.

## ADR-0023 — Shield gadget: a Mission-local one-hit damage buffer

- **Status:** Accepted (2026-10-15)
- **Date:** 2026-10-15
- **Context:** Issue #211, roadmap Phase 3 ("gadgets — shield and scanner
  pending"). The medikit (ADR not needed; issue #88) established the pattern: a
  gadget's *charges* and *state* live on `Mission`, never on the frozen,
  World-owned `core::Agent` (`docs/FOCUS_AREAS.md` §2), so a tactical gadget
  needs no cross-lane contract change. The shield is the defensive counterpart —
  a combatant spends a charge to absorb the next incoming hit. The open
  questions were **where damage is intercepted** and **what a shield absorbs**.
- **Options:**
  1. **Intercept only in `resolveFire`'s primary-target path.** Rejected:
     explosive area damage (`applyAreaDamage`) and stray fire (`applyStrayFire`)
     would bypass the shield, so a shielded agent could still be hurt by the very
     hits the shield is meant to stop.
  2. **Give `core::Agent` a `shieldHp_` field and subtract there.** Rejected: it
     edits a world-owned header for a tactical gadget, and a damage-absorbing
     field on `Agent` is a bigger contract than the medikit precedent set.
  3. **Funnel every damage path through one `Mission::damageAgent` that consults
     a Mission-local shield flag.** Chosen.
- **Decision:** **Option 3.**
  - `Mission` gains `std::vector<int> shields_` (charges, sized to `agents_`,
    like `medikits_`) and `std::vector<bool> shieldUp_` (raised flag). Public
    API: `setShields`, `shields`, `activateShield`, `shieldUp`.
  - `activateShield(index)` spends one charge on a living combatant and raises
    the shield; it is a no-op for a civilian, a dead agent, an out-of-range
    index, or when a shield is already up (a charge is never wasted re-raising).
  - The private `Mission::damageAgent(index, amount)` is now the **single** place
    weapon damage reaches an agent. A raised shield absorbs the hit whole and
    drops (returns 0 dealt); otherwise `Agent::applyDamage` runs as before. All
    three call sites — `resolveFire`, `applyAreaDamage`, `applyStrayFire` — go
    through it.
- **Consequences:**
  - The shield is a **one-hit buffer** that covers ordinary, area, and stray
    damage alike; the hit after it lands normally.
  - No `core::Agent` change; the gadget is Mission-local and deterministic (no
    RNG), matching the medikit.
  - Covered by `tests/test_mission.cpp`: `ShieldAbsorbsTheNextHitThenDrops`,
    `ShieldAbsorbsAnExplosiveHit`, `ShieldWithNoChargeOrOnACivilianIsNoOp`,
    `ShieldDoesNotStackWhileAlreadyUp`.
  - The shield is **not yet surfaced to the player**: no UI binding or content
    field, mirroring the medikit at the time of its ADR. A `focus: input-ui`
    binding and a `focus: content` `shields` field are follow-ups (Rule 4).

## ADR-0024 — v1.0.0 scope: finish the 1993 clone first; defer everything else

- **Status:** Accepted (2026-10-15)
- **Date:** 2026-10-15
- **Directive:** a human maintainer asked (2026-10-15) that the project keep the
  agent fleet **small** to limit resource use, that a credible roadmap lead to a
  **finished clone** rather than accumulating "nice to have" features that are
  not in the original, and that the structure get us to a finished clone as fast
  as possible within legal bounds. This ADR records that directive as a rule. It
  supersedes the *implicit* scope of ADR-0009 (which fenced only the **visual**
  style); ADR-0009's pixel-art decision stands.

- **Context:** the project recreates the **gameplay of Syndicate (1993)**. It has
  made fast, high-quality progress (Phases 0–2 done, Phase 3 roughly half done,
  six playtest releases shipped). But there is **no written definition of
  "finished"** and **no feature fence**, so work drifts toward things the
  original did not have. Evidence from the repo:

  1. **No project-level Definition of Done.** `AGENTS.md` §9 defines "done" for a
     *pull request*, not for *v1.0.0*. Nothing states the end state, so no one
     can tell whether a proposed feature moves us toward it.
  2. **No scope fence.** The only fence (ADR-0009) is about **graphics**. Nothing
     says which *features* are out, so every "wouldn't it be nice" is a legal
     issue and the fleet's eight areas each pull toward their own backlog.
  3. **Measurable drift.** `focus: text` is an entire area (~310 lines of
     `core/i18n`, two ADRs — 0016 and 0020 — a German translation and ongoing
     coverage work) for **localisation**, which the 1993 original did not have.
     ADR-0004 proposes a **modding/scripting layer**, also not in the original.
     Modern quality-of-life (control groups, pause, zoom levels, fullscreen) and
     extra packaging lanes (Windows/macOS) consume capacity too. Each is
     defensible alone; together they are capacity **not** going to the clone.
  4. **The largest gap is unstarted and buried.** The **metagame** — the world
     map, taxation/income, research & development, equipment purchase, mission
     selection, and campaign progression — is *half of the original game's
     systems* and is **0% started** (no economy/research/world-map code exists).
     It sits at roadmap "Phase 4", behind more single-mission polish. A player
     cannot "finish" our game until the campaign exists.

  The failure mode this ADR prevents: a fleet of agents producing an excellent
  single-mission tactical demo **forever**, while the actual clone never lands,
  because nothing fenced the scope or ordered the work toward an end state.

- **Options:**

  1. **Leave scope open; let each area pursue its backlog.** Rejected: it is the
     status quo that produced the drift in point 3, and it makes "finished"
     unfalsifiable.
  2. **Freeze features and only polish what exists.** Rejected: the clone is
     missing its whole metagame half; polishing a demo is not finishing a clone.
  3. **Adopt an explicit, written scope fence for v1.0.0 = the original 1993
     feature set, a project-level Definition of Done, and an ordered roadmap that
     front-loads the missing systems.** Chosen: the only option that both bounds
     the work and aims it at the end state.

- **Decision:** **Option 3.**

  **1. v1.0.0 is defined as feature parity with the 1993 original.** v1.0.0 ships
  when a player can start a new corporation, run the full mission set against a
  world map with research, income and equipment, and reach an end state — using
  the original's **mechanics and systems**, original code and art, and nothing
  that was not in that game. The Definition of Done is written out in
  `docs/ROADMAP.md` and is the single answer to "are we done?".

  **2. The 1993 feature set is the scope.** In scope for v1.0.0 (each traced to
  the original): the four-agent squad and its orders; isometric city missions;
  the weapon families (pistol, uzi, shotgun, minigun, flamethrower, sniper,
  laser, gauss, time bomb) and **gadgets** (medikit, scanner, shield,
  recruiter/"persuade" device, performance drugs); **cybernetic upgrades**
  (legs/arms/chest/eyes); police and rival-syndicate enemies; civilians and
  collateral behaviour; **hijackable vehicles** (cars, trains) with mounted fire;
  a **destructible environment**; the mission objective set (assassinate,
  eliminate, persuade, escort/retrieve, destroy); and the **metagame** (world map
  with territories, taxation/income, research & development, equipment purchase,
  mission selection, campaign progression).

  **3. Explicitly out of scope for v1.0.0 — deferred to v2.x.x or a fork.** These
  are not forbidden forever; they are simply **not part of the clone** and must
  not consume v1.0.0 capacity:

  - **Localisation beyond English.** The original was English-only. v1.0.0 ships
    one language. The string-table *mechanism* may stay (it is already built and
    cheap), but **no new translation work** (more locales, translation coverage
    guards) is v1.0.0 work.
  - **Modding / scripting layer** (ADR-0004): defer. Data-driven content stays;
    an embedded language does not land for v1.0.0.
  - **Modern quality-of-life** not in the original (extra control schemes,
    save-anywhere, difficulty options beyond the original's, UI modernisation).
    Keep only what the original had.
  - **Extra platforms beyond Linux.** Linux is the v1.0.0 target (ADR-0017);
    Windows/macOS remain best effort and get no new v1.0.0 work.
  - **Multiplayer**, level editors, and any new game mode the original lacked.

  **4. The fleet stays small by default.** The coordination scheme supports 1–10
  agents (ADR-0019/0021), but **capacity is not a goal**. Start an agent only for
  work on the critical path to the Definition of Done; work on an out-of-scope
  item is **not** a reason to start an agent. A small fleet (roughly 1–4) is the
  normal target; fan out only when a phase genuinely parallelises. This is a
  resource policy, not a coordination rule: it changes *how many* agents run, not
  *how* they coordinate.

  **5. The roadmap is ordered by dependency toward the end state.** The metagame
  is promoted ahead of further single-mission polish, because it is the largest
  missing block and other systems (research, purchase, campaign) depend on it.

- **Consequences:**

  - `docs/ROADMAP.md` is rewritten: a **Definition of Done**, an explicit **"Not
    in v1.0.0"** fence, and phases reordered so the metagame is the next major
    milestone rather than the last.
  - `AGENTS.md` §1 points at the fence; §9 gains the **project-level** Definition
    of Done; a **fleet-size policy** is added (§1d).
  - `docs/FOCUS_AREAS.md` records that localisation is not on the v1.0.0 critical
    path, so `focus: text` capacity is not spent on new locales.
  - Open issues that are out of scope (further i18n coverage, modding) are
    labelled as deferred; new out-of-scope issues get a defer label rather than a
    `focus:` claim.
  - **Legal position is unchanged** (`docs/LEGAL.md`): recreating the original's
    *mechanics and systems* with original code, art, and names is the whole
    project; the fence narrows *what we build*, it does not license copying.
  - A v2.x.x/fork line may pursue the deferred items — this ADR only says they
    are not v1.0.0.

## ADR-0025 — Coordination hardening: reachable staleness, reconciled labels, a never-idle ladder

- **Status:** Accepted (2026-10-15)
- **Date:** 2026-10-15
- **Context:** A live audit of the running fleet (75 PRs merged in one day, every
  area active, `coord check` green, no collisions) confirmed the flat lease model
  (ADR-0019/0021) works. It also found three defects where the written protocol
  and the running system disagreed, plus one structural gap:

  1. **The "stale" signal was unreachable.** `STALE_AFTER` was **12 h** but
     `DEFAULT_TTL` was **6 h**, so a lease expired *before* it could ever be
     flagged stale. `docs/COORDINATION.md`, `docs/FOCUS_AREAS.md` §5.3, and
     ADR-0021 all promised a "live but quiet > 12 h" holder on the board; in
     practice a stalled holder simply vanished at the TTL and was never shown as
     stale. A documented safety net that cannot fire is worse than none: agents
     trusted it instead of checking the clock.
  2. **Cross-area requests were undiscoverable.** Rule 4 allowed a request as a
     **PR comment**, which is invisible to the lane that must act on it. A content
     PR (#235) sat as a draft for hours, "blocked on a tactical vet", with no
     `focus:` label, no reviewer request, and no issue — so the tactical lane
     never saw it. A silent block is indistinguishable from a dead agent.
  3. **The `status:` label mirror drifted.** `coord release` deleted the lease ref
     but never cleared the label, and the sweep only synced *live* leases, so a
     released or closed issue (e.g. #222) kept `status: claimed` indefinitely.
  4. **The fleet could run out of work.** With the metagame lane drained and no
     next Milestone B issue filed, a free area had nothing claimable — the one
     stop condition the flat model does not itself fix. "Always something to do"
     was an assumption, not a mechanism.

- **Options:**

  1. **Leave it; the model is "good enough".** Rejected: (1) and (2) are silent
     failures that cost real throughput and hide stalled work.
  2. **Add a coordinator to hand out work.** Rejected — reintroduces exactly what
     ADR-0019/0021 removed, and fails when that agent pauses.
  3. **Fix each defect in the mechanism itself, and make "next work" a command.**
     Chosen: keep coordination flat and machine-checked, and make the two failure
     modes (unreachable staleness, empty backlog) impossible to reach silently
     rather than relying on an agent to notice.

- **Decision:** **Option 3.** Concretely:

  - **`STALE_AFTER` is now 3 h**, strictly below `DEFAULT_TTL` (6 h), so a normal
    lease can reach staleness while still live. A test asserts the invariant
    (`STALE_AFTER < DEFAULT_TTL`) so it cannot silently break again.
  - **Rule 4 requests must be discoverable**: filed as an issue labelled
    `focus: <area B>` (and, when a PR is blocked, with B added as a reviewer),
    never as a bare PR comment.
  - **The label mirror is reconciled**: `coord release` clears the labels
    best-effort against a real GitHub remote, and `sweep --gh` clears a lease-set
    `status: claimed` on any **open** issue with no live lease behind it. It leaves
    `status: blocked` / `status: needs-review` alone (they also mark human
    questions and Rule 4 requests, which have no lease) and leaves **closed**
    issues untouched — history stays as-is. The ledger stays the single source of
    truth.
  - **`scripts/coord next`** walks a fixed ladder and **never prints nothing**:
    finish a held lease → claim a free critical-path area's issue → claim any free
    area's issue → file a new issue from the roadmap when the backlog is empty →
    otherwise review an open PR you did not author. The fleet's stop condition
    becomes "add work", never "wait".

- **Consequences:**

  - A stalled holder is now *visible* (stale on the board at 3 h) before its lease
    dies at 6 h, so peers can take over deliberately instead of only after expiry.
  - Blocks are found by the lane that can clear them, without a relay.
  - The `status:` labels can no longer disagree with the ledger for longer than one
    sweep.
  - **An idle agent always has a next action**, and when none is claimable the
    answer is to **create work** (file the roadmap item) or **review**, so a small
    fleet (ADR-0024) never spins down for lack of a queue.
  - `coord` gains one read-only command (`next`); the overhead stays three
    commands (`claim`, `renew`, `release`) plus reads (`status`, `next`, board).
  - **No new dependency, no coordinator, no lock server** — the model is unchanged;
    only the edge cases are closed.
  - **The transition is in place, so it is a no-op for in-flight agents.** The
    lease refs, the three commands, and the board format are unchanged; a live
    lease is never revoked. `stale` is display-only, so lowering `STALE_AFTER` to
    3 h cannot cost a holder its area — `claim` still needs `--takeover` to
    displace a live lease. See `docs/COORDINATION.md` §9.


## ADR-0026 — `coord next` offers only claimable work, blockers first

- **Status:** Accepted (2026-10-15)
- **Date:** 2026-10-15
- **Context:** ADR-0025 added `coord next` so an idle agent always has a next
  action. It read **every** open issue with a `focus:` label and offered the
  newest. Two frictions followed once the fleet filed real work:
  1. **Unclaimable issues were offered.** A `status: blocked` issue (waiting on
     another area), a `question` (a human decision), and a `deferred: v2` issue
     (out of v1.0.0 scope, ADR-0024) all carry a `focus:` label, so `next` would
     route a fresh agent straight to work it could not start — a wasted cycle and
     a second agent parked on the same block.
  2. **Blockers were offered last.** Within an area the newest issue won, so a
     **Rule 4 request** (`status: needs-review`) that another lane was *waiting*
     on sat behind newer work that unblocks no one. Clearing a blocker unblocks a
     peer; starting fresh work does not.

- **Options:**
  1. **Leave it.** Rejected: the whole point of `next` is to remove the decision,
     and a wrong answer is worse than none — it burns a cycle and hides the block.
  2. **Add a coordinator to triage.** Rejected — reintroduces authority
     (ADR-0019/0025).
  3. **Encode the policy in the mechanism.** Chosen: `next` filters unclaimable
     issues and orders a `needs-review` blocker first, so no agent has to judge.

- **Decision:** **Option 3.** `_open_issues_by_area` (the source `next` reads):
  - **skips** any issue labelled `status: blocked`, `question`, or `deferred: v2`
    (a new `NOT_CLAIMABLE_LABELS` set);
  - **marks** a `status: needs-review` issue a *blocker* and orders it ahead of
    plain work within its area, newest first within each rank.

  `next` then offers a waiting blocker in **any** free critical-path area before
  plain work in the first one: clearing a blocker unblocks a peer, so it outranks
  starting fresh work even when the fresh work sits earlier on the critical path.
  No new command, no new label, no schema change: it narrows what an existing
  read offers.

- **Consequences:**
  - An idle agent is never steered to work it cannot start, and never past a
    blocker a peer is waiting on — including across areas.
  - The `focus:` label stays the sole routing key; claimability and blocker status
    are read from the labels already in use (`AGENTS.md` §3), so there is nothing
    new to maintain.
  - A blocked issue is still *visible* on the board and in the ledger; it is only
    excluded from the *claim* suggestion.

## ADR-0027 — A squad loadout is applied at mission load, in `core/data`

- **Status:** Accepted (2026-10-15)
- **Date:** 2026-10-15
- **Context:** Milestone B's *mission selection & deployment* records which four
  slots to send and their bought weapons/gadgets (`Campaign::selectMission`), but
  a mission still loaded its own authored player `AgentSpec`s, so "buy a loadout
  → deploy → fight with it" never happened (docs/METAGAME.md §7, request R1).
  The loop was open at its last step. Three questions had to be settled:

  1. **Where does the override live?** The mission's agents are `core::Agent`
     (owned by `focus: world`); the loader is `core/data` (`focus: content`);
     deployment is `core/economy` (`focus: metagame`). A loadout touches all
     three, so its home decides which area's contract it extends.
  2. **What shape is a loadout?** A resolved `Weapon` (needs the catalogue at the
     call site) or a set of **ids** resolved by the loader?
  3. **How strict is a bad id?** Silently keep the default, or fail the load?

- **Options:**
  1. **Put the override on `Agent`/`Mission` and pass `core::Weapon`s.** Rejected:
     it makes `core/sim` the place deployment logic lives, and a caller must hold
     a `WeaponCatalogue` to build a loadout — the exact coupling R1 wanted to
     avoid.
  2. **A new `core/economy` deploy step that mutates the mission.** Rejected: the
     metagame would then edit mission agents directly, inverting the dependency
     (`economy` already sits above `sim`) and duplicating the weapon-id join.
  3. **A data-only `PlayerLoadout` of catalogue ids, applied by the mission
     loader.** Chosen: `core::PlayerLoadout` (new, in `core/sim`, header-only,
     no `Weapon`) names a `weaponId`/`gadgetId` per slot; `applyLoadout(...)` in
     `core/data/MissionData` resolves the ids against the shared
     `WeaponCatalogue` and the tactical gadget vocabulary and writes the mission's
     player agents. The `core/economy` → `core/data` direction already exists
     (the metagame loads content), so no new dependency edge is created.

- **Decision:** **Option 3.**
  - `PlayerLoadout { std::vector<LoadoutSlot> slots; }` and
    `LoadoutSlot { std::string weaponId, gadgetId; }` live in
    `src/core/sim/PlayerLoadout.h`. They carry **ids only**, so `core/sim` stays
    free of the content loader and there is no include cycle.
  - Slot `i` maps to the i-th **player** agent in authored order, so the mapping
    is independent of enemy/civilian interleaving. A slot past the last player
    agent is ignored, so a four-slot loadout is safe against a smaller squad.
  - `applyLoadout(loadout, mission, weapons, error)` is the single join point. An
    empty id keeps the authored default (a missing loadout changes nothing,
    AGENTS.md §1b). An **unknown** id is a content error — it returns false and
    sets `error`, so a typo cannot silently deploy the wrong weapon (the same
    strictness as an unknown `weaponId`/`agentId` in a mission file).
  - The gadget vocabulary (`gadgetChargesForId`: "medkit" | "shield") lives in
    `PlayerLoadout.h`, **not** in `core/economy`, so the loader stays below the
    metagame. It matches the `kind: "gadget"` items in the equipment catalogue;
    one charge per gadget, because a medikit heals once and a shield absorbs one
    hit.

- **Consequences:**
  - The v1.0.0 loop closes at its last step: a bought loadout reaches the
    deployed agents, and `focus: metagame`'s deploy issue (#312) can hand one
    over. The engine-side wiring (`Game`/`CampaignScreen`) is a separate
    follow-up in that area, not this contract.
  - The interface is frozen: `PlayerLoadout`/`LoadoutSlot` and `applyLoadout` are
    the surface `focus: metagame` builds against (FOCUS_AREAS §2.1).
  - Adding a gadget means adding one arm to `gadgetChargesForId` and one entry to
    the equipment catalogue — a small, local change, not a schema change.

## ADR-0028 — Scanner and performance drugs: presentation-only reveal vs. a real stat buff

- **Status:** Accepted (2026-10-15)
- **Date:** 2026-10-15
- **Context:** Milestone A's gadget list (docs/ROADMAP.md) still had two unbuilt
  items after the medikit, shield, and recruiter: a **scanner** (reveal
  enemies/terrain in a radius) and **performance drugs** (a temporary stat boost).
  Both are per-agent, single-use gadgets with the same activate/consume shape as
  the shield (`Mission::activateShield`). Two questions had to be settled:

  1. **Where does the state live?** On `core::Agent` (owned by `focus: world`) or
     on the `Mission` alongside the medikit/shield counters?
  2. **What does each gadget actually change?** In particular, does a scanner
     reveal information the *simulation* then uses, or is it presentation-only?
     And how does a temporary accuracy buff reach a stat that lives on `Weapon`,
     not `Agent`?

- **Options:**
  1. **Put charges on `Agent`.** Rejected: it would extend the frozen `Agent`
     contract (FOCUS_AREAS §2.1) and cross into `focus: world` for a purely
     tactical feature; the medikit and shield already keep their counters on the
     `Mission` for exactly this reason (ADR-0023).
  2. **Make the scanner change AI targeting (revealed enemies become targetable
     past sight range).** Rejected for v1.0.0: it would let a presentation gadget
     alter combat outcomes and determinism, and the original scanner is an
     information tool, not a targeting override. The reveal is therefore
     **presentation-only**: `scanTargets` reports the marked enemies for the view
     to draw, and the sim never reads it.
  3. **A drug buff that multiplies `Agent::speed` in place, and the weapon's
     accuracy at the fire site.** Chosen: speed is the one stat that lives on
     `Agent`, so the dose multiplies it on activation and divides it back out on
     expiry in `Mission::update`; accuracy lives on `Weapon`, so the buff scales
     the base hit chance inside `resolveFire` (clamped to 1.0) without mutating
     the shared weapon.

- **Decision:** **Option 3.**
  - Both gadgets keep their state on the `Mission`, in vectors sized to `agents_`
    and grown by `addAgent` (like `medikits_`/`shields_`):
    `scanners_`/`scannerTimer_` and `drugs_`/`drugsTimer_`. No `Agent` change.
  - `activateScanner(index)` spends a charge and starts a `kScannerPulseSeconds`
    pulse; `scanTargets(index)` lists the living enemies within `kScannerRadius`
    tiles while the pulse runs. It is **deterministic and RNG-free**, and the
    simulation never consumes the marks.
  - `useDrugs(index)` spends a dose and starts a `kDrugDurationSeconds` buff:
    movement speed is multiplied by `kDrugSpeedMultiplier` (restored exactly on
    expiry) and the base hit chance by `kDrugAccuracyMultiplier` (clamped to 1.0)
    in `resolveFire`. Fire *rate* is unchanged, so the buff cannot multiply
    damage-per-second by both factors.
  - Both are no-ops for a civilian, a dead agent, or when already active (a
    charge/dose is never wasted), mirroring the shield.
  - Balance constants (`kScannerRadius`, `kScannerPulseSeconds`,
    `kDrugDurationSeconds`, the two multipliers) live in `Mission.cpp` next to the
    medikit constants, until a data format is fixed (ADR-0003), exactly as the
    medikit does today.

- **Consequences:**
  - Milestone A's gadget list is complete in `core`; the ROADMAP item can be
    ticked. The scanner's on-screen ping is `focus: render`'s follow-up (issue
    #218), filed as a Rule 4 request — the core side is frozen here.
  - The loadout vocabulary (`gadgetChargesForId`, ADR-0027) gains two arms,
    `"scanner"` and `"drugs"`, so a bought scanner/drugs deploys through the same
    path as the medkit/shield. The matching `kind: "gadget"` catalogue entries in
    `assets/data/world/equipment.json` are a `focus: metagame` follow-up.
  - A scanner does not change combat balance; a drug buff does, and is bounded to
    a single window per dose. Both stay deterministic, so missions remain
    replayable.

## ADR-0029 — Campaign progression: regions are attacked from the frontier

- **Status:** Accepted (2026-10-15)
- **Date:** 2026-10-15
- **Context:** Milestone B's Definition of Done (`docs/ROADMAP.md`) requires the
  loop to **progress through the mission set and reach an end state**, and the
  shipped campaign's win condition is `own-all-territories`. The contract's
  `Campaign::selectMission` (`docs/METAGAME.md` §4.5) only accepted a
  **player-owned** territory, and the shipped `world.json` put a `missionId` on
  **one** territory (id 0), which was already player-owned. Every neutral region
  therefore had no mission and no way to be selected, so no win could ever claim
  a region: the campaign was **unwinnable**, and the "progress → end state"
  half of the DoD was unreachable. Nothing failed at load, so the gap only showed
  in a playtest. A second, structural obstacle: `WorldMap::validate` rejected any
  `missionId` shared by two territories, which forced one authored mission per
  region — and mission content belongs to `focus: tactical`, not metagame.

- **Options:**
  1. **Author a distinct mission for every region.** Rejected: mission content is
     Tactical's area (`docs/FOCUS_AREAS.md` §2), so it is a cross-area dependency
     for a metagame fix, and the original **reuses city maps** across regions
     anyway — a 1:1 map-to-mission rule is less faithful, not more.
  2. **Let any region be attacked regardless of adjacency.** Rejected: it removes
     the map's only strategic structure (why take the Docks before the Sprawl?)
     and is not how the original plays; ownership is supposed to spread outward.
  3. **Attack from the frontier.** Chosen: a region is deployable when the player
     already owns it or holds an **adjacent** region; a win claims it. Ownership
     grows inward from the border, the map is winnable, and a repeated `missionId`
     is allowed so a small mission set covers a larger map.

- **Decision:** **Option 3.** In `core::Campaign`:
  - a new `bool canDeployTo(TerritoryId) const` returns true iff the territory
    has a non-empty `missionId` **and** is player-owned **or** adjacent to a
    player-owned territory;
  - `selectMission` gates on `canDeployTo` (it no longer requires ownership
    directly), so a neutral frontier region is a valid attack target;
  - `WorldMap::validate` no longer requires `missionId` to be unique — several
    regions may share one mission.
  The shipped `assets/data/world/world.json` gives each neutral region a
  `missionId` (reusing the two shipped missions), so `own-all-territories` is
  reachable. The map screen shows the selected region's `STATUS` as
  `ATTACK READY` / `NOT REACHABLE`, and `CampaignScreen::selfTest` now **wins by
  attacking**, so unwinnable data fails the `game_campaign` guard rather than a
  playtest.

- **Consequences:**
  - The metagame loop reaches an end state with the data that ships; the
    "progress" step of the DoD is no longer blocked by a content dependency.
  - A region behind other neutrals is correctly **not** attackable until a
    neighbour falls, which gives the map a front line for free.
  - Real per-region mission content is still Tactical's to author (cross-area
    request); until then, regions share missions, which the original also did.
  - A campaign that cannot be won (a neutral region with no `missionId`, or one
    walled off from any player territory) is now a **test failure**, not a
    silent dead end.

## ADR-0030 — A cross-area block declares `blocked-by:` and clears itself

- **Status:** Accepted (2026-10-16)
- **Date:** 2026-10-16
- **Context:** A cross-area block is declared by hand as `status: blocked` on the
  dependent issue (`docs/COORDINATION.md` §3). Nothing cleared it when the
  blocker landed, so the issue stayed unclaimable forever and a **fresh** agent
  was never routed to it — `next` skips `status: blocked` by design (ADR-0026).
  Observed: #312 was filed blocked on tactical R1 (#311); #311 merged and closed,
  yet at the next cycle #312 was still blocked and `next` offered a different
  tactical issue instead. The metagame agent only resumed because it re-read its
  own tracker by hand; a new process would not have. `_reconcile_status_labels`
  could not help: it clears only `status: claimed`, because `status: blocked` is
  also the human-question convention (§5.2), which has no lease and must not be
  touched.

- **Options:**
  1. **Clear on closure by scanning prose.** Rejected: the block is a sentence
     today, so "does this body reference #311?" matches any passing mention, and
     a false positive clears a live block.
  2. **Document the manual step.** Rejected: it relies on an agent remembering —
     the exact failure just observed.
  3. **Make the dependency machine-readable.** Chosen: the dependent issue's body
     carries `blocked-by: #<n>`, and the sweep clears `status: blocked` once every
     referenced issue is closed. Self-clearing, no new authority, no new label.

- **Decision:** **Option 3.** A cross-area block is declared as `status: blocked`
  **plus** a `blocked-by: #<n>` line in the issue body (several numbers per line
  allowed). The scheduled `sweep` reads the open-issue set once and, for each open
  issue carrying `status: blocked` whose `blocked-by:` refs are **all closed**,
  removes the label (`scripts/coord`, `_clear_resolved_blocks`). Two guard rails
  keep the scope as narrow as the existing reconciler:
  - an issue with **no** `blocked-by:` refs is never touched, so a §5.2 human
    question (which also carries `status: blocked`) is safe;
  - if GitHub cannot be read the sweep clears **nothing** — an unknown open set is
    not an empty one, so a failed read never drops a live block.

- **Consequences:**
  - A block lifts itself the cycle after its last blocker closes, so the issue is
    claimable again and `next` routes to it with no human or agent edit.
  - Declaring a block gains one required line; the block stays *visible* (label +
    board) while it is real, and the reason is now greppable rather than prose.
  - The human-question convention is unchanged: it carries no `blocked-by:` line,
    so the sweep ignores it, exactly as it ignores a Rule 4 request today.
  - A block whose blocker never closes still waits forever by design — the sweep
    only ever *lifts* a block, never creates or extends one.
## ADR-0031 — Cybernetics apply as one-shot stat multipliers at mission load

- **Status:** Accepted (2026-10-15)
- **Date:** 2026-10-15
- **Context:** Milestone A's last unstarted item is **cybernetic upgrades**
  (legs/arms/chest/eyes) — permanent, passive stat changes bought in the
  metagame (docs/ROADMAP.md). `EquipmentKind::Cybernetic` and a catalogue entry
  (`targeting-implant`) already exist, but nothing applied a cybernetic to a
  combat stat, so it is purchasable and inert. Three questions had to be settled:

  1. **Where does a cybernetic's effect live?** The catalogue item is only
     `{id, kind, name, cost}`; the modifier (how much speed/accuracy/health/sight
     it grants) needs a home.
  2. **How is it represented — as a delta or a multiplier?** A flat `+2 speed`
     or a `×1.2`? And what does it modify: the agent's base stat, or a separate
     buff layer?
  3. **Perception had no field.** Accuracy lives on `Weapon`, health and speed on
     `Agent`, and there was **no sight-range field at all** — so "eyes" has
     nothing to change. `Agent` is owned by `focus: world` (FOCUS_AREAS §2.1), so
     this needed a world contract, not a tactical edit to `Agent`.

- **Options:**
  1. **Put the modifiers on `Agent`/`Weapon` and apply them there.** Rejected:
     an upgrade is metagame content, and adding four modifier fields to the
     frozen `Agent`/`Weapon` contracts (Rule 3) for a passive, load-time-only
     change would bloat the interfaces every other area builds against.
  2. **A separate runtime buff layer the sim consults each tick** (mirroring the
     drug buff). Rejected: a cybernetic is **permanent**, so a per-tick layer is
     needless per-frame work on the critical path (AGENTS.md §1b) and a second
     path for every stat to flow through.
  3. **A data-only `CyberneticEffect` of multipliers in `core/sim`, applied once
     by `Mission::applyCybernetic` at mission load, with perception delegated to
     the per-agent `Agent::sightRange()` that `focus: world` landed for this
     upgrade (#337).** Chosen: it matches the loadout pattern (`PlayerLoadout` is
     data-only, applied once by `applyLoadout`, ADR-0027), keeps the `Agent`
     modifier surface to the single field World authored, and puts the upgrade
     logic where the sim already owns the agents.

- **Decision:** **Option 3.**
  - `CyberneticEffect` (`src/core/sim/Cybernetic.h`, header-only, engine-free)
    holds four **multipliers** — `speedMultiplier`, `accuracyMultiplier`,
    `healthMultiplier`, `sightMultiplier` — all defaulting to 1.0. A multiplier
    scales with the agent's authored stat, so a chest upgrade raises a 100-health
    agent and a 200-health one proportionally.
  - `cyberneticEffectForId(id, out)` is the closed vocabulary of the equipment
    catalogue's `kind: "cybernetic"` items: `legs` (speed), `arms` (accuracy),
    `chest` (health), `eyes` (perception), and the already-shipped
    `targeting-implant` (accuracy). An unknown id returns false, so a typo is
    rejected rather than silently deploying an un-upgraded agent.
  - `Mission::applyCybernetic(index, id)` applies the effect once: multiplies
    speed, multiplies max health (via `Agent::setMaxHealth`, which also fills the
    extra health, so the upgrade is a clean gain not a wound), multiplies weapon
    accuracy **clamped to 1.0** (an upgrade must never make a shot certain), and
    multiplies sight range. Deterministic; no RNG. It is a no-op for a civilian,
    a dead agent, an unknown id, or an invalid index.
  - **Perception** multiplies the agent's per-agent `Agent::sightRange()`
    (default `kDefaultSightRange`, the world contract landed for this upgrade in
    #337); `Mission::seesTarget` reads it, so an eyes upgrade measurably extends
    the range at which a combatant acquires a target — a real behavioural effect,
    not just a getter. `Mission::sightRange`/`setSightRange` are thin delegators
    for mission setup and tests.
  - `LoadoutSlot` gains a third data-only id, `cyberneticId`, and `applyLoadout`
    applies it through the same strict path as a weapon/gadget: an unknown id is
    a content error.

- **Consequences:**
  - Milestone A's cybernetics item is done: a cybernetic measurably changes its
    stat, is data-driven (one arm here + one catalogue entry, no schema change),
    and is unit-tested.
  - The modifier data lives in `core/sim` (Tactical) until a data file format for
    cybernetic modifiers is fixed (ADR-0003); moving it to `assets/data` is then
    a small, local change.
  - `focus: metagame` must add the `legs`/`arms`/`chest`/`eyes` catalogue (and
    research) entries **and** map a bought cybernetic to
    `LoadoutSlot::cyberneticId` in `Campaign::selectedLoadout`, which today
    deliberately skips cybernetics as "not a loadout item". Until that lands, a
    cybernetic is fully usable via `applyLoadout` but not yet purchasable through
    the campaign UI (Rule 4 request filed on #313).
  - The interface is additive and frozen: `CyberneticEffect`/`cyberneticEffectForId`,
    `Mission::applyCybernetic`/`sightRange`/`setSightRange`, and
    `LoadoutSlot::cyberneticId` are the surface the metagame builds against.

## ADR-0032 — `Mission` owns vehicle policy; the entity stays policy-free

- **Status:** Accepted (2026-10-15)
- **Date:** 2026-10-15
- **Context:** Milestone A's hijackable vehicles reached a fork. `focus: world`
  landed `core::Vehicle` (#320): position, A* movement (`driveTo`), health /
  destruction, single-agent occupancy (`hijack`/`eject`/`driver`), and a mounted
  `Weapon` (`canFire`/`beginFireCooldown`). The entity is **deliberately
  policy-free** — it records *who* holds the wheel and *what* the driver may
  fire, but decides nothing about legality or damage. The follow-up (#318,
  tactical) had to give the feature a home: who may hijack, how a drive order is
  gated, and where mounted fire lands. Two kinds of question had to be answered,
  and neither should bloat the frozen entity:

  1. **Authority:** does `Vehicle` grow the policy, or does `Mission`?
  2. **Outcomes:** does a vehicle's gun bypass the agent damage funnel
     (`Mission::damageAgent`, where a shield absorbs a hit, ADR-0028/0031), or go
     through it? And can an agent's weapon destroy a vehicle at all?

- **Options:**
  1. **Add hijack/order/damage policy to `core::Vehicle`.** Rejected: the entity
     is frozen and unit-tested on its own, and it has no access to the agent list
     or the grid's occupants — policy there would need a back-reference to
     `Mission`, an inversion of ownership, and would duplicate combat rules.
  2. **A new `VehicleController` layer beside `Mission`.** Rejected: it would own
     a second copy of the agents, the grid, and the RNG, and the sim would have
     two owners of the same world — exactly the duplication the boundary avoids.
  3. **`Mission` owns vehicle policy; the entity stays policy-free.** Chosen: it
     mirrors how `Mission` already owns all agent combat policy over the pure
     `Agent`, keeps one damage funnel, and leaves `core::Vehicle` untouched.

- **Decision:** **Option 3.**
  - `Mission` tracks vehicles (`addVehicle`/`vehicles()`) and a parallel
    `vehicleTargets_` vector (an explicit mounted-fire target per vehicle, or -1
    for auto-acquire), kept in step exactly as `medikits_`/`shields_` are.
  - **Hijack (`orderHijack(vehicle, agent)`)**: legal only for a living,
    non-driving **combatant** within `kHijackRadius` (1.5) tiles of the vehicle's
    tile, and only for an intact, undriven vehicle. On success the agent becomes
    the driver and its position is **folded onto the vehicle's** — the driver
    rides along, and `syncDrivers` keeps the two identical each update. An
    explicit order (not auto-on-enter) because it matches the player's
    move/attack orders and keeps the outcome deterministic and surprise-free.
  - **Drive orders (`orderDrive`)**: gated on an occupied, intact vehicle (its
    driver issues the order), then delegated to `Vehicle::driveTo`. An empty or
    wrecked car ignores a drive order.
  - **Mounted fire (`resolveVehicleFire`)**: a vehicle's own gun honours an
    explicit `orderVehicleAttack` target or auto-acquires the nearest living
    enemy, and uses the same range + line-of-sight rules as an agent. Its damage
    goes through **`damageAgent`/`applyAreaDamage`**, so a shield still covers
    the hit; killing a player/enemy through a mounted weapon updates the same
    kill tallies, and a stray mounted shot can still panic / kill civilians.
  - **A driver does not also fire a personal weapon or act on its own**
    (`isDriving` skips it in `updateAI` and `resolveFire`): the mounted gun is
    its only weapon while at the wheel, so there is exactly one fire source per
    vehicle and no double-damage.
  - **Agent-vs-vehicle damage**: an agent's personal weapon never targets a
    vehicle (vehicles are not in the agent target loop). A vehicle is damaged by
    **explosives**: `applyAreaDamage` funnels blast damage into a private
    `damageVehicle`, and a vehicle **wrecked by a blast detonates**, hurting
    agents within `kVehicleWreckRadius` for a fraction of its maximum health and
    breaching destructible walls in that radius (`breachTilesInBlast`, #411).
    That makes a car cover that can backfire, and keeps both entity kinds on one
    damage funnel each.
  - `Vehicle::applyDamage` still stops a wreck and ejects the driver; `Mission`
    owns what the agent does next (nothing until the next order).

- **Consequences:**
  - `core::Vehicle` is unchanged — the policy-free boundary holds, and the entity
    keeps its own tests.
  - Milestone A's vehicles item is now reachable in play: `Mission` owns the
    policy, so Render and Input/UI have something to read and drive (their
    follow-ups). The interface is additive and frozen:
    `addVehicle`/`vehicles`, `orderHijack`/`ejectVehicle`/`orderDrive`/
    `orderVehicleAttack`, and `vehicleDriver`/`vehicleOf`/`isDriving`.
  - Vehicle stats remain in code (`makeCar`/`makeTrain`) until
    `assets/data/vehicles.json` lands (`focus: content`, #319, golden rule 7);
    moving them to data is then a local change.
  - The wreck-detonation rule is a balance constant in `core/sim`
    (`kVehicleWreckRadius`/`kVehicleWreckDamageScale`) until a data format is
    fixed (ADR-0003).
  - Follow-ups: render (draw vehicles + the wreck) and input/UI (hijack/drive
    keys) are unblocked once this lands; a driver's queued-move and attack orders
    are currently not offered (the view drives the vehicle, not the agent).

## ADR-0033 — Flat coordination: durable handoff notes and honest failure reporting

- **Status:** Accepted (2026-10-15)
- **Date:** 2026-10-15
- **Amends:** ADR-0021 / ADR-0025. The flat, no-coordinator decision and the
  git-ref lease are **kept unchanged**; this adds the two things a flat fleet
  still lacked when an agent stops mid-work.

- **Context:** A review of the fleet's coordination after several cycles found
  the model sound but two residual sources of friction, both of which cost work
  or waste agent cycles without any human in the loop:

  1. **A lease is scoped to *now*.** It is deleted on `release` and ages out on
     its TTL, so a fact the *next* process needs — "push auth is broken, run `gh
     auth setup-git`", "the low-spec size cap is platform-owned, file Rule 4,
     do not trim the content" — had **nowhere durable to live**. The only
     alternatives were an issue (heavyweight: it must be filed, labelled,
     triaged, and closed) or a PR comment (invisible to the next process, which
     does not read the previous PR). An agent that stopped mid-work stranded its
     findings, and the next agent re-discovered them the hard way.
  2. **A credential failure was reported as a lost race.** `_commit_leases`
     turned *any* failed `git push` into "could not publish … the ledger moved
     under us", and `claim` then re-read the (unchanged) ledger and blamed a
     phantom concurrent writer. An agent with stale push credentials was sent to
     `coord status` to inspect state that had not changed, instead of being told
     to fix auth. The diagnosis was actively wrong, which is worse than terse.

  The fleet is **1–10 agents**, each a stateless session that may stop mid-work
  or pause for an unbounded time; human interaction must stay minimal
  (ADR-0021's framing, unchanged). Any fix must add **no** new service, role, or
  lock, and must not require an in-flight agent to change anything.

- **Options:**

  1. **File an issue for every cross-cycle fact.** Rejected: it turns a note
     into a tracked work item that must be labelled, triaged, and closed, which
     is exactly the ceremony ADR-0021 deleted, and it pollutes the open-issue
     count that `coord next` uses as workload.
  2. **A hub issue / bulletin board for handoffs.** Rejected: reintroduces the
     hand-maintained, drift-prone, single-writer artifact ADR-0021 removed.
  3. **Do nothing; rely on the PR description.** Rejected: the next process
     does not read the previous cycle's PR, so the fact is effectively lost.
  4. **A durable per-area note log stored as git refs, plus honest push
     errors.** Chosen. It reuses the exact primitive the lease already proved:
     a git ref on the shared remote, keyed by area, with no server and no lock.

- **Decision:** **Option 4**, in two parts.

  **1. Handoff notes.** A note is an append-only entry in a per-area log stored
  as a git ref, `refs/coord/notes/<area>`, keyed by area exactly like a lease.
  The interface is two commands:

  ```
  scripts/coord note  --area <area> --agent "<model>" --text "<fact>"
  scripts/coord notes [--area <area>] [--json]
  ```

  - Notes **never expire** and are **not a lock**: writing one neither takes nor
    holds a lease, and a note never blocks a `claim`. They are read before
    starting an area and written when a fact would otherwise be re-discovered.
  - Appends are **merged, not clobbered**: `append_note` re-reads the log and
    unions, so two agents appending at once both keep their note. The log is
    capped at the most recent `MAX_NOTES` (20) per area.
  - The generated board prints every area's notes under **Handoff notes**, so a
    fresh process sees the handoff with no command; `coord next` can surface them
    too.
  - They are **not** an assignment or a queue — that stays the issue tracker.

  **2. Honest push-auth errors.** `_push_hint()` recognizes credential-failure
  text from git; `_commit_leases` raises a distinct `CoordAuthError` for it, and
  `cmd_claim` re-raises it **verbatim** with an actionable hint instead of
  entering the lost-race branch. A real lost race (non-fast-forward) is still
  reported as a race, with the new holder named.

- **Consequences:**
  - **A stopped agent's findings survive.** The next process inherits the
    handoff through the board or one `notes` call, so the same failure is not
    re-diagnosed every cycle. This is the property the lease, scoped to *now*,
    could not provide.
  - **An auth failure is fixed, not misdiagnosed.** An agent with stale
    credentials is told to fix auth, not sent to inspect an unchanged ledger.
  - **No new dependency, service, or role.** Notes are git refs; the CLI stays
    Python 3 stdlib + `git`; the scheme stays flat.
  - **The transition is additive.** No lease, branch, or PR changes; an agent
    mid-cycle does nothing. Notes appear when the first agent writes one; a
    legacy agent simply has no notes yet, which is not an error. `sweep` never
    deletes a note ref.
  - Covered by `tests/test_coord.py` (`TestNotes`, `TestPushAuthDiagnosis`),
    which exercise the real CLI against a throwaway bare remote.

### Legacy comment-claim reader: retained, not retired

The coordination review asked whether to delete the legacy `CLAIM:` / `LEASE:` /
`TAKEOVER:` comment reader outright. It is **kept**, but **demoted**, for three
reasons:

- It is no longer on any live path. `LEGACY_CLAIM_RE` / `LEGACY_LEASE_RE` /
  `LEGACY_TAKEOVER_RE` are referenced only inside `cmd_migrate`
  (`scripts/coord`), the documented one-off import tool
  (`docs/COORDINATION_MIGRATION.md`). Nothing reads a comment to decide whether
  an area is taken: `list_refs`/`read_lease` read git refs, and the board is
  rendered from the ledger. The mechanism of record is already the ref.
- Deleting it would delete the only written record of how the pre-ADR-0021
  protocol mapped onto the ledger, which a future reader migrating an old hub
  issue needs. It costs a handful of lines and never runs unless invoked.
- Historical data may stay: the guardrail for this work is to preserve the
  history (as with ADR-0021), not to rewrite it.

The decision is therefore **no code change**: the reader stays as a migration
artifact, and the flat ref-based scheme is the only live mechanism. If the fleet
ever wants it gone, the delete is a self-contained removal of the three regexes,
`cmd_migrate`, and the `migrate` help text — no other caller exists.

## ADR-0034 — A lease is identified by agent *and* branch, so same-model agents do not collide

- **Status:** Accepted (2026-10-16)
- **Date:** 2026-10-16
- **Amends:** ADR-0021 / ADR-0033. The git-ref lease and the flat model are
  **kept unchanged**; this fixes how "who holds this lease" is decided.

- **Context:** A lease records a single self-asserted string, `agent`, and the
  docs tell agents to set it to their **model** name (`docs/COORDINATION.md` §2,
  `--agent "Claude Sonnet 4.5"`). A model name is **not unique**: two concurrent
  workspaces running the same model produce the same string, and the ledger
  cannot tell them apart. Observed this cycle: one workspace held
  `release/#350` (branch `release/v0.8.0-dominion`) as `--agent "OpenHands"`;
  from an unrelated workspace also using `--agent "OpenHands"` and sitting on
  `main`,

  ```
  $ scripts/coord next --agent "OpenHands"
  You hold release / #350 (3h left).
  ```

  Rung 1 is `mine = [l for l in leases if l.agent == args.agent]`, so it picked
  the first same-named lease and asserted it belonged to the caller. It did not.
  Worse, `release`/`renew` guard ownership with `lease.agent != args.agent`, so
  for a same-named caller that check **passes**: `scripts/coord release --area
  release --issue 350 --agent "OpenHands"` would delete a peer's **live** lease
  mid-work — the exact double-claim the lease exists to prevent — and the area
  would then look free to a third agent.

- **Options:**

  1. **Require a unique agent id (UUID, hostname, workspace path).** Rejected:
     every in-flight agent would have to change how it claims, and the docs,
     tests, and CI all speak the model name. It also makes the ledger harder to
     read by a human, who wants to know *which model*, not a UUID.
  2. **Keep name-only matching and tell humans to pass distinct names.**
     Rejected: a convention is not a mechanism. Nothing enforces it, and the
     failure (a peer's lease silently freed) is destructive and invisible.
  3. **Key the lease ref by branch as well as area.** Rejected: it changes the
     ref layout and the CAS, and an agent legitimately holds one area while on
     any branch — the branch is metadata about the holder, not a second lock.
  4. **Use the branch the lease already records as a tiebreaker.** Chosen:
     `--branch` is already stored on every claim that passes one, so this adds
     no field and no ref, and it changes no in-flight behaviour.

- **Decision:** **Option 4.** A lease is *mine* only when the `agent` matches
  **and** the `branch` it records is the branch I am on:

  ```python
  def lease_is_mine(lease, agent, branch):
      if lease.agent != agent:
          return False
      if not lease.branch or not branch:   # legacy / no --branch: name alone
          return True
      return lease.branch == branch
  ```

  - `next` rung 1 matches on `lease_is_mine`, so a peer's lease is not reported
    as yours. When a same-named lease exists on a *different* branch, `next`
    says so explicitly (area, issue, that branch) instead of leaving the agent to
    guess from the board.
  - `renew` and `release` refuse when `lease_is_mine` is false. `--force` is
    still the explicit override, and a new optional `--branch` lets a caller name
    the branch instead of relying on `HEAD` (e.g. releasing from elsewhere).
  - A **branchless** lease (legacy, or claimed without `--branch`) has nothing
    to compare, so it matches by name alone — the pre-ADR-0034 behaviour, kept so
    nothing that exists today breaks.

- **Consequences:** Two workspaces on the same model can now coexist without one
  reading or freeing the other's lease; the fix is inert for a solo fleet
  (branchless leases behave exactly as before) and needs no new field, ref, or
  service. The residual limit is honest: if two same-model workspaces also share
  a branch *and* an area, they are genuinely indistinguishable, but they cannot
  both hold the area (the CAS still admits one) — the second is told the area is
  held, which is the correct outcome. Tests in `tests/test_coord.py`
  (`TestSameNameIdentity`) cover the peer-is-not-mine, refuse, `--force`, and
  explicit-`--branch` paths, and are proven to bite by reverting the guard to
  name-only matching.


## ADR-0035 — `coord next` drains the merge queue before claiming fresh work

- **Status:** Accepted (2026-10-15)
- **Date:** 2026-10-15
- **Amends:** ADR-0025 / ADR-0026. The flat, no-coordinator model and the lease
  are unchanged; this inserts one rung into the never-idle ladder.

- **Context:** After the metagame milestone closed, a monitoring pass found the
  fleet **idle in its merge phase**: six areas were free, yet a green, non-draft,
  fully-reviewed PR (#336) sat unmerged for over an hour. The cause is a routing
  gap, not a missing agent:

  - `coord next` reached its "review and merge a PR you did not author" job
    **only at the last rung** — i.e. only when *every* area was held. With areas
    free and claimable issues open, the ladder always offered a **claim** first,
    so a fresh agent started new work and left the finished PR to age.
  - Claiming is the *expensive* action: it commits an agent to a whole cycle and
    makes the newly-started work a fresh orphan risk. Merging a green PR is the
    *cheap* action: the work is already done, reviewed and passing; it needs one
    command. The ladder ranked the expensive action ahead of the cheap one.
  - This is the same class of defect ADR-0025/0026 closed (a wrong routing answer
    burns a cycle and hides finished work), so it belongs in the mechanism, not
    in a convention an agent must remember.

- **Options:**

  1. **Leave it; agents will merge peers' PRs.** Rejected: the observed stall
     proves they do not — all running agents were heads-down on their own claims,
     and the ladder actively steered new agents away from merging.
  2. **Add a coordinator / merge bot.** Rejected — reintroduces authority and a
     service that fails when it pauses (ADR-0019/0021/0025).
  3. **Make draining a rung of `next`.** Chosen: the ladder itself prefers
     merging a waited green PR over claiming non-critical work, so no agent has to
     judge and no human has to nudge.

- **Decision:** **Option 3.** `coord next` gains a rung **between** the
  critical-path claim and the plain claim:

  > 1. finish a held lease → 2. claim a free critical-path issue →
  > **3. drain the merge queue: review+merge a green, non-draft PR open ≥ 30 min**
  > → 4. claim any free area's issue → 5. file the roadmap gap → 6. review a PR.

  A PR is **drainable** when it is open, **not** a draft, its merge state is
  `CLEAN` (mergeable, checks green, no conflicts), and it has been open at least
  `MERGE_DRAIN_MIN_AGE` (30 min). The oldest drainable PR is offered first, so the
  queue drains FIFO and a *stuck* PR is reached before a merely young one.

  The position is deliberate:

  - **It outranks a plain (non-critical) claim.** A green PR is finished work one
    step from landing; merging it beats *starting* new work, which commits a cycle
    and risks orphaning the PR that was already done.
  - **It never preempts the critical path or a waiting blocker** (rung 2). The
    release is never starved by draining, and a peer blocked on a Rule 4 request
    is still unblocked first.
  - **It sits below rung 1.** You finish your own lease before adopting a PR; the
    30-min floor also stops a claim from being abandoned the instant a peer pushes.

- **Consequences:**

  - A green PR can no longer idle behind free areas: the moment it is 30 min old
    and `CLEAN`, `next` offers it to the first idle agent. This is the peer
    replacement for a coordinator draining the queue, now reachable at rung 3
    instead of only at the last rung.
  - **No new command, no new label, no schema change.** `next` reads one more
    GitHub query (`pr list`) and narrows what it offers; `claim`/`renew`/`release`
    are untouched and the lease is still the lock.
  - Best-effort like every `next` read: `gh` absent, offline, or unauthenticated
    yields no drainable PRs and the ladder falls through — `next` still answers.
  - **The transition is a no-op for in-flight agents.** Only a read-only command
    changes; no lease, branch or PR is affected.
  - Covered by `tests/test_coord.py` (`TestNextAction.*drain*`, `TestDrainablePrs`),
    which stub the GitHub reads and assert the ordering (drain before plain claim,
    after the critical path, never ahead of your own lease).

## ADR-0036 — A major version is gated behind a feature-complete, human-approved candidate

- **Status:** Accepted (2026-10-16)
- **Date:** 2026-10-16
- **Amends:** ADR-0024 (the v1.0.0 scope fence) and `AGENTS.md` §6a (releases).
  The scope fence and the minor-release process are unchanged; this adds the
  **major-version** step the process was missing.

- **Context:** `AGENTS.md` §6a defines what a *release* is — a frozen, playable
  snapshot a human can playtest — and how to cut one (`0.x.0` minor releases,
  one tag per branch, a `CHANGELOG.md` entry, `docs/releases/**`, a GitHub
  Release page). It says nothing about a **major version** (`X.0.0`). The next
  major version, **v1.0.0**, is the project's whole goal: §9 and
  `docs/ROADMAP.md` define it as *feature parity with the 1993 original*, playable
  end to end. As written, an agent could tag `v1.0.0` the moment CI is green,
  with **no rule** requiring that a build implementing the full v1.0.0 scope
  exist, that a human have played it, or that it be approved. That is the one
  release where the claim on the tin ("this is the finished clone") is large
  enough that shipping it un-played is a real risk — and it is irreversible under
  §6b (a released tag is immutable).

- **Options:**

  1. **Treat v1.0.0 as just another minor release.** Rejected: it removes the only
     human checkpoint in front of the project's headline claim. CI proves it
     *builds and its tests pass*; it cannot prove the game *is the finished clone*
     a person would enjoy. The two are exactly the gap a major version closes.
  2. **Gate every release, including minors.** Rejected: §6a deliberately keeps
     minor releases cheap ("cut one whenever a hands-on playtest is useful; do not
     wait for a finished game"). A mandatory approval on every `0.x.0` would stall
     the fleet on a human and defeat that rule.
  3. **Gate only major versions behind a candidate + human approval.** Chosen:
     cheap releases stay cheap, and the single large, irreversible claim gets one
     explicit human checkpoint.

- **Decision:** **Option 3.** Add a **major-version gate** to §6a:

  > A **major version** (`X.0.0` — first is **v1.0.0**) may be rolled out only
  > after:
  >
  > 1. A **release candidate** exists that **implements everything** in that
  >    version's Definition of Done (for v1.0.0: `docs/ROADMAP.md` →
  >    *Definition of Done — v1.0.0*, §9) — no missing feature, no "will land
  >    later" carve-out.
  > 2. That candidate is **buildable and playable by a human** from the exact
  >    branch/tag, following its `docs/releases/vX.Y.Z-*.md`.
  > 3. A human has **playtested** it and **approved** the rollout, recorded on the
  >    candidate's GitHub Release page (or its tracking issue) via
  >    `docs/releases/MAJOR_RELEASE_GATE.md`.
  >
  > Only then is the major **tag** cut and the version **rolled out**. The
  > candidate is tagged as a **pre-release** (e.g. `v1.0.0-rc.1`) so §6b
  > immutability applies to the candidate too; if the playtest finds gaps, cut
  > `-rc.2` rather than re-tagging. Minor releases (`0.x.0`) keep §6a unchanged.

  The gate is **human-owned**: agents prepare the candidate, the release notes,
  and the checklist, and a human supplies the approval. An agent must never
  self-approve a major version (unlike the §3a sole-account merge rule, which is
  about merging PRs, not about declaring the game finished).

- **Consequences:**

  - Every major version has exactly one human checkpoint, in front of the
    irreversible, headline release. Minor releases are untouched, so the fleet
    is not gated on a human for routine work.
  - The gate needs a **record**, so `docs/releases/MAJOR_RELEASE_GATE.md` is the
    checklist a candidate carries and a human signs; it is the single source for
    "what does approval mean", referenced by §6a, §9, `docs/ROADMAP.md`, and the
    release area's remit in `docs/FOCUS_AREAS.md`.
  - **No code, no new dependency, no CI change.** The gate is docs + a pre-release
    tag + a human approval; `ctest` and the seven CI jobs are unaffected.
  - **v1.0.0 is not yet candidate-able**: `docs/ROADMAP.md` Milestone C still has
    open items (destructible environment, the mission set, original art/audio,
    save/load, balance). The gate makes that the explicit precondition rather
    than something an agent might discover late.
