## 1. What this project is

An open-source, from-scratch recreation of the *gameplay* of the 1993 DOS game
**Syndicate** (and elements of **Syndicate Wars**). We recreate mechanics,
feel, and systems. We do **not** ship, copy, or trace any original asset, code,
name, or trademark. See `docs/LEGAL.md`.

- **Language:** C++17
- **Game framework:** SDL2 + `SDL_Renderer` (see ADR-0006; Cocos2d-x was
  dropped as too heavy — see ADR-0001)
- **Build:** CMake ≥ 3.15 + `scripts/*.sh`
- **Primary platform:** Debian-based Linux (Linux Mint, Ubuntu). macOS and
  Windows are supported and documented, but not tested regularly.
- **License:** MIT (see `LICENSE`)

### Goal for v1.0.0 — faithful reproduction

**v1.0.0 aims to reproduce the original 1993 game as closely as possible**
within legal bounds: the same feel, the same systems, and — deliberately —
the **same chunky pixel-art look**, because that *is* the original look and
feel. So for v1.0.0, **prefer pixel graphics**: low-resolution raster art,
palette-based, nearest-neighbour scaled, authored at the original's native
scale. Vector art (e.g. SVG) and other "improved" graphics, higher-fidelity
rendering, smoother/modern handling, and quality-of-life changes are **out of
scope for v1.0.0** — they belong to a **v2.x.x** release or to a **fork**.

Rules that follow from this:

- Do **not** modernise the visuals or the interface as part of v1.0.0 work; match
  the original instead.
- The low-spec / old-hardware profile (ADR-0008) is aligned with this goal: the
  original ran on hardware of that era, so a small, low-resolution, software-
  rendered build is the faithful target, not a limitation to escape.
- We still copy **no** original asset, sprite, palette file, code, name, or
  trademark. Faithfulness means recreating the *feel* and the *look* with
  original art, never shipping the original's files (see `docs/LEGAL.md`).

**Scope is fenced (ADR-0024).** v1.0.0 is **feature parity with the 1993
original** and nothing more. `docs/ROADMAP.md` holds the **Definition of Done**
(what "finished" means) and the **"Not in v1.0.0"** fence. The short version:
things the original did **not** have — localisation beyond English, a modding /
scripting layer (ADR-0004), modern quality-of-life, extra platforms beyond Linux,
multiplayer — are **out of scope for v1.0.0** and deferred to a v2.x.x line or a
fork. Before starting work, check it against the fence; if a task is out of scope,
do not build it. Out-of-scope work needs a **human decision**, not an agent's
enthusiasm: open an issue with `question` and propose it.

## 1b. Target machines — keep it lightweight

The game must run on **very old, low-end hardware**: think a computer that was
low-end 15 years ago. It does **not** need to run on a 386, but it must not
require a modern GPU or lots of RAM.

Practical rules:

- Prefer a software-rendered path (we use `SDL_Renderer`, which can fall back to
  the software backend) over a hard OpenGL/Vulkan requirement.
- Keep the binary and its dependencies small; avoid pulling in large frameworks.
- Keep per-frame work cheap: no per-pixel effects on the critical path, prefer
  tiles/sprites and cached surfaces.
- Do not assume a dedicated GPU, large VRAM, or a fast CPU.
- Profile assumptions: target smooth play on integrated graphics from ~2010.
- Build the low-spec profile (`-DFOSSYND_LOW_SPEC=ON`) or run with `--low-spec` to
  get the smallest binary, a small window, and the software renderer (ADR-0008).
  CI builds this profile on every change. A game that will not start on very old
  hardware is a bug.

## 1c. Dependencies — open source first

For every tool, library, and dependency, **prefer open source**. Choose a
permissively licensed (MIT/BSD/zlib/CC0) option compatible with our MIT license
(`docs/LEGAL.md`). Avoid proprietary toolchains where an open one works. If you
must add a dependency, record why in the PR and, if architectural, in an ADR.

## 1d. Keep the fleet small (resource policy)

**Capacity is not a goal** (ADR-0024). The coordination scheme supports 1–10
agents, but running more agents than the work needs wastes resources. The normal
target is **1–4 agents**. Start (or request) an additional agent only when there
is **critical-path work** for it in `docs/ROADMAP.md` that genuinely parallelises
with what is already running — for example, Milestones A and B are independent.
"There is an open issue" is **not** by itself a reason to start an agent, and an
out-of-scope item never is. When in doubt, fewer agents.

This is a *resource* policy, not a coordination rule: it changes **how many**
agents run, never **how** they coordinate (still flat, ADR-0019/0021).

A small fleet only works if every agent always has something to do. That is the
job of `scripts/coord next` (§3.16): an idle agent asks for its next action and
always gets one — claim, seed an issue, or review. Keep the **backlog floor**
above zero: when an area is free and has no open issue, the fix is to **file the
next roadmap item as an issue**, not to idle or to add agents.

## 3. Multi-agent coordination protocol

Many models edit this repo. Coordination is **flat** (no coordinator, ADR-0019)
and **machine-checked**: a claim is a **git-ref lease**, not a comment
(ADR-0021). The whole protocol is `docs/COORDINATION.md`; the short form:

1. **One task = one branch = one PR.** Use the branch naming scheme in §6.
2. **Claim before you build, with the ledger.** `scripts/coord claim --area
   <area> --issue <n> --agent "<role>-<n>-<host>" --branch <branch>`. The **area is the
   lock** (`docs/FOCUS_AREAS.md` §2): a live lease on an area blocks a second
   agent from it. `scripts/coord status` is authoritative — do not read comment
   timestamps. The claim is a **lease** with a TTL (default 6 h, max 24 h);
   `scripts/coord renew` extends it and `scripts/coord release` ends it.
3. **Small, reviewable PRs.** Prefer < ~400 changed lines. Split large features.
4. **Never force-push a branch another agent may be using.** If you must rewrite
   history on a shared branch, say so in the PR first.
5. **Record decisions in `docs/DECISIONS.md`** (ADRs) before implementing
   anything architectural. If two agents disagree, the ADR decides; if none
   exists, open an issue and ask a human.
6. **Leave the tree green.** Every PR must build and pass `ctest`. Never merge
   red.
7. **State your agent name and model** in the PR description (e.g.
   "`ta-1-kastenbrot`, Claude Sonnet 4.5"). The name is your identity in the
   ledger (`<role>-<n>-<host>`, `docs/ORGANISATION.md` §3); the model alone is
   not unique. This makes handoffs debuggable.
8. **Keep this file current.** When your PR changes how we build, test, or
   coordinate, update `AGENTS.md` in the same PR.
9. **Review and merge each other's PRs.** See §3a. This applies to every agent
   and to human maintainers.
10. **Work inside your focus area.** The repo is divided into focus areas (the set
    is data — `docs/focus-areas.json`, docs/ORGANISATION.md §9; eleven today; see
    `docs/FOCUS_AREAS.md`). One of them (`rules`) is the **SM's own lane**: the SM
    triggers it and `coord next` never routes a plain worker to it; every other
    lane, **including `platform`** (build/CI/packaging), is a normal **worker**
    lane — the SM never does project work (ADR-0041). Claim a **free** area with
    the **highest pending
    workload**, preferring one you already know. Only the agent holding the
    area's live lease (or a helper it explicitly tasks) edits the files an area
    owns. Need a change in another area's files? File a cross-area request
    (`docs/FOCUS_AREAS.md` §4, Rule 4) — never edit them yourself.
11. **Leases expire; abandoned work is reclaimed by the clock.** A lease past its
    TTL is **dead** and any agent may claim the area (`scripts/coord claim`), or
    take a live-but-quiet one — **stale after 2 h** — with `--takeover`
    (announced, never silent), or by first filing a cooperative **takeover
    request** (`scripts/coord takeover --request`, which `coord next` surfaces;
    `docs/ORGANISATION.md` §6a). There is **no reassignment step** and no
    coordinator. If you stop mid-task, your lease ages out on its own — no peer
    or human has to notice.
12. **There is no coordinator; coordination is flat.** No agent owns the merge
    queue, the workload plan, or the process docs, and no agent has authority over
    another's focus. Review and merge any PR you did not author (§3a); adopt an
    orphaned green PR (its holder now shows as **stale** on the board); resolve
    overlaps by the fixed rules in `docs/FOCUS_AREAS.md` §4, where **merged code
    wins ties**. Process-doc changes are self-service too, needing two peer
    reviews (`docs/FOCUS_AREAS.md` §6). There is no `focus: coordinator` label.
13. **Questions are answered by the rules, or go straight to the human.** Read
    `AGENTS.md` and `docs/FOCUS_AREAS.md` first — scope/ordering/ownership/process
    questions are answered there and any agent applies them itself. If the rules
    are genuinely unclear, **propose the answer** (an ADR or a rules PR) and
    proceed on the reversible path. A question needing a **human decision**
    (product direction, licensing, a rule change, release policy) is posted by the
    **asking agent itself** on the issue thread (`question` + `status: blocked`),
    with options and a recommendation — **no relay, no waiting silently**. See
    `docs/COORDINATION.md` §3.
14. **Helpers are requested, never self-started.** An agent whose queue is empty
    must not begin work in another area on its own. It works on tasks assigned by
    that area's live owner; if the area has **no live lease**, it self-claims it
    (`scripts/coord claim`). There is no availability announcement — the ledger
    (`scripts/coord status`) is the signal (ADR-0021). Reviewing PRs and triaging
    issues need no assignment (`docs/FOCUS_AREAS.md` §5).
15. **The board is generated.** `docs/COORDINATION_BOARD.md` is rendered from the
    ledger by `scripts/coord board` and rewritten by the scheduled sweep. Never
    hand-edit it and never open a "refresh the queue" PR — the old hand-maintained
    §8 table is gone (ADR-0021).
16. **An idle agent always has a next action — ask for it.** Run `scripts/coord
    next --agent "<role>-<n>-<host>"` whenever you do not know what to do. It never prints
    nothing: it walks a fixed ladder and stops at the first rung that applies —
    (1) finish/renew a lease you hold, (1b) if you are the **SM**, claim a free
    `rules` issue (the SM's own lane — the process docs; the SM never does
    project work, and a plain worker is never routed to `rules`, ADR-0041), (2) claim a free
    **critical-path** area's issue, (3) **drain the merge queue**: review and
    merge a green, non-draft PR
    that has waited ≥ 30 min (§3a), (4) claim any free area's issue, (5) **file a
    new issue** from the roadmap when the backlog is empty, (6) otherwise review
    an open PR you did not author (§3a). Rung 3 exists because a green PR is
    *finished* work one step from landing: merging it is worth more than starting
    new work, and it is how the fleet drains the queue instead of leaving a green
    PR to age (ADR-0035). The fleet must never stall for want of something to do;
    when it does, the fix is to **add work**, never to add agents (§1d,
    ADR-0024).
17. **Hand off through notes, not memory.** A lease is scoped to *now*: it is
    released or expires, so a fact the *next* process needs has nowhere else to
    live. Write it to the area's note log — `scripts/coord note --area <a> --agent

    claim. Use one for broken tooling, a trap in the area, or a decision not to
    re-litigate; do **not** use it as a queue or an assignment (§3, ADR-0033).
    The key may also be a **channel** — `sm`, `po`, or `takeover` — for the
    process roles (`docs/ORGANISATION.md` §5).
18. **Know your role, and know the budget.** Each computer has a **Product
    Owner** (decides *what* is built, the priority order, the backlog, and the
    worker prompts) and a **Scrum Master** (watches coordination: the roster,
    blockers, the merge queue, seeding issues; it owns the one **`rules`** lane —
    the process docs — and triggers that work itself; it may merge
    PRs and open/close issues in its scope, and — while the repo has one GitHub
    account — self-review a rules-doc PR). Neither owns a *game* focus area, and
    neither may assign work or override a live lease. **Talk to peers directly**
    (`scripts/coord msg` / `scripts/coord inbox`): a generated prompt is only for
    starting a chat that does not exist yet, and the human is copied in only on a
    genuine human decision (docs/ORGANISATION.md §5). The **daily agent budget is shared across computers
    and other projects** and is enforced by the **human**, not the tooling, so
    keep task scopes **small enough to reuse a worker** for the next task rather
    than requesting a new chat. See `docs/ORGANISATION.md`.
## 3a. Reviewing and merging other agents' pull requests

Agents should keep the queue moving: **review open PRs that you did not author
and merge them when they are good.** A stale, green PR that nobody merges is
lost work. **No one owns the queue** (there is no coordinator, §3.12): the first
free agent merges the oldest mergeable PR, and **adopts an orphaned PR** (its
author gone quiet — its area now shows as a **stale** holder on the coordination
board, `docs/COORDINATION.md` §4) by reviewing and merging it itself.
This is how the fleet drains the queue without any agent depending on another.

**Who may merge.** Normally, merge PRs **authored by someone else**: the point is
independent review, so do not merge your own PR while another agent or human can
review it.

**Exception — sole account.** As long as the GitHub account that owns this
repository is the *only* account working on the project (i.e. you are the only
active author and there is no separate reviewer to hand off to), the **creator
may review and merge their own PR**. This is the normal mode of operation, not a
last resort. Still do the review below honestly, and say in the merge comment who
merged it (the model) so handoffs stay debuggable (§3.7). Once a second account
joins the project, revert to the "review someone else's PR" rule.

**Before merging, verify (in this order):**

1. **Not a draft.** (Your own PR is acceptable only under the sole-account rule
   above.)
2. **Scope and legality.** It matches its stated intent, stays within the
   project's goals (§1 — for v1.0.0, pixel-faithful, no modernising), and
   introduces no copyrighted asset, name, or code (`docs/LEGAL.md`).
3. **CI is green** on the PR head (all jobs: core, core+game, low-spec,
   sanitizers, warnings-as-errors, packaging).
4. **Mergeable** — the PR is not conflicted with `main`. If it is conflicted,
   the author must rebase; do not force it.
5. **Review the diff.** Read it. Confirm tests exist for new `core` logic, no new
   compiler warnings, and that new files carry the AI-attribution marker (§1a).
6. **Sanity-check locally** when practical: build the PR's head (or trust green
   CI if the environment cannot build it). For engine changes, run the game.
7. **Tone of the change.** It follows the golden rules (§4) and does not smuggle
   in unrelated churn.

**How to merge.** Prefer a **squash merge** (one logical change per PR, §6),
with the PR title as the commit subject. Use the async merge API and confirm the
final status is `merged` (not merely `enqueued`):

```bash
gh api -X PUT repos/<OWNER>/<REPO>/pulls/<N>/merge-async -f merge_method=squash -f sha=<HEAD_SHA>
# then poll until status != pending
gh api repos/<OWNER>/<REPO>/pulls/<N>/merge-async/<UUID>
```

**When to hold instead.** Do not merge if any of these is true — leave a review
comment explaining why and let the author respond:

- The PR is a draft, is conflicted, or CI is red or still running.
- You cannot tell what it changes, or it does not match its description.
- It changes architecture without an ADR (§3.5), or touches `main` history.
- It looks like it needs a human decision (e.g. a rename of the project, a
  licensing question, a change to these very rules) and no agent has yet
  confirmed it with the human on the thread.
- It was opened by a human who is actively iterating.

Record the review in the PR: a short comment with the verdict (`approved and
merged`, or `holding: <reason>`). When you merge, say which model did the merge,
so handoffs stay debuggable (§3.7).

## 4. Golden rules of the codebase

These are non-negotiable unless an ADR supersedes them.

1. **Engine-agnostic core.** All game logic (math, world model, pathfinding,
   combat rules, economy) lives in `src/core/` and must **not** include
   `SDL.h`. It must build and be unit-testable with a plain compiler.
   Rendering/input/audio live behind the engine layer (`src/game/`, `src/world/`,
   `src/entities/`).
2. **Core is pure and testable.** No global mutable state in `core`. Prefer
   free functions and small value types. Deterministic where possible.
3. **No engine types in public core APIs.** Use our own `Vec2`/`TilePos`, not
   `SDL types`, in `core`.
4. **Simulation ≠ rendering.** Gameplay ticks on a fixed timestep; the renderer
   interpolates. Never derive gameplay outcomes from frame rate.
5. **Tests are real.** Unit tests call real code paths. No mocks unless the
   dependency genuinely cannot run headless — and then justify it in a comment.
6. **Every new core system ships with tests** in `tests/`.
7. **Data over code.** Weapons, agents, missions, and balance values live in
   data files (see §7), not hard-coded constants, so multiple agents can extend
   content without merge conflicts in C++.
8. **Assets are original or explicitly licensed.** No ripped sprites, sounds,
   fonts, or names. See `docs/ASSETS.md`. **Prefer pixel art** for v1.0.0: the
   goal is to match the original's chunky low-resolution look (§1). Author
   sprites and tiles as low-resolution, palette-based raster images and scale
   them nearest-neighbour. Vector/SVG art is not the v1.0.0 default; it is a
   v2.x.x (or fork) concern. Runtime-generated primitives remain the placeholder
   strategy until real pixel art exists.
9. **Warnings are errors in spirit.** The build uses `-Wall -Wextra -Wpedantic`.
   Do not merge code that adds warnings.
10. **Small commits, descriptive messages** (§8).

## 6a. Releases and release branches

A **release** is a snapshot a human can playtest. Cut one whenever a hands-on
playtest is useful — in practice, whenever gameplay has changed enough to show
something to (potential) players. Do not wait for a "finished" game.

Rules:

1. **One release = one tag = one `release/vX.Y.Z-<slug>` branch** off `main`,
   plus a GitHub Release page. Follow SemVer and keep a matching `CHANGELOG.md`
   entry. Existing examples: `release/v0.1.0-playable-slice`,
   `release/v0.2.0-command-control`, `release/v0.3.0-bystanders`,
   `release/v0.4.0-smart-enemies`, `release/v0.5.0-recruitment`,
   `release/v0.6.0-firestorm`, `release/v0.7.0-demolition`,
   `release/v0.8.0-dominion`.
2. **Every release must be visibly different from the previous one.** A player
   who runs both builds should immediately see *something* changed. While the
   game is small, this is strict: the change must be obvious, not subtle. Once
   the game is complex enough, changes may be small enough that casual players
   miss them — but never ship a release that looks identical to the last.
3. **Every release branch carries version-specific build & play instructions**
   in `docs/releases/vX.Y.Z-<slug>.md`. They must be specific to *that* tag and
   branch (e.g. checking out the correct branch/tag after cloning), and must
   include **how to copy which files and directories where** to get a runnable
   copy of the game onto another computer. The same file is **also kept on
   `main`**, so the record is complete without checking out a tag (see the
   history rule below).
4. **Graphics** follow golden rule 8 and §1: for v1.0.0 the target look is the
   original's, so prefer **pixel art**. Do not gate a release on vector/SVG art.
5. Update `AGENTS.md` §10 and the roadmap when a release ships.
6. **`main` is the complete record.** Everything the project has shipped must be
   visible on `main`: keep the full, numbered `CHANGELOG.md` history there (add
   the new version's section to `main`, don't only write it on the release
   branch), and keep each release's `docs/releases/vX.Y.Z-<slug>.md` on `main`
   too. A release branch may carry an identical copy; it is not the only copy.
   When a release ships, land these on `main` in the same change that records it
   in §10. (This rule exists because v0.3.0 and v0.4.0 initially left their
   changelog sections and release docs only on their release branches.)

A release branch is a frozen, playable snapshot: keep it building and playable,
and do not let unrelated work drift onto it.

### 6a-i. Major versions need a feature-complete, human-approved candidate

Rules 1–6 above cover **minor** releases (`0.x.0`): cut one whenever a playtest is
useful. A **major version** (`X.0.0` — the next is **v1.0.0**) is different: its
claim is "this is the finished clone", it is irreversible under §6b, and it is
the one release a machine cannot validate. So a major version may be rolled out
**only** after all of:

1. **Feature-complete candidate.** A build exists that **implements everything**
   in that version's Definition of Done — for v1.0.0, `docs/ROADMAP.md` →
   *Definition of Done — v1.0.0* and §9 below. No missing feature, no "lands
   later" carve-out; the candidate is the whole scope or it is not a candidate.
2. **A human can build and play it.** From the candidate's exact branch/tag, a
   human follows its `docs/releases/vX.Y.Z-*.md` and gets a runnable copy on
   another machine.
3. **Human approval.** A **human** has playtested the candidate and **approved**
   the rollout, recorded via `docs/releases/MAJOR_RELEASE_GATE.md` on the
   candidate's GitHub Release page (or its tracking issue).

Only then is the major **tag** cut and the version **rolled out**. Details:

- **Tag the candidate as a pre-release** — e.g. `v1.0.0-rc.1` — so §6b
  immutability applies to it; if the playtest finds gaps, cut **`-rc.2`**, never
  re-tag. The final `vX.Y.Z` tag is cut only after approval, on the approved
  commit.
- **The gate is human-owned.** Agents prepare the candidate, the release notes,
  and the filled-in checklist; a **human supplies the approval**. An agent must
  **never self-approve** a major version — the §3a sole-account self-merge rule is
  about merging PRs, not about declaring the game finished.
- **It cannot be waived by an agent.** If the scope is not done, the honest move
  is to keep shipping `0.x.0` milestones (ADR-0025 §3.7), not to cut `1.0.0`.

Reasoning: **ADR-0036**. Minor releases (`0.x.0`) are unchanged by this section.

### 6b. Release branches are immutable

Once a release is published (tagged, with a GitHub Release page), **do not touch
its branch or tag again.** No new commits, no rewrites, no re-tagging — not for
docs, not for cleanup, not for "small" fixes. A released branch is an artifact a
human may already have cloned and built.

The only exception is when leaving it alone would **break the project or is
legally required** — for example, a required library the release depends on has
been removed, so the documented build no longer works.

When that happens, do **not** edit the old branch. Instead:

1. Cut a **new branch off the finished release branch** (e.g.
   `fix/v0.3.0-<short-desc>`), apply the minimal fix there, and record why in the
   commit and in `docs/DECISIONS.md`.
2. Leave the original branch and tag exactly as they were, and say so in the new
   branch's PR description (which release it repairs and why the original is
   untouched).

If a correction is only needed for the *current* line of work, it belongs on
`main` (or the next release), never back-ported onto a shipped snapshot.

## 7. Data & content

- Balance/content data lives in `assets/data/` as **JSON**, e.g.
  `assets/data/missions/*.json`. The format is fixed by **ADR-0003** and

## 8. Build & test (canonical commands)

```bash
# Full build: core + tests + the SDL2 game target.
./scripts/build.sh

# Or manually (Debian/Ubuntu: sudo apt-get install libsdl2-dev)
cmake -S . -B build -DFOSSYND_BUILD_GAME=ON
cmake --build build -j
ctest --test-dir build --output-on-failure

# Core-only build + tests (no SDL needed) — this is what CI runs.
cmake -S . -B build-core -DFOSSYND_BUILD_GAME=OFF
cmake --build build-core -j
ctest --test-dir build-core --output-on-failure

# Core + tests under ASan + UBSan (developer/CI; ADR-0015).
cmake -S . -B build-san -DFOSSYND_BUILD_GAME=OFF -DFOSSYND_SANITIZE=ON -DCMAKE_BUILD_TYPE=RelWithDebInfo
cmake --build build-san -j
ctest --test-dir build-san --output-on-failure

# Warnings are errors (developer/CI; issue #192) — a warning fails the build.
cmake -S . -B build-werror -DFOSSYND_BUILD_GAME=ON -DFOSSYND_WERROR=ON
cmake --build build-werror -j
ctest --test-dir build-werror --output-on-failure
```

CI runs seven jobs on every push/PR: a **core + game** job (installs
`libsdl2-dev`, builds with `-DFOSSYND_BUILD_GAME=ON`, runs `ctest`, which
includes the headless `game_smoke` test), a **core-only** job (no graphics deps),
a **low-spec** job (`-DFOSSYND_LOW_SPEC=ON`, ADR-0008) so old-hardware support
cannot bit-rot, a **sanitizers** job (`-DFOSSYND_SANITIZE=ON`, core-only,
ADR-0015) that runs the unit tests under ASan + UBSan, a **warnings-as-errors**
job (`-DFOSSYND_WERROR=ON`, core + game) so a warning cannot land on `main`
(issue #192), a **shellcheck** job (`shellcheck scripts/*.sh`, issue #286) so a
shell-script bug like the #256 shebang-above-the-marker one is caught
mechanically rather than by a human, and a **packaging** job
(CPack, ADR-0017) that builds the Linux `.tar.gz` + `.deb` and runs the packaged
binary. Two further packaging lanes — **macOS** (`TGZ` + `DMG`) and **Windows**
(`ZIP`) — are **gated to `workflow_dispatch` and non-blocking**, because those
runners can queue and be cancelled before starting, which would redden `main`
and deadlock merges (#136, #138). Dispatch the workflow to exercise them. If your
change touches `src/core/` or `tests/`, all seven push/PR jobs must pass. If it
touches `src/game/`, also run the game target locally and note the result in the
PR.

## 9. Definition of Done

**For v1.0.0 (the project).** v1.0.0 is done when the game is at **feature parity
with the 1993 original** and playable end to end. The authoritative, checkable
list is `docs/ROADMAP.md` → *Definition of Done*. In short: a player can start a
corporation, tax territories, research and buy equipment, pick and deploy a
squad on a mission, win or lose with the full tactical system, and progress to an
end state — all with original code and art, and **nothing** outside the scope
fence (ADR-0024). If that list is true, we are done; if a proposed change does not
move us toward it, it is out of scope.

- **"Walk as close as you can" (issue #146):** `core::findPathToNearest` returns
  `findPathDetailed`'s result when the goal is reachable, but when the goal is
  blocked, out of bounds, or cap-abandoned it returns a path to the walkable tile
  reachable from `start` that is nearest the goal (Manhattan, tie broken by
  lowest tile index), so a click on an unreachable tile moves the squad toward it
  instead of being dropped. `start` is never the fallback (the point is to
  *move*); `NoPath` only when `start` is invalid or nothing else is reachable.
  The bounded BFS reuses the same node cap (ADR-0008) and corner rule as
  `findPath`. Consumer side (engine/input) is Input/UI's — a follow-up.
- **`Rng::nextFloat()` is truly half-open `[0, 1)` (issue #383):** the old
  mapping `float(nextUint64() >> 11) * 2^-53` narrowed the all-ones 53-bit draw
  *up* to `2^53`, so it returned exactly `1.0f` about once in 50M draws — outside
  the documented range and a latent determinism trap. `nextFloat()` now clamps
  that single case to `0x1.fffffep-1f` (largest float < 1); every other draw is
  bit-for-bit unchanged, so no existing seed or test outcome shifts. `Rng` is
  world-owned (`src/core/util/Rng.h`); use it, never `<random>`/`rand()`, in core.
- **Reachability primitive (issue #188):** `core::reachableTiles` returns every
  walkable tile reachable from a start (in stable row-major order, start
  included), and `core::areConnected` is a thin wrapper asking whether one tile
  is in another's set. Both take the same `allowDiagonal` flag and node cap as
  `findPath`, and share one internal `bfsReachable` walk with `findPathToNearest`
  — so reachability and `findPath` agree exactly on the walk, the 4/8-way corner
  rule, and the ADR-0008 budget. Use them instead of an A* per target for mission
  validation (is the objective walled off?) or AI reachability; they are
  deterministic and RNG-free.

- **Perception is a per-agent stat (issue #333):** `core::Agent` carries a
  `sightRange()` (tiles, straight-line; `setSightRange` clamps negatives to 0),
  defaulted to `kDefaultSightRange` (`12.0f`, the value the AI used before the
  field existed) so adding it changes no behaviour. It exists so two agents can
  perceive differently and a cybernetic "eyes" upgrade has a stat to raise. The

- **Agent routes are string-pulled (issue #93):** `findPath` with
  `allowDiagonal=true` post-processes the A* path with string-pulling
  (`core/world/LineOfSight.h`) so an agent walks straight between corners instead
  of staircasing. **`Agent::moveTo` must pass `allowDiagonal=true`** for this to
  take effect — it does. (PR #99 added the smoothing but left `moveTo` on the
  4-way default, so it was inert in game until #101 wired it up.) Smoothing never
  adds or moves a waypoint, so a route stays a subsequence of the A* path and is
  always walkable. Deterministic, RNG-free; the 4-way path is returned unchanged.
  **The smoothing pass is bounded by the A* node budget (issue #309):** it may
  spend at most `maxExpandedNodes` `hasLineOfSight` probes, then keeps the raw A*
  tail. It is otherwise unbounded by the cap (O(n²) in the waypoint count — a
  60x60 serpentine cost ~1.6M probes / ~54 ms vs. ~180 us for the search), which
  would stall a frame (ADR-0008). Realistic orders stay far under the budget, so
  their smoothing is unchanged. `simplifyPath` is internal to `Pathfinding.cpp`.
- **A move route keeps the agent's own tile centre as its first waypoint:**
  `Agent::moveTo` (and `Vehicle::driveTo`) set `nextWaypoint_ = 0` for a
  *new* route instead of skipping the start tile. A path is validated
  centre-to-centre, but an agent stands at a fractional position, so walking
  straight at the second waypoint could cut the corner of a tile the centre line
  never touched — the agent clipped a wall (fuzz: ~1 in 2500 off-centre orders)
  and, once its tile was blocked, `findPathToNearest` refused to move it, so it
  was **permanently stuck**. Visiting the tile centre first makes every walked
  segment a validated centre-to-centre segment. Re-issuing the *same* route
  (`path_ == found.path`) keeps the current `nextWaypoint_`, because the AI
  re-paths every tick while retreating (`Mission::stepAwayFrom`) — resetting the
  index each tick oscillated the agent back to its centre (caught by
  `Mission.WoundedEnemyRetreats`). Guards (issue #409):
  `Agent.MoveToNeverEntersABlockedTileFromAnOffCentrePosition` and the Vehicle
  mirror `Vehicle.DriveToNeverEntersABlockedTileFromAnOffCentrePosition` pin the
  start-waypoint half, and `Agent.MoveToReissuedSameRouteKeepsProgress` /
  `Vehicle.DriveToReissuedSameRouteKeepsProgress` pin the same-route half (each
  fails under the corresponding pre-#398 behaviour).

- **Sound effects are a hand-rolled SDL2 layer (issue #423, ADR-0040).**
  `game::Audio` (`src/game/Audio.{h,cpp}`, its own translation unit — do not grow
  the shared `Game.cpp`) owns one `SDL_OpenAudioDevice` and a small fixed set of
  **generated** cues (`Shoot`, `Hit`, `Explosion`, `Victory`, `Defeat`) mixed
  into a streaming buffer fed with `SDL_QueueAudio`. **No new dependency** (SDL2
  is already linked, so `SDL_mixer` was rejected) and **no audio asset** — every
  cue is synthesised, so nothing can be copied from the original (golden rule 8).
  It is **never fatal**: when no device opens (a headless run, no sound card, a
  driver that cannot provide the baked format) it logs one `audio: disabled (...)`
  line and stays a silent no-op, so `enabled()` is false and every later call is
  harmless — the game always runs (AGENTS.md §1b). `Game::update` calls
  `updateAudio()` then `audio_.update()`: `updateAudio` snapshots the frame's
  events (the core's kill counts and mission state, plus `anyShot` derived from an
  agent's `gunfireTimer()` *rising* — `Agent::beginFireCooldown` sets it to 0.75
  on every shot) and turns them into cues through the **pure, device-free
  `cuesForFrame(previous, current)`**, which fires only on a *change* (a new kill,
  a decided outcome) so a steady state is silent and a kill/outcome fires once.
  View-only; it never writes core (golden rule 4). A headless run opens no device
  at all. **SFX are in scope for v1.0.0; music is not** (ADR-0024). The
  `--check-audio` guard (ctest `game_audio`) drives the real synthesis/mixing path
  and the real `cuesForFrame` mapping with no device: it fails on an empty or
  silent cue, non-deterministic synthesis, a mixer that does not sum cues, a
  disabled `Audio` that is not a no-op, a steady frame that fires a cue, or a
  kill/outcome that fires twice or maps to the wrong cue. The `docs/BUILD.md`
  audio-troubleshooting note is a **Release**-owned follow-up (a Rule 4 request,
  not an edit from Platform).
